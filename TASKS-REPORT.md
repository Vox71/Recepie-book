# Отчёт о выполненных задачах: бэкенд проекта «Recepie-book»

Документ написан в двух слоях, чтобы его могли читать и менеджер, и новый разработчик
(джун/стажёр):

- **для менеджера** — разделы «Итог», «Что сделано сверх задач», «Ограничения», «Словарь терминов»;
- **для разработчика** — разделы «Как устроен код», «Поток одного запроса», «Как добавить новый
  адрес», «Как читать тесты», а также блоки **«Для разработчиков»** внутри каждой задачи
  (файлы, функции, что именно проверяется).

Работы разделены на пять задач, каждая — отдельный участник:

1. **Подключить базу данных** — данные сохраняются между перезапусками, транзакции, миграции.
2. **Создать Flask-приложение** — 19 адресов из контракта, валидация, единая обработка ошибок.
3. **Авторизация** — регистрация и вход, пароль в виде хэша, JWT для личных экранов.
4. **Тесты API** — 93 автоматические проверки, у каждого адреса есть успешный и «плохой» кейс.
5. **MVP-модель генерации рецептов** — персональный подбор рецептов: избранное пользователя,
   холодильник, KNN и векторизация текстов. Это рабочая заглушка ML-модуля из `ml_planning/ml_plan`;
   включается флагом и не меняет контракт API.

## Как устроен код (карта для новичка)

### Структура проекта

```
Recepie-book/
├── openapi.yaml                  # контракт API: все 22 адреса, поля и коды ответов
├── backend/
│   ├── main.py                   # точка входа (gunicorn вызывает create_app())
│   ├── worker.py                 # фоновая задача: уведомления о просроченных продуктах
│   ├── tests/                    # автотесты (12 файлов, 75 кейсов) + conftest.py с фикстурами
│   ├── tests/data/               # сэмпл датасета, размеченная выборка аллергенов, корпус метрик
│   ├── migrations/               # версионные SQL-миграции для уже существующих баз
│   ├── requirements-ml.txt       # необязательные зависимости импорта (pyarrow)
│   └── app/
│       ├── __init__.py           # фабрика create_app(): сборка blueprints, обработчики ошибок
│       ├── config.py             # настройки только из переменных окружения
│       ├── db.py                 # пул соединений, транзакции, health-check
│       ├── schema.sql            # структура БД (9 таблиц) + триггеры
│       ├── migrate.py            # применение schema.sql и миграций (журнал schema_migrations)
│       ├── errors.py             # доменные исключения → HTTP-коды
│       ├── validation.py         # проверка входных данных (лимиты = размеры колонок)
│       ├── serializers.py        # имена колонок БД → имена полей API
│       ├── security.py           # JWT, декоратор @token_required, ограничение частоты запросов
│       ├── embeddings.py         # эмбеддинги SBERT (ленивая загрузка, EMBEDDINGS_ENABLED)
│       ├── ml/                   # MVP рекомендательного модуля: предобработка, TF-IDF модель v1,
│       │                         # KNN, словарь аллергенов и скрипты метрик
│       ├── importer/             # импорт датасета povarenok: чтение, нормализация, CLI, скачивание
│       ├── api/                  # HTTP-слой: по файлу на область (auth, recipes, fridge, …)
│       ├── services/             # бизнес-логика: правила и порядок действий
│       └── models/               # SQL-слой: по модулю на таблицу, только параметризованные SQL
```

### Поток одного запроса (на примере `POST /recipes`)

1. **Flask** находит маршрут в `app/api/recipes.py` (`@bp.post("/recipes")`).
2. **Валидация тела**: `validation.json_object_body()` — тело должно быть JSON-объектом,
   иначе сразу 400 через `errors.BadRequest`.
3. **Бизнес-логика**: `services/recipe_service.create_recipe(db, payload)` — проверяет поля
   (`require_string`, лимиты из `validation.py` совпадают с размерами колонок).
4. **SQL**: `models/recipes.insert_recipe(...)` — запрос с параметрами (`%s`), значение никогда
   не «вклеивается» в текст запроса (защита от SQL-инъекций).
5. **Транзакция** в `db.py`: `with db.cursor()` — либо всё выполнилось, либо полный откат.
6. **Ответ**: `jsonify({...}), 201`; ошибки централизованно превращаются в
   `{"error": "<текст>"}` с кодом 400/401/404/405/503 в `app/__init__.py`.

Такое разделение (api → services → models → db) означает, что новичку достаточно понимать
один слой за раз: HTTP-детали не смешаны с SQL, а правила — с запросами.

### Правила, которые соблюдает код

- Настройки и секреты — **только** из переменных окружения (`app/config.py`), в коде их нет.
- Все SQL-запросы — параметризованные, собираются в одном месте (`app/models/`).
- Любое значение из запроса проходит проверку до обращения к БД (400 вместо ошибки базы).
- Ошибки одного формата: `{"error": "..."}`.
- Проверка токена — один декоратор `@token_required`, а не копипаста в каждом адресе.

## Как добавить новый адрес (пошаговый рецепт для новичка)

Порядок важен: сначала контракт, потом код, потом тест. Так поведение сервиса и документация
не разъезжаются.

1. **Контракт** — добавить путь в `openapi.yaml` (метод, тело запроса, коды ответов).
2. **HTTP-слой** — функция во `app/api/<область>.py`:
   `payload = json_object_body()` (валидация тела) → `return jsonify(<service>(get_db(), payload)), 201`.
   Если адрес личный — добавить декоратор `@token_required`, а пользователя брать
   через `current_user_id()`, **никогда** из тела запроса.
3. **Правила полей** — добавить проверки в `app/validation.py`, если нужен новый тип поля.
   Лимиты длины брать из схемы БД (например, `recipes.recipe_name` → `varchar(200)`).
4. **Бизнес-логика** — функция в `app/services/<область>_service.py`: проверки, порядок
   действий, тексты сообщений.
5. **SQL** — функция в `app/models/<таблица>.py`; только параметризованные запросы.
6. **Формат ответа** — при переименовании колонок добавить преобразование в `app/serializers.py`
   (например, `recipe_name` → `name`).
7. **Тест** — 1 успешный кейс + 1 кейс на отказ в `backend/tests/test_<область>.py`
   (за образец можно взять `tests/test_recipes.py`), затем строка в `TEST-CHECKLIST.md`.
8. **Прогон** — `python -m pytest`, `ruff check .`, `black --check .` (это же делает CI).
9. **Необязательная функциональность** — если новая часть нужна не всем, она закрывается флагом:
   переменная в `config.py` + ветка в сервисе, как `SMART_RECOMMENDATIONS_ENABLED` (задача 5).
   Контракт при этом не меняется, поведение по умолчанию остаётся прежним, а тест прогоняет
   оба режима на одних данных.

## Как читать тесты

- **Файл = область API**, а не «свалка»: `test_auth.py`, `test_recipes.py`, `test_fridge.py`,
  `test_user_preferences.py`, `test_notifications_recommendations.py`, `test_system.py`
  (служебные адреса), `test_database.py` (сама схема БД, триггеры, таблицы без адресов),
  `test_ml_engine.py` (компоненты ML-модуля, без базы) и `test_smart_recommendations.py`
  (`/recommend_recipes` с флагом и без него).
- **Один адрес = 1–3 кейса**: успешный сценарий и отказ. Несколько однотипных проверок
  собраны в один кейс обычным циклом `for`, а не десятком параметризованных тестов —
  так набор читается как список сценариев, а не как таблица вариантов. В сообщении `assert`
  передаётся сам «плохой» объект, поэтому при падении сразу видно, на чём упало:
  `assert response.status_code == 400, payload`.
- **Фикстуры** (`tests/conftest.py`) — как в учебнике: `client` — приложение без базы,
  `db_client`/`db` — приложение с базой и фасад для SQL-проверок, `register_user` и
  `add_fridge_items` — подготовка данных через настоящие HTTP-запросы, `db_app_factory` —
  то же приложение, но с другим набором переменных окружения (так проверяется флаг
  `SMART_RECOMMENDATIONS_ENABLED` на одной и той же базе).
  Перед каждым кейсом все восемь таблиц очищаются (`TRUNCATE ... RESTART IDENTITY CASCADE`),
  поэтому тесты не зависят друг от друга и от порядка запуска.
- **Два режима прогона**:

```bash
cd backend
python -m pytest                 # без БД: 28 passed, 47 skipped
TEST_DATABASE_URL=postgresql://postgres:changeme@localhost:5432/mydatabase python -m pytest
                                 # с БД: 75 passed
```

  Кейсы, которым нужна база, помечаются `skipped`, а не «зелёными»: в CI отдельный шаг
  проверяет доступность базы, чтобы набор не мог пройти на одних пропусках.

## Задача 1. Подключить базу данных

**Что было нужно.** Данные не должны жить «в памяти» приложения: при перезапуске сервиса
рецепты, пользователи и продукты обязаны сохраняться. При сбое посередине операции не должно
оставаться «полузаписанных» данных.

**Что сделано.**

- Сервис подключается к **PostgreSQL** через пул соединений (`app/db.py`): соединения
  переиспользуются, а не открываются на каждый запрос; соединение всегда возвращается в пул,
  даже если внутри произошла ошибка.
- Каждая операция — **транзакция**: либо целиком применяется, либо полностью откатывается.
  При обрыве связи сервис не падает, а отвечает 503 «база недоступна».
- **Структура описана в одном файле** `app/schema.sql` и применяется при старте сервиса
  (`AUTO_INIT_SCHEMA=true`). Файл безопасно запускать повторно: используются
  `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`
  и `DROP TRIGGER IF EXISTS` — повторный запуск ничего не ломает и не дублирует.
- Созданы **девять таблиц**: восемь из согласованной схемы `docs/db_scheme.png`
  (`users`, `recipes`, `fridge_items`, `favorite_recipes`, `generated_recipes`,
  `user_allergy_preferences`, `fridge_item_versions`, `fridge_item_audit`) и
  `recipe_ingredients` — расширение под импорт датасета (см. ниже).
- **Целостность задана в самой базе**: внешние ключи (`ON DELETE CASCADE` для дочерних таблиц,
  `SET NULL` для истории версий), уникальность `username` и `email` без учёта регистра,
  `CHECK (quantity > 0)`, `NOT NULL` там, где значение обязательно.
- **Историю ведёт база, а не код**: триггеры `fridge_items_version_trigger` и
  `fridge_items_audit_trigger` (функции `fridge_items_log_version`, `fridge_items_log_audit`)
  пишут новую версию продукта и запись аудита со «снимками» `old_values`/`new_value` (`jsonb`).
  Поэтому история верна, даже если данные правят SQL-ом мимо API.
- Добавлены **индексы** под частые выборки (имя рецепта, срок годности, пользователь и время
  действия в аудите, `lower(email)`).
- Изменения структуры оформляются **миграциями**: `migrations/0001_db_scheme_rework.sql`
  и `app/migrate.py` (запуск `python -m app.migrate`) с журналом применённых миграций
  в таблице `schema_migrations`; повторный запуск ничего не применяет второй раз.

**Осознанные отличия `schema.sql` от `docs/db_scheme.png`** (все они описаны в `README.md` и
проверяются тестами):

| Место | В схеме `docs/db_scheme.png` | В реализации | Почему так |
|---|---|---|---|
| `users.password` | `varchar(120)` | `varchar(200)` | scrypt-хэш werkzeug занимает 162 символа и не влезал |
| `fridge_items.quantity` | `integer default 1` | `NOT NULL DEFAULT 1 CHECK (quantity > 0)` | количество не может быть нулевым или отрицательным (в API — `minimum: 1`) |
| `users.email` | `varchar(120) unique not null` | плюс уникальный индекс `users_email_lower_key` по `lower(email)` | контракт считает email регистронезависимым |
| `fridge_item_versions.fridge_items_id` | правило `ON DELETE` не указано | `ON DELETE SET NULL` | иначе падал бы `DELETE /delete_expired_products`, а история продукта терялась |
| метки времени и `version` | только `default current_timestamp` | плюс `NOT NULL` | база сама всегда заполняет `last_added`, `updated_at`, `action_time`, `generated_on`, `version` |
| `recipes.instruction` | `varchar(100)` без `NOT NULL` | `text`, допускает `NULL` | инструкция не помещается в 100 символов, у импортированных рецептов её нет; API пока требует поле |
| триггер `fridge_items_log_audit` | не описан (поведение — вопрос реализации) | при невозможности записать запись аудита (удаляется пользователь) — `RAISE WARNING` и продолжение | иначе каскадное удаление пользователя падало на внешнем ключе |
| `recipes.ingredients` | `ingredients` | `ingredients` | в текстовом описании `docs/db_plan` опечатка «igredients», берём написание диаграммы |

**Что это даёт продукту.** Данные переживают перезапуск и обновление, при сбоях не появляется
мусорных «полузаписей», а поддержка одним запросом к `/ready` понимает, «виноват» сервис или база.

**Как проверить без программирования.**

1. `docker compose up --build` в корне проекта — поднимутся база, бэкенд, фронтенд, Swagger.
2. `http://localhost:8000/ready` → `{"status":"ready","database":"ok"}`.
3. Остановить контейнер с базой и обновить страницу → `{"status":"not_ready","database":"unavailable"}`,
   при этом `http://localhost:8000/health` продолжает отвечать `{"status":"ok"}`.
4. Перезапустить сервис — данные на месте (том `pgdata`).

**Для разработчиков.** `app/db.py` — пул (`DB_POOL_MIN/MAX`), контекст `cursor()` с
`commit`/`rollback`, `health_check()`; `app/schema.sql` — таблицы, индексы, триггеры;
`app/models/*` — по модулю на таблицу, только параметризованные запросы;
`app/migrate.py` + `migrations/` — версионные изменения; `app/api/system.py` — `/health`, `/ready`.
Проверяется файлом `tests/test_database.py` (11 кейсов: состав и типы колонок, ключи, индексы,
ограничения, работа триггеров, ингредиенты рецепта, `source_url`, метки времени,
таблицы без адресов).

## Задача 3. Авторизация

**Что было нужно.** Дать пользователю возможность зарегистрироваться и войти, не хранить пароли
в открытом виде и закрыть от посторонних личные экраны (уведомления, удаление просроченного,
рекомендации).

**Что сделано.**

- **Регистрация**: логин, email, пароль; пароль сохраняется только как необратимый хэш (scrypt) —
  восстановить исходный пароль из базы невозможно. Длины полей совпадают с колонками
  (`users.username varchar(80)`, `users.email varchar(120)`), email приводится к нижнему регистру.
- Аллергии и предпочтения хранятся в двух согласованных видах: строкой в карточке пользователя
  (`users.allergies`/`preferences`) и отдельными строками в `user_allergy_preferences`. Оба вида
  пишутся в одной транзакции; повторный вызов `/user_preferences` заменяет значения (без дублей),
  пустой список очищает всё.
- **Вход** выдаёт **JWT** со сроком жизни 12 часов (значение из контракта, настраивается
  переменной окружения): `jwt.encode(payload, JWT_SECRET, HS256)`, в токене `sub` = id пользователя,
  а также `iat` и `exp`.
- Токен передаётся стандартным заголовком `Authorization: Bearer <токен>`.
- **Защищены 5 адресов**: `GET /protected`, `GET /notify_expired`, `DELETE /delete_expired`,
  `GET /suggest_recipes`, `GET /recommend_recipes` — без действительного токена они отвечают 401.
- Проверка токена — **один декоратор** `@token_required` (`app/security.py`): проверяет заголовок,
  подпись, срок и наличие `sub`, кладёт id пользователя в `g.user_id`. Защита нового маршрута —
  одна строка кода.
- Пользователь работает **только со своими данными**: id берётся из токена (`current_user_id()`),
  а не из тела запроса. Кейс `test_delete_expired_touches_only_the_user_from_the_token` это
  доказывает: продукты второго пользователя остаются нетронутыми.
- **Секрет подписи** — только из окружения (`JWT_SECRET` или `FLASK_SECRET_KEY`). Если он не задан,
  сервис не выдаёт токены и падает с понятной ошибкой при старте — «тихой дыры» не бывает.
- **Защита от подбора пароля**: ограничение частоты запросов к `/login` и `/register`
  (`RATE_LIMIT_ENABLED`, по умолчанию выключено — см. «Ограничения»).
- Ответ при входе **не подсказывает**, что именно неверно (email или пароль), а повторная
  регистрация занятого email/username даёт понятный 400.

**Что это даёт продукту.** Личные данные закрыты, пароли не утекают даже при утечке базы,
а токен одинаково удобен для веб- и мобильного клиента.

**Как проверить без программирования** (Swagger):

1. `POST /register` → 201.
2. `POST /login` тем же email и паролем → в ответе `token`.
3. Кнопка **Authorize**, вставить токен, затем `GET /protected` → 200 с id пользователя.
4. Убрать токен и снова `GET /protected` → 401.
5. `POST /register` тем же email → 400 «пользователь уже существует».

**Для разработчиков.** `app/security.py` (`create_access_token`, `decode_access_token`,
`@token_required`, `InMemoryRateLimiter`), `app/services/auth_service.py` (регистрация и вход),
`app/api/auth.py` (адреса), `app/models/users.py` (таблица `users`).
Правила — CONTRIBUTION.md §3, §9. Проверяется файлом `tests/test_auth.py` (6 кейсов) и кейсом
`test_all_four_routes_require_a_token`.

**Статус.** ✅ Готово. Всё перечисленное закреплено тестами, включая 6 вариантов «плохого» токена.

## Задача 5. MVP-модель генерации рецептов

**Что было нужно.** Сделать рекомендации персональными: сервис должен предлагать блюда «под
пользователя», а не только «что есть в холодильнике». Основой стало проектирование в
`ml_planning/ml_plan` и диаграмма активностей `ml_planning/image.png`: рекомендательный модуль на
методах NLP, обучающая выборка из избранного пользователя, метод k ближайших соседей (KNN),
исключение аллергенов и учёт содержимого холодильника. Полное обучение модели (SBERT на истории
пользователей, `pymorphy2`) — тема следующего шага, поэтому нужен **MVP**, который проходит весь
путь от данных в базе до ответа API и его можно включать флагом.

**Что сделано.** В `backend/app/ml/` реализована минимальная рабочая версия модуля — шаг в шаг по
диаграмме (соответствие «компонент → файл → отличие от целевого решения» есть в `README.md`):

| Компонент (`ml_plan`) | Что реализовано | Файл |
|---|---|---|
| предобработка данных | нормализация (регистр, «ё» → «е», пунктуация), удаление стоп-слов, лемматизация по таблице окончаний, поиск аллергенов по леммам | `app/ml/preprocessing.py` |
| векторизация | SBERT, если он включён и доступен (`EMBEDDINGS_ENABLED=true`); иначе разреженный «bag-of-lemmas», чтобы сервис и тесты работали без `torch` | `app/ml/vectorizer.py` |
| обучающая выборка | тексты ингредиентов избранных рецептов (`favorite_recipes`); профиль пользователя — центроид этих векторов | `app/ml/engine.py` |
| алгоритм рекомендаций | KNN по косинусной близости на чистом Python; сортировка устойчивая, поэтому на одних и тех же данных ответ всегда один и тот же | `app/ml/knn.py` |
| фильтрация | рецепты с аллергенами пользователя отбрасываются до ранжирования, число отброшенных попадает в ответ и в лог | `app/ml/engine.py` |
| контекстная адаптация | к близости добавляется бонус за продукты из холодильника (`FRIDGE_BONUS = 0.2` × доля совпавших продуктов) | `app/ml/engine.py` |

  холодильник и аллергии пользователя, запускает конвейер и записывает предложенные рецепты в
  `generated_recipes` — как это делала прежняя логика, поэтому история не теряется.
- **Контракт API не менялся**: те же 19 адресов и та же форма ответа `{"message", "recipes"}` с
  полями `id`, `name`, `ingredients`, `instructions`, `difficulty_level`. Меняется только текст
  сообщения: теперь он объясняет результат («рекомендовано N рецептов по избранному и холодильнику,
  M отброшено из-за аллергий») и причину пустого списка.
- **Флаг включения** — `SMART_RECOMMENDATIONS_ENABLED` (по умолчанию `false`: без него сервис

  старт; `tests/test_smart_recommendations.py` (3 кейса с базой) — сам адрес: ответ с флагом, ответ
  без флага на тех же данных, пустой профиль и удалённый пользователь. Набор вырос до 44 кейсов.

## Спринт 2, задача 3. Просроченные продукты: одно правило

Ветка `fix/expired-products`. Задача из [`docs/sprint-2-plan.md`](docs/sprint-2-plan.md): два

или при разных `TZ` у контейнеров отчёт мог показывать продукт, который удаление не трогало,

**Что сделано.**

- в `app/models/fridge.py` появилось одно определение
  `EXPIRED_CONDITION = "expiration_date < CURRENT_DATE"`; его используют все запросы о
  просроченном (`list_expired_items`, `delete_expired_items`, `list_user_ids_with_expired_items`),

- у `list_expired_items` удалён параметр `today` — он и был вторым источником даты;
- `openapi.yaml`: у `/notify_expired`, `/delete_expired` и `/delete_expired_products` описано одно

  остаются, повторный `DELETE` удаляет 0; `test_notify_expired_and_delete_expired_products_use_one_rule`
  — сколько продуктов показал отчёт, столько удаление и удалило, после удаления отчёт пуст;
- новая фикстура `add_relative_fridge_items` создаёт продукты по часам базы, поэтому тест не

## Спринт 2, задача 4. API избранного

Таблица `favorite_recipes` была в схеме с самого начала, но адресов у неё не было: рекомендации
считали профиль по избранному, а добавить рецепт в избранное можно было только через SQL. Ветка
`feat/favorites-api` закрывает этот разрыв.

**Что появилось.**

| Адрес | Что делает | Коды |
|---|---|---|
| `GET /favorite_recipes` | страница избранных рецептов владельца токена, от новых к старым | 200, 400 (`limit`/`offset`), 401 |
| `POST /favorite_recipes` | добавляет рецепт в избранное, повтор идемпотентен | 201, 400, 401, 404 |
| `DELETE /favorite_recipes/{id}` | убирает рецепт из избранного владельца токена | 200, 401, 404 |

**Решения.**

- **`user_id` только из токена.** Ни тело `POST`, ни URL не выбирают владельца: поле `user_id`
  в теле игнорируется (это проверяет тест), поэтому один пользователь не может писать в чужое
  избранное (CONTRIBUTION.md §3). Чтение и удаление тоже идут с `WHERE user_id = <из токена>`.
- **Порядок «новые сверху»** — по `favorite_recipes.created_at` (колонка из задачи 1 спринта 2);
  при совпадении метки порядок добивается `favorite_recipes.id DESC`, потому что `created_at` —
  это время начала транзакции и два быстрых запроса могут получить одинаковое значение.
- **Идемпотентность** — пара `(user_id, recipe_id)` уже уникальна
  (`favorite_recipes_user_recipe_key`), поэтому вставка идёт с `ON CONFLICT DO NOTHING`, а
  повторный вызов отвечает 201 с сообщением «уже в избранном»; дублей в таблице не появляется.
- **Чужая запись — 404, а не 403.** Для второго пользователя строки не существует, и ответ не
  раскрывает, что рецепт лежит в чьём-то избранном.
- **Несуществующий рецепт — 404, а не 500.** Внешний ключ на `recipes.id` проверяется до вставки.
- **Пагинация** — те же `limit`/`offset` (по умолчанию 50, максимум 200), что у остальных списков
  (CONTRIBUTION.md §4); модуль рекомендаций по-прежнему берёт избранное целиком через
  `list_favorites`, страница нужна только API.

**Готово, если:** авторизация и доступ к чужим данным проверены тестами — 4 кейса в
`tests/test_favorites.py` (успех, 401 без токена, чужие записи, валидация).

**Как проверить.** Swagger (`http://localhost:8080/`): `POST /register`, `POST /login`,

HitRate@5, MRR) и сравнить с прежней заглушкой как baseline. Критерий приёмки: v1 выше baseline
по Precision@5 и MRR.

**Что сделано.**

- `backend/app/ml/model.py` — сама модель: IDF по формуле `ln((1+N)/(1+df)) + 1`, незнакомое
  слово получает наибольший вес, артефакт — один JSON-файл (`version`, `trained_at`, `documents`,
  `source`, `default_idf`, `idf{лемма: вес}`), атомарная запись, стат-кэш (переобучение
  подхватывается без рестарта). CLI: `python -m app.ml.model [--from-db --limit N] [--out PATH]`.
- `backend/app/ml/corpus.py` — корпус для обучения и оценки: файл датасета (через импортёр) или
  `recipes` + `recipe_ingredients`; рецепты-заглушки без ингредиентов отбрасываются.
- `backend/app/ml/evaluate.py` — протокол leave-one-ingredient-out, пять метрик, разбивка по
  частоте продукта в корпусе, JSON-вывод; код возврата 1, если v1 не лучше baseline.
- `backend/app/ml/vectorizer.py` — третий бэкенд `tf-idf-v1` (порядок: SBERT → модель v1 →
  bag-of-lemmas); `backend/app/ml/engine.py` — параметр `model` и `artifact_for_settings()`;
  `backend/app/services/smart_recommendation_service.py` — загрузка артефакта на запрос;
  `backend/app/models/recipes.py::list_recipes_for_model` — выборка `id/name/ingredients`.
- Настройка `SMART_RECOMMENDATIONS_ARTIFACT` в `app/config.py`; каталог артефактов остаётся в
  `.gitignore` (данные и модели не коммитятся, см. план спринта).
- Корпус метрик `backend/tests/data/recommendation_sample.json` (120 рецептов, 855 ингредиентов),
  новый файл тестов и документ `docs/recommendation-model.md`.

**Числа (прогон 29.10.2026, корпус 120 рецептов, 813 запросов, k = 5).**

| Стратегия | P@1 | P@5 | R@5 | Hit@5 | MRR@5 |
|---|---|---|---|---|---|
| baseline (bag-of-lemmas) | 0.385 | 0.326 | 0.344 | 0.672 | 0.493 |
| **v1 (TF-IDF)** | **0.395** | **0.360** | **0.380** | **0.711** | **0.513** |

`P@5` +3,3 п.п. (+10 % относительно), `MRR` +0.020, `Hit@5` +3,9 п.п. — критерий задачи выполнен.

```bash
cd backend
python -m app.ml.model        # обучить модель (или --from-db — на импортированном каталоге)
python -m app.ml.evaluate     # таблица метрик + вердикт; код возврата 1 при регрессе
```

**Как это проверено тестами.** `backend/tests/test_recommendation_model.py` — 9 кейсов (8 без БД):
веса IDF и `default_idf`; round-trip артефакта и стат-кэш; отсутствующий/битый файл, чужая
версия и пустой словарь → откат на bag-of-lemmas (критерий задачи); переключение движка на модель
(`vectorizer=tf-idf-v1`, `model_documents=N`) и изменение порядка выдачи; арифметика метрик на

чтение корпуса из БД (`recipe_ingredients` приоритетнее текста).

**Ограничения.** Корпус метрик написан для проверки (120 рецептов), а не взят из датасета, поэтому
числа in-sample относительно корпуса обучения IDF; на реальном каталоге нужно прогнать

## Спринт 2, задача 5. Синхронизация контракта `openapi.yaml`

**Что требовалось.** Привести контракт и реализацию к одному виду после импорта датасета:
`instruction`/`difficulty_level` — nullable (у импортированных рецептов их нет), `source_url` и
список ингредиентов в схеме рецепта (с решением по объёму ответа), `limit`/`offset` у
`GET /recipes` и адресов избранного, лимит длины инструкции — как у колонки `text`.

**Что уже было сделано раньше:** пагинация `GET /recipes`, `GET /favorite_recipes` и
`GET /fridge_items` описана в контракте и совпадает с кодом (`1..200`, по умолчанию 50,
`offset ≤ 1 000 000`); лимит инструкции — 10 000 символов, как `recipes.instruction` (техдолг).

**Что исправлено сейчас.**

- `openapi.yaml`: у `Recipe` появился `required` (все семь полей присутствуют всегда),
  `instructions`, `difficulty_level` и новый `source_url` помечены `nullable: true` с пояснением
  «null у импортированных рецептов»; добавлена схема `Ingredient` (`name`, `quantity`) и массив
  `ingredient_list` с описанием, что он заполняется импортёром.
- `backend/app/models/recipes.py`: `RECIPE_COLUMNS` включает `source_url` (сразу во всех адресах,
  которые отдают рецепт); новая `list_ingredient_details` отдаёт строки `recipe_ingredients`
  вместе с количеством, `list_ingredient_names` теперь строится поверх неё.
- `backend/app/serializers.py`: `serialize_recipe` принимает `ingredient_list` и возвращает новый
  объект `Recipe`.
- Новый `backend/app/services/recipe_presenter.py`: одна точка, где страница/ответ получает
  ингредиенты **одним** запросом на страницу (`present_recipes`), а не запросом на рецепт. Через
  него теперь отвечают `GET /recipes`, `GET /recipes/{id}`, `GET /favorite_recipes`,
  `GET /suggest_recipes` и оба режима `GET /recommend_recipes`.
- Решение по объёму ответа: `ingredient_list` отдаётся **всегда** вместе с текстом `ingredients`
  (замер: 8 ингредиентов ≈ 0,4 КБ на рецепт, страница из 50 ≈ +21 КБ) — клиент видит ровно те
  строки, по которым работает фильтр аллергенов, и ему не нужен второй запрос на рецепт. У рецептов,
  созданных через `POST /recipes`, массив пуст: структурные строки пишет только импортёр.

**Как проверено.** Новый кейс `test_imported_recipe_exposes_the_source_and_the_ingredient_list`
(импортированный рецепт: `null` в трёх полях, `source_url`, порядок по `sort_order`,
`quantity = null` у продукта без количества, те же поля в странице) и уточнённые проверки набора
полей в `test_get_recipe_by_id`, `test_add_list_and_remove_favourites`,
`test_suggest_recipes_uses_the_expired_products`, `test_smart_recommendations_*`. Прогон: 85 из 85.

**Ограничения.** `POST /recipes` по-прежнему не пишет `recipe_ingredients` — структуру ручного
рецепта клиент получает пустой (текст `ingredients` остаётся). Научить создание писать строки —
отдельная небольшая задача: это изменение поведения, а не контракта.

**Для разработчиков.** `openapi.yaml` (схемы `Recipe`/`Ingredient`),
`backend/app/services/recipe_presenter.py`, `backend/app/serializers.py`,
`backend/app/models/recipes.py`, `backend/tests/test_recipes.py`.

**Статус.** ✅ Готово: контракт и реализация совпадают, обратная совместимость сохранена (только
новые поля и `nullable`), 85 из 85, `ruff`/`black` чистые.

## Что сделано сверх этих пяти задач

Это «инфраструктура» вокруг продукта: без неё сервис работал бы только на машине разработчика.

- **Запуск в один шаг**: `docker-compose.yml` поднимает четыре контейнера — базу, бэкенд,
  фронтенд и Swagger; настроен порядок запуска (бэкенд ждёт готовности базы).
- **Готовность к продакшену**: gunicorn вместо встроенного сервера Flask, многоступенчатая сборка
  образа, контейнер не работает под суперпользователем, есть liveness/readiness-пробы.
- **CI (GitHub Actions)**: `backend-tests.yml` — тесты, `ruff`, `black` и контроль доступности
  базы на каждый push/PR; `docker-image.yml` — сборка образов и smoke-проверка `/ready`, `/health`;
  `backend-smart-recommendations-ci.yml` — тот же набор плюс прогон кейсов ML-модуля и проверка
  чтения флага из окружения для ветки `feat/smart-recommendations`.
- **Живая документация**: Swagger показывает все 22 адреса из `openapi.yaml` — можно нажимать
  кнопки и проверять поведение без Postman.
- **Документация проекта**: `README.md` (запуск, структура и раздел «Модуль рекомендаций
  (заглушка ML)»), `CONTRIBUTION.md` (правила команды), `TEST-CHECKLIST.md` (что проверяют тесты),
  `ml_planning/ml_plan` (проектирование рекомендательного модуля), `TASKS-REPORT.md` (этот отчёт).
- **Воркер уведомлений** о просроченных продуктах работает отдельным процессом `worker.py`,
  поэтому регулярная работа не увеличивает время ответа пользовательских запросов.

## Ограничения и открытые вопросы

Честный список того, что стоит знать перед приёмкой (ничего из этого не блокирует работу сервиса,
но требует решения продукт-овнера).

| Ограничение | Простыми словами | Технически | Что предлагается |
|---|---|---|---|
| Частота входов не ограничена по умолчанию | Защита от подбора пароля написана, но не включена | `RATE_LIMIT_ENABLED=false`; лимитер `InMemoryRateLimiter` живёт в процессе, автотеста нет | Включить в проде и добавить кейс |
| Часть адресов открыта по контракту | `POST /user_preferences`, `POST /recipes`, `GET /fridge_items`, `DELETE /delete_expired_products` не требуют входа и видят данные всех пользователей | поведение задано `openapi.yaml`, а не кодом | Обсудить и поменять контракт вместе с тестами |
| Токен живёт 12 часов | Значение взято из контракта; для прода обычно короче | `JWT_TTL_HOURS`, по умолчанию 12 | Согласовать срок или добавить «продление входа» |
| Нет статической проверки типов в CI | Проверяется стиль (`ruff`, `black`), но не типы | в CI нет `mypy` | Добавить отдельным шагом |
| Тяжёлая ML-библиотека в зависимостях | Замедляет установку и CI, хотя «умный» подбор выключен | `EMBEDDINGS_ENABLED=false`; `sentence-transformers` в `requirements.txt` | Вынести в отдельный набор «по желанию»: MVP рекомендаций (задача 5) работает и без неё |
| Лемматизация упрощена | «Молока» и «молоко» сводятся к одной форме, но на редких словах таблица окончаний может ошибиться | `app/ml/preprocessing.py`: таблица окончаний вместо `pymorphy2` | Подключить `pymorphy2`/`spaCy`, когда зависимость станет допустимой |
| Модель не обучается | Профиль считается «на лету» из избранного, сохранённой модели нет; адаптация «со временем» не реализована | `app/ml/engine.py` — вычисление при каждом запросе, KNN перебирает все рецепты | Офлайн-обучение: эмбеддинги и индекс, хранимая модель |
| Качество рекомендаций не измерено | Неизвестно, насколько точны подборы: цифр пока нет | метрик `precision@k`/`recall@k` и офлайн-набора нет | Собрать офлайн-набор и считать метрики до включения флага в проде |
| SBERT-режим не проверяется в CI | Проверен только запасной векторизатор | в CI `EMBEDDINGS_ENABLED=false`, тесты идут через «bag-of-lemmas» | Отдельный (долгий) джоб с установленным `sentence-transformers` |
| Аллергии ищутся по тексту ингредиентов | Аллерген ловится по вхождению слова в строку `ingredients`, возможны пропуски и ложные срабатывания | нормализованных ингредиентов в схеме нет — сравнение лемм в `app/ml/preprocessing.py` | Хранить ингредиенты отдельными строками и фильтровать по ним |
| Предпочтения не влияют на «умный» режим | `preferences` учитывает только базовая логика, не модуль | `app/ml/engine.py` использует избранное, холодильник и аллергии | Добавить бонус за предпочтения, как в `recommendation_service.py` |
| Флаг по умолчанию выключен | В проде пока работает прежняя логика, эффект виден после включения | `SMART_RECOMMENDATIONS_ENABLED=false` | Включать после проверки метрик качества |
| История и аудит растут постоянно | Каждое изменение продукта добавляет строку в две таблицы, очистки нет | `fridge_item_versions`, `fridge_item_audit` наполняются триггерами | Добавить срок хранения или архивацию |
| Точность проверки схемы | Схема БД «на проживание» проверяется против реальной базы, а без неё эти кейсы пропускаются | `tests/test_database.py` скипается без `TEST_DATABASE_URL` | Локально поднимать БД через `docker compose up -d db` (полный прогон уже подтверждён) |
