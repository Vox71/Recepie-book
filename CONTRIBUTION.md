# Правила разработки проекта

## 1. Общие принципы

- Одна задача — одна ветка — один pull request.
- Не смешивать в одном PR новую фичу, исправление бага и рефакторинг.
- PR не должен быть огромным. Если изменений много — разбить на несколько.
- Перед merge нужно минимум одно одобрение от другого участника.
- Удалять ненужный код, а не комментировать его.
- Если меняешь API — обнови `openapi.yaml` в том же PR. Контракт проверяется автоматически:
  `backend/tests/test_openapi_contract.py` падает, если файл невалиден, если адрес/метод или лимиты
  расходятся с кодом или если тело ответа не соответствует схеме.

## 2. Структура проекта

- Разделять код по слоям, а не сваливать всё в один файл:
app/
init.py
config.py # настройки
db.py # работа с базой
models/ # модели данных
services/ # бизнес-логика
api/ # роуты
tests/ # тесты

- Фронтенд (`frontend/`, React + TypeScript, спринт 3, задача 3) делится так же:
  `src/pages/` — экраны, `src/components/` — переиспользуемые части, `src/app/` — маршруты и
  общие настройки, `src/api/` — вызовы API (появится в спринте 4), `src/__tests__/` — тесты.
  Адреса страниц живут только в `src/app/routes.ts`, а не строками по компонентам.

- Настройки читать только из переменных окружения.
- Не создавать глобальные объекты на уровне модуля.

## 3. Безопасность

- Пароли, ключи и токены не хранить в коде. Только в `.env`.
- `.env` не коммитить. В репозитории держать `.env.example`.
- Пароли хранить только в виде хэша.
- JWT-секрет — длинный и случайный.
- Все эндпоинты, которые меняют данные, защищать авторизацией.
- `user_id` брать из токена, а не из тела запроса.
- SQL-запросы — только с параметрами `%s`. Не склеивать строки вручную.
- Не логировать пароли, токены и личные данные.
- `debug=True` — только локально, не в проде.
- Ограничить частоту запросов к `/login` и `/register`.

## 4. API

- Единый формат ошибки:
```json
{ "error": { "code": "NOT_FOUND", "message": "Recipe 42 not found" } }
```


- Правильные HTTP-коды:


  -  201 — создано,
  -  400 — плохой запрос,
  -  401 — не авторизован,
  -  403 — нет прав,
  -  404 — не найдено,
  -  409 — конфликт,
  -  500 — ошибка сервера.

- Названия ресурсов — существительные во множественном числе (/recipes).
- Списки возвращать с пагинацией (?limit=&offset=).
- Даты — в формате ISO 8601.
- Поля JSON — в snake_case.


## 5. Валидация входных данных

- Проверять все данные, которые приходят от пользователя.
- Обязательные поля проверять явно. Если чего-то нет — вернуть 400.
- Проверять типы: строка, число, список.
- Ограничивать длину строк.
- Email проверять на формат.
- Для значений из фиксированного набора использовать `Enum`.

## 6. Работа с базой данных

- Соединение и курсор всегда закрывать. Лучше через `with` или `try/finally`.
- Использовать транзакции. При ошибке делать `rollback`.
- Не выполнять запросы в цикле, если можно сделать один общий.
- Менять схему БД только через миграции.
- Ограничения (`NOT NULL`, `UNIQUE`, внешние ключи) задавать в самой БД.

## 7. Обработка ошибок

- Клиенту не показывать traceback. Только понятное сообщение.
- Ловить конкретные исключения, а не всё подряд.
- `except: pass` — запрещено.
- Ошибки логировать с контекстом.
- Для внешних вызовов ставить таймаут.

## 8. Логирование

- `print()` в коде запрещён. Использовать `logging`.
- Уровни: `DEBUG` — отладка, `INFO` — важные события, `WARNING` — подозрительное, `ERROR` — ошибки.
- Не писать в логи пароли, токены и личные данные.
- Сделать эндпоинты `/health` и `/ready`.

## 9. Авторизация

- Токен передавать в заголовке `Authorization: Bearer <token>`.
- Время жизни access-токена — не больше часа в проде.
- Проверку прав вынести в отдельный декоратор или middleware.
- Пользователь работает только со своими данными.

## 10. Тестирование

- На каждый новый эндпоинт — минимум один успешный и один неуспешный тест.
- Отдельно тестировать авторизацию и доступ к чужим данным.
- Тесты не должны зависеть от порядка запуска.
- Использовать `pytest`.
- Не merge-ить, если тесты падают.

## 11. Стиль кода

- Форматирование — `black`, длина строки 100.
- Линтер — `ruff`.
- Проверка типов — `mypy` для новых модулей.
- Docstring для публичных функций.
- Имена переменных и функций — на английском, понятные.
- Магические числа и строки выносить в константы.
- Фронтенд: форматирование — `prettier` (ширина 100), линтер — `eslint` (flat config),
  типы — `tsc -b` в строгом режиме; вместо `black`/`ruff`/`mypy` эти три команды и есть проверка
  стиля (`npm run format:check`, `npm run lint`, `npm run typecheck`).

## 12. Фоновые задачи

- Не запускать фоновые задачи внутри веб-процесса.
- Задачи должны быть безопасны при повторном запуске.
- Долгие операции не выполнять прямо в HTTP-запросе.

## 13. Docker

- Образы фиксировать по конкретной версии.
- Multi-stage сборка — в финальном слое только необходимое.
- Контейнер запускать не от root.
- У backend должен быть `HEALTHCHECK`.
- Swagger UI — только для разработки.
- `openapi.yaml` держать в репозитории.

## 14. Git и работа с ветками

- Ветки называть по шаблону: `feat/...`, `fix/...`, `chore/...`, `docs/...`.
- Сообщения коммитов — по Conventional Commits:
  `feat(recipes): add pagination`
- Force-push в `main` запрещён.
- В описании PR указать: что сделано, зачем, как проверить.

## 15. Чек-лист перед PR

- [ ] Одна задача, PR небольшой
- [ ] Нет секретов и паролей в коде
- [ ] Изменяющие эндпоинты защищены
- [ ] `user_id` берётся из токена
- [ ] SQL-запросы параметризованы
- [ ] Есть `rollback` при ошибке
- [ ] Входные данные валидируются
- [ ] Нет мёртвого кода и дублей имён
- [ ] Обновлён `openapi.yaml`, если менялся API (контрактные тесты зелёные)
- [ ] Есть тесты, CI зелёный
- [ ] Логи без паролей и токенов
- [ ] `black`, `ruff`, `mypy` проходят локально
- [ ] Для изменений во фронтенде: `npm run typecheck`, `lint`, `format:check`, `test:run` и
      `build` в `frontend/` проходят локально

## 16. Что нельзя делать ни в каком случае

- Хранить секреты, пароли и токены в коде или логах.
- Склеивать SQL-запросы строками.
- Оставлять изменяющий эндпоинт без авторизации.
- Брать `user_id` из тела запроса.
- Оставлять `debug=True` в проде.
- Писать `except: pass`.
- Дублировать имена функций и роутов.
- Менять API без обновления `openapi.yaml`.
- Merge-ить, когда тесты падают.

## 17. Технический долг

- Заводить issue с меткой `tech-debt` на всё, что не сделали сейчас.
- В PR, где появился долг, ставить ссылку на issue.
- Каждый спринт выделять часть времени на закрытие долгов.
- Долги по безопасности закрывать раньше новых фич.
