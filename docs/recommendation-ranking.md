# Ранжирование рецептов: честный split, BM25, co-occurrence и гибрид

Документ фиксирует эксперимент 27.11.2026 на PostgreSQL 15. Цель — не подобрать
красивое число на обучающем корпусе, а получить воспроизводимую оценку на отложенных
рецептах и проверить, что сочетание лексических и ассоциативных сигналов лучше одного
TF-IDF.

## Протокол

- **Корпус:** 12 000 рецептов из povarenok-датасета, 105 087 строк ингредиентов.
- **Split по рецептам:** 8 398 train, 1 800 validation, 1 800 test; `seed=42`.
- **Запрос:** leave-one-ingredient-out, как в `docs/recommendation-model.md`: один
  ингредиент скрыт, остальные образуют запрос.
- **Релевантные:** рецепты, в которых есть скрытый ингредиент; исходный рецепт исключён.
- **Оценка:** по 1 000 первых запросов validation и test. Модели обучаются только на
  train; validation используется для весов, test — только для финальных чисел.
- **Кандидаты:** рецепты, которые делят с запросом хотя бы один термин.
- **Порог `k`:** 10.

Из запроса и документов удалены продукты из `PANTRY` (соль, вода, масло, сахар, специи
и т. п.): они есть почти везде и не помогают отличить рецепты. Поэтому числа этого
документа не стоит напрямую сравнивать с прежним in-sample-прогоном на 3 000 рецептов.

## Что добавлено

1. **Нормализация продуктов** (`app/ml/normalization.py`):
   - словарь синонимов (`помидоры`/`томаты`, `картошка`/`картофель`,
     `куриное`/`курица` и т. п.);
   - удаление pantry-продуктов;
   - канонические леммы для запроса и документа.
2. **BM25** (`app/ml/bm25.py`): насыщение частоты термина и нормировка по длине
   документа; IDF считается только по train.
3. **Co-occurrence / positive PMI** (`app/ml/cooccurrence.py`): ассоциации
   «продукт ↔ продукт», построенные по train. Скрытый ингредиент отсутствует в запросе,
   поэтому совместная встречаемость — прямой сигнал для его восстановления.
4. **Гибридный score:** нормализованные BM25 + PMI + доля пересечения запроса с
   рецептом; веса подбираются на validation по MRR, затем P@k.
5. **Потоковая оценка:** метрики считаются по одному запросу, без хранения всех
   кандидатов в памяти. Ограничение `--max-queries` задаёт число отложенных запросов,
   а не размер каталога.

## Команда

```bash
cd backend
export DATABASE_URL=postgresql://...
python -m app.ml.experiment --from-db --limit 12000 --k 10 --max-queries 1000 --json
```

## Результаты

Выбранные веса: **BM25 0.50, co-occurrence 0.75, overlap 0.10**.

### Validation, 1 000 запросов

| Стратегия | P@1 | P@10 | R@10 | Hit@10 | MRR@10 |
|---|---:|---:|---:|---:|---:|
| BM25 | 0.311 | 0.295 | 0.296 | 0.748 | 0.442 |
| co-occurrence | 0.478 | 0.423 | 0.423 | 0.819 | 0.580 |
| **hybrid** | **0.481** | **0.438** | **0.438** | **0.852** | **0.600** |

### Test, 1 000 запросов

| Стратегия | P@1 | P@10 | R@10 | Hit@10 | MRR@10 |
|---|---:|---:|---:|---:|---:|
| BM25 | 0.287 | 0.291 | 0.292 | 0.739 | 0.427 |
| co-occurrence | 0.420 | 0.405 | 0.405 | 0.818 | 0.552 |
| **hybrid** | **0.445** | **0.430** | **0.430** | **0.822** | **0.565** |

## Как читать

- Co-occurrence оказался сильнее BM25: скрытый продукт лучше предсказывается по
  продуктам, которые часто встречаются вместе с ним, а не по лексическому совпадению.
- Гибрид даёт лучший P@1 и MRR на validation и лучший P@1/P@10/MRR на test.
- Разрыв validation → test небольшой (P@10 0.438 → 0.430, MRR 0.600 → 0.565), то есть
  веса не переобучены на validation.
- Hit@10 = 0.822 на test означает: хотя бы один рецепт с нужным продуктом попал в
  топ-10 в 82 % запросов.

## Ограничения

- 12 000 рецептов — это первые строки датасета, а не случайная выборка. На большем и
  более разнообразном каталоге числа изменятся.
- Оценка идёт по 1 000 отложенных запросов, а не по всем 14 тысячам: это ограничение
  времени и памяти, не качества модели.
- Используются только названия ингредиентов; шаги, КБЖУ, популярность и пользовательские
  профили не участвуют.
- SBERT и user-level оценка по холодильнику в этот прогон не входят.
- Leave-one-ingredient-out — диагностический протокол, а не гарантия того же качества
  в реальном сценарии «что приготовить из холодильника».

## Следующие шаги

1. Прогнать тот же эксперимент на 20–50 тысячах рецептов.
2. Добавить SBERT как отдельный компонент и сравнить на том же test.
3. Собрать 100–300 профилей холодильника и оценить Hit@10/MRR на реальных запросах.
4. После этого решать, какой гибрид включать в `GET /recommend_recipes`.
