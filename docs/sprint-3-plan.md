# План спринта 3: таймеры и удобство приготовления

Документ продолжает [`docs/sprint-2-plan.md`](sprint-2-plan.md): спринт 2 научил сервис работать
на реальных данных (импорт, аллергены, модель рекомендаций), спринт 3 — про то, что происходит
**во время** готовки. Дополняет [`docs/timer.md`](timer.md) (алгоритм и точность) и
[`docs/user_story.md`](user_story.md) (постановка от пользователя).

## Цель спринта

Дать пользователю таймер прямо в рецепте: время берётся из рецепта, отсчёт не сбивается
перезагрузкой и не зависит от часов телефона, а звонок срабатывает вовремя. Контракт API
меняется только там, где это нужно для таймера, и каждое изменение сопровождается обновлением
`openapi.yaml` и контрактными тестами (CONTRIBUTION.md §1).

## Задача 1. Таймеры в рецепте — `feat/recipe-timers`

**User story.** Как пользователь, я хочу видеть таймеры в рецепте, чтобы было удобнее засекать
время.

**Критерии приёмки** (полностью — в [`docs/user_story.md`](user_story.md), п. 7):

1. У рецепта можно указать время приготовления в минутах (`cooking_time_minutes`), оно
   возвращается в карточке рецепта; у импортированных рецептов времени нет (`null`).
2. Пользователь может запустить таймер рецепта: без явной длительности сервер берёт время
   рецепта; для рецепта без времени требуется `duration_seconds`, иначе понятная ошибка 400.
3. Запущенный таймер виден в списке активных до конца отсчёта; после перезагрузки страницы
   список приходит с сервера вместе с его текущим временем.
4. Таймер можно отменить; отменённый и истёкший таймеры исчезают из активных, в базе остаются
   со статусом `cancelled`/`finished`.
5. Таймеры одного пользователя не видны другому: владелец берётся из токена, чужой таймер — 404.
6. Отсчёт не сбивается: момент окончания хранится в базе, а клиент считает остаток от пары
   «`ends_at` − `server_time`» по монотонным часам (алгоритм — `docs/timer.md` §5).

**Что сделано.**

- схема: `recipes.cooking_time_minutes` (1..1440, nullable) и таблица `timers`
  (`timestamptz`-дедлайн, ограничения `duration_seconds`/`status`, индекс
  `timers_user_status_idx`), миграции `0003_recipe_cooking_time.sql`, `0004_timers.sql`;
- API: `POST /timers`, `GET /timers/active`, `DELETE /timers/{id}` под `@token_required`;
  валидация (`duration_seconds` 1..86400, `label` ≤ 100, максимум 20 активных таймеров);
- сервис: дедлайн вычисляет база (`now() + make_interval`), истёкшие таймеры закрываются чтением
  списка, поэтому отдельный воркер не нужен;
- контракт: 3 адреса, схемы `Timer`, `TimerInput`, `TimerCreatedResponse`,
  `ActiveTimersResponse`, поле `cooking_time_minutes` в `Recipe`/`RecipeInput`;
- тесты: `tests/test_timers.py` (11 кейсов), новый кейс в `tests/test_recipes.py`, 4 кейса в
  контрактных тестах, обновлён `tests/test_database.py` (10-я таблица, колонка, внешние ключи);
- документация: `docs/timer.md`, `docs/db_schema.md`, `TEST-CHECKLIST.md`, `README.md`,
  `docs/user_story.md`, этот план и `TASKS-REPORT.md`.

**Готово, если:** `pytest` — 126 passed (61 без БД + 65 с БД), покрытие ≥ 80 %,
`ruff`/`black` чистые, `python -m app.migrate` добавляет колонку и таблицу и повторный запуск
возвращает `none`, контрактные тесты зелёные, ручной сценарий: рецепт с `cooking_time_minutes=1`
→ `POST /timers` без длительности → 201 и `ends_at = started_at + 60 с` → через минуту
`GET /timers/active` пуст.


## Задача 2. Данные со страниц povarenok.ru — `feat/recipe-pages`

**User story.** Как пользователь, я хочу видеть пошаговую инструкцию с количеством ингредиентов
на каждом этапе, чтобы готовить блюдо без путаницы (п. 6 в [`docs/user_story.md`](user_story.md)) —
и, как следствие, таймеры по шагам и более полную карточку рецепта.

**Почему эта задача.** Импорт датасета даёт только `url`, `name`, `ingredients`, поэтому у
импортированного рецепта пусты `instruction` и `difficulty_level`, а время для таймера (задача 1)
приходится вводить руками. Страница рецепта содержит шаги, время, порции и КБЖУ — это самый
дешёвый способ наполнить карточку, не покупая и не размечая данные.

**Критерии приёмки.**

1. Парсер читает страницу по микроразметке (`itemprop`), а не по CSS-классам, и выдерживает
   `windows-1251`, отсутствие отдельных блоков и битую вёрстку.
2. Шаги сохраняются по порядку в `recipe_steps` (номер, текст, фото шага) и дублируются
   нумерованным текстом в `recipes.instruction`.
3. Время и порции попадают в `recipes.cooking_time_minutes`/`recipes.servings`, **только когда
   страница их публикует** (это ~50 % и ~42 % страниц соответственно); КБЖУ — в `recipe_nutrition`
   (два блока: всё блюдо и 100 г).
4. Прогон идемпотентен: повторный запуск не делает ни одного запроса в сеть и ни одного `UPDATE`;
   `--force` переразбирает, `--refresh` перекачивает.
5. Один битый или недоступный рецепт не валит прогон: он попадает в счётчик `failed` и остаётся
   неразобранным, остальные обогащаются.
6. Ответы API не ломают контракт: `Recipe` получает `steps`, `servings`, `nutrition`, схемы
   `RecipeStep`/`RecipeNutrition`, контрактные тесты зелёные.

**Что сделано.**

- схема (миграция `0005_recipe_pages.sql`, 12 таблиц): `recipes.servings`, `recipes.parsed_at`,
  `recipes.parser_version`, таблицы `recipe_steps` (уникальность `(recipe_id, step_number)`) и
  `recipe_nutrition` (1:1 к рецепту, `numeric(10,2)` с проверками ≥ 0);
- `app/importer/pages.py` — чистый парсер и загрузчик (cp1251, собственный User-Agent, таймаут,
  `PageError`), ISO 8601 `totalTime` → минуты, деградация вместо падения;
- `app/importer/enrich.py` — отбор кандидатов, кэш HTML, вежливость (`--delay`), стоп по 403/429,
  одна транзакция на рецепт, статистика прогона;
- CLI: `--enrich`, `--url`, `--pages-dir`, `--delay`, `--force`, `--refresh`;
- API: `steps`/`servings`/`nutrition` в `Recipe` (три батч-запроса на страницу вместо N+1),
  `RecipeInput` не меняется — шаги и КБЖУ пишет только парсер;
- тесты: `tests/test_importer_pages.py` (23 кейса) на обрезанных реальных страницах, кейс
  карточки в `tests/test_recipes.py`, кейс контракта, обновлён `tests/test_database.py`;
- документация: [`docs/povarenok-pages.md`](povarenok-pages.md), `docs/db_schema.md`, README,
  TEST-CHECKLIST, `docs/test-coverage.md`, этот план и `TASKS-REPORT.md`.

**Эксперимент (12.11.2026).** Шесть живых страниц → мини-датасет → импорт → обогащение из кэша:

```
enrich: candidates=6, fetched=0, from_cache=6, updated=6, without_steps=0,
        without_time=2, without_servings=2, with_nutrition=6, failed=0
```

Шаги получили 6/6 рецептов (4–12 шагов на рецепт), время и порции — 4/6, КБЖУ — 6/6. Полный
текст эксперимента — в `TASKS-REPORT.md`, раздел «Спринт 3, задача 2».

## Решения, которые стоит помнить

| Решение | Почему так | Что было бы иначе |
|---|---|---|
| Дедлайн хранится в базе и считается её часами | web-процессов может быть несколько, а часы приложения и БД — разные; правило «дата из базы» уже принято для просроченных продуктов | таймер «уезжал» бы после перезапуска контейнера |
| `timestamptz` для `started_at`/`ends_at`/`closed_at` | таймер обязан пережить смену пояса и переход на летнее время | после перевода часов таймер срабатывал бы на час раньше/позже |
| Нет воркера | закрытие просроченных — один идемпотентный `UPDATE` в чтении списка | лишний процесс, который надо поднимать, мониторить и тестировать |
| Нет паузы | пауза почти всегда означает «перезапустить», а состояний и веток становится вдвое больше | усложнение API без выигрыша в точности |
| Фронтенд в задачу не входит | `frontend/` — пустая заготовка; алгоритм зафиксирован в `docs/timer.md` §5, чтобы реализация не придумывала свой | «таймер работает» нельзя было бы проверить контрактными тестами |

## Риски

| Риск | Как снижаем |
|---|---|
| Пользователь ждёт «звонок при закрытой вкладке» | в `docs/timer.md` §6 таблица точности: без Web Push это невозможно, push — задача 3 |
| Фронтенд ещё не написан, алгоритм может разойтись с ним | эталонный алгоритм и запреты («не считать тики», «не брать часы устройства») зафиксированы в документации и в docstring тестов |
| Слишком много активных таймеров от одного клиента | `MAX_ACTIVE_TIMERS = 20`, 21-й → 400 |
| Часовой пояс сервера и пользователя различаются | все моменты времени в API — ISO 8601 с offset (`serializers.iso_datetime`), в БД — `timestamptz` |
| Сайт изменит вёрстку | парсим микроразметку `itemprop`, а не классы; поведение зафиксировано фикстурами; `parser_version` позволяет переразобрать кэш без сети |
| Сайт начнёт отдавать 403 | свой User-Agent, `--delay 1.0`, стоп после трёх блокировок подряд; прогон сообщает `stopped`, а не долбит сайт |
| Часть ссылок датасета мертва | шаг 0 измеряет живость на реальных данных; при необходимости URL берутся из каталога сайта, мёртвые попадают в `failed` |
