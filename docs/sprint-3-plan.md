## Цель спринта

Дать пользователю таймер прямо в рецепте: время берётся из рецепта, отсчёт не сбивается
перезагрузкой и не зависит от часов телефона, а звонок срабатывает вовремя. Контракт API
меняется только там, где это нужно для таймера, и каждое изменение сопровождается обновлением
`openapi.yaml` и контрактными тестами (CONTRIBUTION.md §1).

## Задача 1. Таймеры в рецепте — `feat/recipe-timers`

**User story.** Как пользователь, я хочу видеть таймеры в рецепте, чтобы было удобнее засекать
время.

**Критерии приёмки** (полностью — в [`docs/user_story.md`](user_story.md), п. 7):

1. У рецепта можно указать время приготовления в минутах (`cooking_time_minutes`), оно
   возвращается в карточке рецепта; у импортированных рецептов времени нет (`null`).
2. Пользователь может запустить таймер рецепта: без явной длительности сервер берёт время
   рецепта; для рецепта без времени требуется `duration_seconds`, иначе понятная ошибка 400.
3. Запущенный таймер виден в списке активных до конца отсчёта; после перезагрузки страницы
   список приходит с сервера вместе с его текущим временем.
4. Таймер можно отменить; отменённый и истёкший таймеры исчезают из активных, в базе остаются
   со статусом `cancelled`/`finished`.
5. Таймеры одного пользователя не видны другому: владелец берётся из токена, чужой таймер — 404.
6. Отсчёт не сбивается: момент окончания хранится в базе, а клиент считает остаток от пары
   «`ends_at` − `server_time`» по монотонным часам (алгоритм — `docs/timer.md` §5).

**Что сделано.**

- схема: `recipes.cooking_time_minutes` (1..1440, nullable) и таблица `timers`
  (`timestamptz`-дедлайн, ограничения `duration_seconds`/`status`, индекс
  `timers_user_status_idx`), миграции `0003_recipe_cooking_time.sql`, `0004_timers.sql`;
- API: `POST /timers`, `GET /timers/active`, `DELETE /timers/{id}` под `@token_required`;
  валидация (`duration_seconds` 1..86400, `label` ≤ 100, максимум 20 активных таймеров);
- сервис: дедлайн вычисляет база (`now() + make_interval`), истёкшие таймеры закрываются чтением
  списка, поэтому отдельный воркер не нужен;
- контракт: 3 адреса, схемы `Timer`, `TimerInput`, `TimerCreatedResponse`,
  `ActiveTimersResponse`, поле `cooking_time_minutes` в `Recipe`/`RecipeInput`;
- тесты: `tests/test_timers.py` (11 кейсов), новый кейс в `tests/test_recipes.py`, 4 кейса в
  контрактных тестах, обновлён `tests/test_database.py` (10-я таблица, колонка, внешние ключи);
- документация: `docs/timer.md`, `docs/db_schema.md`, `TEST-CHECKLIST.md`, `README.md`,
  `docs/user_story.md`, этот план и `TASKS-REPORT.md`.

**Готово, если:** `pytest` — 126 passed (61 без БД + 65 с БД), покрытие ≥ 80 %,

## Решения, которые стоит помнить

| Решение | Почему так | Что было бы иначе |
|---|---|---|
| Дедлайн хранится в базе и считается её часами | web-процессов может быть несколько, а часы приложения и БД — разные; правило «дата из базы» уже принято для просроченных продуктов | таймер «уезжал» бы после перезапуска контейнера |
| `timestamptz` для `started_at`/`ends_at`/`closed_at` | таймер обязан пережить смену пояса и переход на летнее время | после перевода часов таймер срабатывал бы на час раньше/позже |
| Нет воркера | закрытие просроченных — один идемпотентный `UPDATE` в чтении списка | лишний процесс, который надо поднимать, мониторить и тестировать |
| Нет паузы | пауза почти всегда означает «перезапустить», а состояний и веток становится вдвое больше | усложнение API без выигрыша в точности |
| Фронтенд в задачу не входит | `frontend/` — пустая заготовка; алгоритм зафиксирован в `docs/timer.md` §5, чтобы реализация не придумывала свой | «таймер работает» нельзя было бы проверить контрактными тестами |
