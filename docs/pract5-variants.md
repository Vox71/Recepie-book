# Практика 5: как задания соотносятся с вариантами

Файл для отчёта и защиты. Здесь коротко: какой вариант что разрешает, какой способ реально
применён, почему не использованы остальные способы и как это объяснить.

## Главное правило

`docs/pract5` задаёт **разрешённые способы** рефакторинга для варианта. Использовать все четыре
способа не обязательно: можно взять один и повторить его несколько раз. Нельзя брать способы из
чужого варианта.

`docs/pract5_resolve` — это распределение вариантов по студентам и файлам проекта. «Участник 1,
вариант 8» означает не «вариант 1», а «первый участник списка делает вариант 8».

## Вариант 1 — Волков Михаил

**Разрешено:** Extract Method, Replace Method with Method Object, Remove Middle Man,
Encapsulate Field.

**Что сделано:** длинный `handle_starttag` разбит на короткий диспетчер и 15 методов
`_start_name`, `_start_nutrition`, `_start_step` и т. д.

**Почему это вариант 1:** каждая ветка `if/elif` вынесена в отдельный метод. Это классический
Extract Method: код не меняет поведение, но читается по частям.

**Почему не остальные способы:** `Method Object` здесь избыточен — нет сложного алгоритма с
состоянием; `Remove Middle Man` нечего удалять; инкапсулировать поля не требуется.

**Формулировка для отчёта:** «Применён Extract Method из варианта 1: тело `handle_starttag`
разбито на методы, порядок проверок сохранён».

## Вариант 6 — Журавлев Владислав

**Разрешено:** Remove Control Flag, Encapsulate Collection, Separate Query from Modifier,
Replace Constructor with Factory Method.

**Что сделано:** `active_timers()` разделена на `close_expired_timers()` (изменяет данные) и
`active_timers()` (только читает).

**Почему это вариант 6:** функция одновременно была запросом и модификатором. Теперь запрос
отделён от изменения — это Separate Query from Modifier.

**Почему не остальные способы:** управляющего флага и коллекции в этом участке нет; фабричный
метод не нужен, потому что конструктор не меняется.

**Формулировка для отчёта:** «Применён Separate Query from Modifier: `close_expired_timers`
отвечает за изменение, `active_timers` — только за чтение».

## Вариант 7 — Потапов Артем

**Разрешено:** Substitute Algorithm, Replace Magic Number with Symbolic Constant,
Replace Type Code with Subclasses, Decompose Conditional.

**Что сделано:** `parse_ingredients` разложена на `_is_missing_value`, `_parse_ingredients_text`,
`_pairs_from_container` и короткий диспетчер.

**Почему это вариант 7:** длинная цепочка `if/isinstance` — это условный оператор, который
разложен на отдельные функции. Ближайший способ — Decompose Conditional.

**Почему не остальные способы:** алгоритм не заменяется целиком; магических чисел и кодов типов
в этом участке нет.

**Формулировка для отчёта:** «Применён Decompose Conditional из варианта 7: цепочка проверок
формата разложена на отдельные функции, поведение сохранено».

## Вариант 5 — Савчук Иван

**Разрешено:** Extract Interface, Pull Up Method, Self Encapsulate Field, Remove Assignments to
Parameters.

**Что сделано:** общая разметка `AppLayout` и `AuthLayout` вынесена в `PageFrame`, оба layout
стали короткими обёртками.

**Как это связано с вариантом 5:** общий каркас «поднят» в один переиспользуемый компонент.
Формально это ближе к Extract Class / Extract Component, но в варианте 5 ближайший по смыслу
способ — Pull Up Method.

**Почему не остальные способы:** интерфейс здесь не нужен; полей и параметров, которые нужно
инкапсулировать, в компонентах нет.

**Формулировка для отчёта:** «Из варианта 5 применён Pull Up Method в адаптации для React:
общий каркас страниц поднят в `PageFrame`, два layout-файла оставлены обёртками».

**Слабое место:** если преподаватель требует буквальный Pull Up Method через наследование,
стоит заранее сказать, что в React используется композиция, а не классы.

## Вариант 4 — Тропина Елизавета

**Разрешено:** Replace Temp with Query, Replace Array with Object, Replace Type Code with
State/Strategy, Replace Error Code with Exception.

**Что сделано:** результаты рекомендаций вместо словарей `{"recipe": ..., "score": ...}`
складываются в `ScoredRecipe` с полями.

**Как это связано с вариантом 4:** составная структура данных заменена объектом. Формально
исходная структура — словарь, а не массив, поэтому это ближайший способ `Replace Array with
Object`, а не буквальный массив.

**Почему не остальные способы:** временную переменную можно было бы заменить, но основная
проблема — непроверяемые ключи; коды типов и кодов ошибок в участке отсутствуют.

**Формулировка для отчёта:** «Из варианта 4 применён Replace Array with Object по смыслу:
словарь результатов заменён объектом `ScoredRecipe` с явными полями».

**Слабое место:** строго говоря, это `Replace Data Value with Object`. Если преподаватель
принципиален, лучше не называть словарь массивом, а объяснить замену составной структуры
объектом.

## Вариант 8 — Мокрецов Егор

**Разрешено:** Introduce Explaining Variable, Replace Conditional with Polymorphism,
Introduce Parameter Object, Inline Temp.

**Что сделано:** восемь параметров `enrich_recipes` собраны в `EnrichOptions`.

**Почему это вариант 8:** это буквальный Introduce Parameter Object — вместо длинного списка
параметров один объект настроек. Функция принимает `db` и `options`.

**Почему не остальные способы:**

- Introduce Explaining Variable — нет длинного выражения, которое нужно объяснять;
- Replace Conditional with Polymorphism — нет условного оператора по типу;
- Inline Temp — нет временной переменной, которую нужно убирать.

**Формулировка для отчёта:** «Применён Introduce Parameter Object из варианта 8: восемь
параметров собраны в `EnrichOptions`; остальные способы варианта к участку не применимы».

## Как заполнять отчёт

Для каждого студента достаточно трёх предложений:

1. «В варианте N разрешены такие-то способы».
2. «В коде применён способ X: было ..., стало ...».
3. «Остальные способы не использованы, потому что ...; это не нарушение, так как методичка
   разрешает использовать не все способы варианта».

## Что сказать, если спросят про неиспользованные способы

«Методичка разрешает не использовать все способы варианта. В участке нет условий / временных
переменных / иерархии типов, поэтому выбранный способ — единственный подходящий. Поведение кода
не изменилось, это подтверждают тесты».
