# План спринта 4: фронтенд поверх готового API

Документ продолжает [`docs/sprint-3-plan.md`](sprint-3-plan.md). Спринт 3 дал серверу таймеры,
шаги и КБЖУ и создал клиент: каркас с роутингом (задача 3) и вёрстку экранов «Вход» и «Рецепт»
(задача 4). Спринт 4 — наполнение этого клиента данными: API-клиент, авторизация, реальный рецепт и
экран таймеров. Технические детали — в [`docs/frontend.md`](frontend.md), визуальная часть — в
[`docs/design-system.md`](design-system.md), алгоритм таймера — в [`docs/timer.md`](timer.md).

## Цель спринта

Пользователь открывает сайт, входит под своей учётной записью, открывает рецепт и запускает
таймер; после перезагрузки страницы таймер продолжает идти, потому что время считает сервер.
Контракт API не меняется: всё нужное уже отдаётся (`openapi.yaml`, 25 адресов), задача спринта —
клиент к нему.

## Задачи спринта

| № | Задача | Ветка | Статус |
|---|---|---|---|
| 1 | API-клиент и авторизация: `POST /login`, хранение токена, защита маршрутов (вёрстка входа готова) | — | ⏳ следующая |
| 2 | Страница рецепта на реальных данных: `GET /recipes/{id}`, шаги, ингредиенты, КБЖУ (вёрстка готова) | — | ⏳ после задачи 1 |
| 3 | Экран таймеров: старт, список активных, отмена, восстановление по `server_time` | — | ⏳ перенесена из спринта 3 |
| 4 | Остальные страницы: список рецептов, избранное, холодильник | — | ⏳ после задач 1–2 |

Порядок обязателен: без токена не работают ни таймеры, ни избранное (все адреса под
`@token_required`), а без карточки рецепта таймеру неоткуда взять `recipe_id` и
`cooking_time_minutes`.

## Задача 3 (перенесена из спринта 3). Экран таймеров

**Почему перенос.** В спринте 3 не хватило времени: каркас и роутинг сделаны, а экран требует
ещё API-клиента и авторизации. Серверная часть готова полностью (задача 1 спринта 3), поэтому
перенос не блокирует бэкенд и не меняет контракт.

**Что нужно сделать.**

- `src/api/` — `fetch`-обёртка с `Authorization: Bearer <token>`, разбором `{error}` и типами;
- `src/api/timers.ts` + `src/api/types.ts` — DTO по схемам `Timer`, `TimerInput`,
  `TimerCreatedResponse`, `ActiveTimersResponse` из `openapi.yaml`;
- хук `useTimers(recipeId)`: старт (`POST /timers`), список (`GET /timers/active`), отмена
  (`DELETE /timers/{id}`);
- якорь отсчёта по [`docs/timer.md`](timer.md) §5: `remaining0 = ends_at − server_time`,
  дальше `performance.now()`; часы устройства не используются;
- восстановление после перезагрузки и при возврате на вкладку (`visibilitychange`, `pageshow`);
- звонок: `AudioContext` разблокируется на клике «Старт», плюс вибрация и `Notification`, если
  разрешены;
- тесты (Vitest + Testing Library): рендер списка, старт, отмена, «таймер истёк — сработал один
  раз», восстановление из ответа сервера; `fetch` подменяется, сеть в тестах не используется.

**Критерии приёмки.**

1. На `/recipes/:recipeId` видно активные таймеры этого рецепта и кнопку «Старт».
2. После перезагрузки страницы таймер продолжает идти с тем же остатком (источник — сервер).
3. Отмена убирает таймер из списка; чужой таймер недоступен (404 обрабатывается понятной ошибкой).
4. По истечении времени звонок срабатывает ровно один раз.
5. Тесты покрывают все четыре сценария и не ходят в сеть.

**Статус:** ⏳ перенесена в спринт 4, не начата.

## Задача 1. API-клиент, авторизация и экран входа

- `src/api/client.ts`: базовый URL из `VITE_API_URL` (по умолчанию `http://localhost:8000`),
  `Authorization`, таймаут через `AbortSignal`, единый тип ошибки;
- `src/api/auth.ts`: `POST /register`, `POST /login`, `GET /profile`, `DELETE /profile`;
- хранение токена: решение зафиксировать в `docs/frontend.md` (localStorage vs память) — от
  него зависит поведение после перезагрузки и защита от XSS;
- экран `/login`: вёрстка готова (задача 4 спринта 3), остаётся реальная отправка формы, показ
  ошибок 400/401 и переход на `/recipes/:id` после успеха; защита маршрутов (неавторизованный
  уходит на `/login`);
- тесты: успешный вход, неверные данные, редирект, сохранение токена.

**Готово, если:** можно войти под пользователем из бэкенда и увидеть защищённую страницу; тесты
зелёные; токен не попадает в логи и в URL.

## Задача 2. Страница рецепта на реальных данных

Вёрстка готова (задача 4 спринта 3), мок `src/mocks/recipe.ts` типизирован под контракт — задача
меняет источник данных, а не разметку.

- `GET /recipes/{id}` → заголовок, ингредиенты (`ingredient_list`), шаги (`steps`), КБЖУ
  (`nutrition`), время и порции (поля уже выводятся, включая `null` как прочерк);
- состояния загрузки/ошибки/404;
- типы DTO — по схемам `Recipe`, `RecipeStep`, `RecipeNutrition`;
- тесты на рендер шагов, отсутствие шагов и 404.

**Готово, если:** карточка показывает данные из API, ничего не выдумывая при `null`
(время/порции/КБЖУ бывают пустыми — см. `docs/povarenok-pages.md`).

## Задача 4. Остальные страницы

Список рецептов (`GET /recipes`), избранное (`/favorite_recipes`), холодильник (`/products`),
рекомендации (`/recommend_recipes`) — по одной странице за раз, каждая с тестами и типами DTO.

## Риски

| Риск | Как снижаем |
|---|---|
| Токен в `localStorage` уязвим к XSS | решение и его последствия фиксируются в `docs/frontend.md`; токен не пишется в URL и логи |
| Отсчёт таймера на клиенте «поплывёт» | эталонный алгоритм из `docs/timer.md` §5, тесты на якорь и `visibilitychange` |
| Страница рецепта покажет пустоту как ошибку | `null` в `servings`/`nutrition` — норма (≈58 % страниц без порций), UI показывает прочерк |
| Фронтенд и бэкенд запускаются на разных портах | порт 3000 зафиксирован (`strictPort`), CORS уже настроен на него |
