# План спринта 4: рецепты, порции, рекомендации и внешняя интеграция

Документ заменяет предыдущую версию плана. Спринт 4 больше не посвящён только подключению
готового API к экрану таймеров: в центр вынесены работа с реальным рецептом, пересчёт порций,
рекомендации по холодильнику и проверка качества данных и модели. Экран таймеров и остальные
страницы в этот план не входят, если они не появятся в списке задач отдельно.

## Базовая линия

К началу спринта в `main` уже есть:

- регистрация и вход, JWT, защита личных маршрутов (`frontend/src/auth/`);
- API-клиент с заголовком `Authorization: Bearer` (`frontend/src/api/client.ts`);
- страница холодильника: список, добавление, удаление, удаление просроченных;
- защищённые адреса `/profile/fridge`;
- `GET /recipes/{id}` с ингредиентами, шагами, порциями и КБЖУ;
- парсер страниц povarenok для шагов, времени, порций и КБЖУ;
- TF-IDF + KNN и метрики ранжирования (`app/ml/evaluate.py`).

Это не переделывается. Новые задачи используют эту базу и меняют только то, что нужно для
описанных ниже сценариев.

## Цель спринта

Пользователь открывает реальный рецепт, меняет количество порций и видит пересчитанные
граммовки и КБЖУ. Система показывает рецепты, которые можно приготовить из продуктов в его
холодильнике, и список недостающих продуктов. Модель рекомендаций проверена на реальных данных,
основные отказы системы описаны и покрыты тестами. Интеграция с MCP Vkusvill вынесена в
отдельный этап: сначала проверяется доступность внешнего API, потом пишется код.

## Задача 1. Порции и пересчёт ингредиентов

**Ветка:** `feat/recipe-servings`.

### Что должно получиться

Страница `/recipes/:recipeId` показывает данные из `GET /recipes/{id}`, а не из
`frontend/src/mocks/recipe.ts`. Пользователь выбирает количество порций, и все числовые
количества ингредиентов пересчитываются пропорционально. КБЖУ пересчитывается по тем же
правилам. Если исходное количество порций неизвестно, система просит указать его явно и не
подставляет выдуманное значение.

### Что сделать

1. Добавить `frontend/src/api/recipes.ts`:
   - DTO `Recipe`, `RecipeIngredient`, `RecipeStep`, `RecipeNutrition`;
   - `getRecipe(token, recipeId, signal)`;
   - ошибки через существующий `ApiError`.
2. Перевести `RecipePage` на загрузку рецепта:
   - состояния `loading`, `error`, `404`;
   - отмена запроса через `AbortController`;
   - повтор запроса по кнопке.
3. Подключить статусы ингредиентов к холодильнику:
   - запросить `GET /profile/fridge` тем же токеном;
   - отметить продукт как имеющийся, если его название совпало с ингредиентом по нормализованной
     форме;
   - если холодильник недоступен, страница рецепта всё равно показывает ингредиенты, но без
     статусов «есть / нужно добавить» и с понятным предупреждением.
4. Ввести нормализацию количества:
   - `quantity_text` — исходная строка;
   - `amount` — число;
   - `unit` — единица;
   - `grams` — число граммов, если единица массы;
   - `scalable` — можно ли умножать.
5. Реализовать чистую функцию пересчёта:

   `factor = selected_servings / base_servings`.

   Для массы (`г`, `кг`) пересчитывать в граммах: `500 г × factor`, `1 кг` сначала переводить
   в `1000 г`.
   Для объёма (`мл`, `л`) сохранять объёмные единицы.
   Для штук, ложек, щепоток и подобных единиц масштабировать число, сохраняя единицу.
   Для `по вкусу`, `щепотка` без числа и иных нечисловых значений оставлять текст без изменения.

6. Пересчитывать КБЖУ:
   - общие значения — умножить на `factor`;
   - значения на 100 г — не менять;
   - значения на порцию — новое общее значение разделить на новое число порций.
7. Добавить управление порциями:
   - целое положительное число;
   - `0`, отрицательное, пустое и нечисловое значение не применяются;
   - при `servings = null` показать поле «На сколько порций рассчитан рецепт?» и не пересчитывать
     до ввода корректного базового значения.
8. Показывать в интерфейсе, что единицы, которые нельзя перевести в граммы, масштабируются в
   исходных единицах. Не выдавать «2 шт.» за граммы.
9. Добавить компонент или блок КБЖУ, если его ещё нет на странице.
10. Обновить тесты страницы рецепта: загрузка, ошибка, `404`, пересчёт, `null`-порции,
    нечисловые единицы, неверный ввод.

### Важно про токен

Маршрут `/recipes/:recipeId` уже закрыт `RequireAuth`. Токен нужен для доступа к странице и
запросам к API. Для самой арифметики токен не нужен.

Если требуется **сохранять выбранное количество порций за пользователем**, это отдельная
функция:

- таблица `user_recipe_servings`;
- `GET/PUT /profile/recipes/{id}/servings`;
- `user_id` только из токена;
- тест на чужого пользователя.

Без этого требования не нужно добавлять токен в формулу пересчёта.

### Критерии приёмки

- Страница рецепта не использует mock.
- Пересчёт ингредиентов и КБЖУ корректен при изменении порций.
- Некорректный ввод не меняет предыдущее корректное значение.
- При отсутствии базовых порций система просит их указать.
- Есть состояния загрузки, ошибки и `404`.
- Тесты, `typecheck`, `lint`, `format:check` и `build` зелёные.

### Риски

- В `quantity_text` встречаются разные форматы и нечисловые значения.
- У части рецептов нет `servings`.
- Не все единицы можно перевести в граммы без таблицы плотностей; это ограничение должно быть
  видно пользователю, а не скрыто.

## Задача 2. Реальные данные и рекомендации по холодильнику

**Ветка:** `feat/fridge-recommendations`.

### Что уже есть

`GET /recommend_recipes` уже защищён токеном, использует холодильник, аллергии и избранное.
Но текущий движок ранжирует рецепты по близости и бонусу за продукты, а не гарантирует, что
все ингредиенты рецепта есть у пользователя.

### Что сделать

1. Завершить подготовку реальных данных:
   - импортировать датасет;
   - выполнить `--enrich` для страниц;
   - заполнить `recipe_ingredients`, шаги, время, порции и КБЖУ там, где источник это даёт;
   - зафиксировать статистику: сколько рецептов без порций, шагов, времени и КБЖУ.
2. Обучить модель на реальном каталоге:

   ```bash
   python -m app.ml.model --from-db --limit 150000
   ```

   Артефакт не коммитить; путь передавать через `SMART_RECOMMENDATIONS_ARTIFACT`.
3. Добавить расчёт покрытия рецепта продуктами холодильника:
   - сравнивать нормализованные названия ингредиентов;
   - учитывать леммы;
   - определить список базовых продуктов (соль, вода, масло), которые можно не требовать;
   - вернуть `missing_ingredients` и `coverage`.
4. При необходимости добавить режим `?mode=full` для рецептов, где все основные ингредиенты
   есть в холодильнике, и обновить `openapi.yaml` и контрактные тесты.
5. Сделать интерфейс рекомендаций:
   - карточки рецептов;
   - список недостающих продуктов;
   - пустой холодильник;
   - отсутствие рецептов;
   - ошибка загрузки.
6. Тесты: полное покрытие, частичное покрытие, пустой холодильник, аллергии, чужой пользователь.

### Критерии приёмки

- Пользователь получает рецепты, которые покрываются продуктами его холодильника.
- Для каждого рецепта видно, чего не хватает.
- Пустой холодильник даёт понятное сообщение.
- Рекомендации строятся по данным пользователя из токена.
- Модель обучена на реальном каталоге, метрики зафиксированы.

### Важное ограничение

«Завершение парсинга» не означает, что нужно распарсить все 147 тысяч страниц до начала работы.
Для рекомендаций по ингредиентам достаточно датасета и `recipe_ingredients`. Полный обход
страниц нужен прежде всего для карточки рецепта: шаги, время, порции, КБЖУ. Эти задачи нужно
разделять, иначе рекомендации будут ждать многодневный парсинг сайта.

## Задача 3. Проверка качества модели

**Ветка:** `test/ml-quality-gate`.

### Важно

Текущая модель — TF-IDF + KNN. У неё нет функции потерь и градиентов в том смысле, в котором они
есть у обучаемой нейросети. Проверить loss и градиенты у неё нельзя: это проверка несуществующих
величин.

Есть два варианта:

- **A, рекомендуемый:** проверить качество ранжирования и сделать sanity-check на реальных
  данных. Использовать существующие `P@k`, `Recall@k`, `HitRate`, `MRR`, добавить
  train/validation/test и проверки на утечки.
- **B:** если loss и градиенты обязательны, сначала добавить обучаемую модель-реранкер и только
  потом считать loss на train/validation, проверять градиенты и делать sanity-check. Это
  отдельная ML-задача, а не тестирование текущей модели.

### Что сделать по варианту A

1. Разделить данные на train/validation/test по рецептам, а не по отдельным ингредиентам.
2. Обучать IDF только на train.
3. Считать на validation: `P@1`, `P@5`, `Recall@5`, `HitRate@5`, `MRR@5`, при необходимости
   NDCG, coverage и diversity.
4. Sanity checks: пустой профиль, неизвестный продукт, холодный старт, отсутствие артефакта,
   битый артефакт, повторяемость, отсутствие утечки train → test, время ответа.
5. Сравнить v1 с baseline на одном split.
6. Оформить отчёт с командами воспроизведения и ограничениями.

### Критерии приёмки

- Метрики воспроизводятся одной командой.
- Есть validation/test, а не только проверка на обучающем корпусе.
- Sanity-check не пропускает пустые и вырожденные ответы.
- Зафиксировано, что loss/градиенты к TF-IDF не применяются; при необходимости создана
  отдельная задача на обучаемую модель.

## Задача 4. Отказоустойчивость основной системы

**Ветка:** `test/resilience`.

### Что проверить

| Отказ | Ожидаемое поведение |
|---|---|
| PostgreSQL недоступна | понятная ошибка `503`, без частично записанных данных |
| пул соединений исчерпан | запрос не висит бесконечно, соединение возвращается |
| неверный или просроченный токен | `401`, очистка токена, возврат на `/login` |
| чужой ресурс | `404`, без раскрытия существования |
| таймаут povarenok | рецепт не считается разобранным, импорт продолжается |
| `403`/`429` от сайта | остановка после серии ошибок, без потери уже импортированного |
| битый HTML | запись не ломает транзакцию |
| отсутствующий артефакт модели | fallback на bag-of-lemmas, сервис работает |
| битый артефакт модели | предупреждение в лог, fallback |
| пустой холодильник | понятное сообщение |
| повторный запрос | идемпотентность там, где она обещана |

### Что сделать

- добавить тесты с подменой БД, сети и артефактов;
- проверить фронтенд: ошибка загрузки, повтор, отмена запроса, `401`;
- проверить импорт: прерывание, повторный запуск, `--force`, кэш;
- проверить рекомендации без модели и с пустыми данными;
- оформить отчёт: отказ → ожидаемое поведение → фактический результат → вывод.

### Критерии приёмки

- Ни один отказ не приводит к белому экрану, потере данных или зависанию.
- Найденные дефекты исправлены или заведены в техдолг.
- Есть воспроизводимый набор команд и отчёт.

## Задача 5. MCP Vkusvill

**Ветка:** `feat/vkusvill-mcp`.

### Сначала spike

До кода нужно проверить:

- существует ли доступный MCP-сервер ВкусВилла;
- какие инструменты он предоставляет: поиск товара, корзина, оформление;
- как проходит авторизация;
- есть ли ограничения API, тарифы и юридические ограничения;
- можно ли работать в тестовом окружении;
- какие данные нужны для сопоставления ингредиента с товаром.

Если доступа или официального API нет, задачу нельзя считать готовой к реализации. Это нужно
зафиксировать в отчёте и не имитировать интеграцию.

### Что сделать, если доступ есть

1. Вынести интеграцию в backend-адаптер, а не во фронтенд.
2. Секреты — только через переменные окружения.
3. Добавить таймауты, ограниченные повторные попытки и обработку ошибок.
4. Сопоставлять ингредиенты с товарами по названию, единице и количеству с учётом выбранных
   порций.
5. Добавлять в корзину только после подтверждения пользователя.
6. Обеспечить идемпотентность: повторный клик не должен добавлять товар дважды.
7. Тестировать с фейковым MCP-сервером; реальный сервис в CI не вызывать.
8. Отдельно проверить недоступность внешнего сервиса и частичное добавление.

### Критерии приёмки

- Недостающие ингредиенты добавляются в корзину в количестве, соответствующем выбранным порциям.
- Пользователь видит подтверждение и может перейти в корзину.
- При ошибке внешнего сервиса нет частично некорректного состава без уведомления.
- Секреты не попадают в репозиторий и логи.
- Недоступность MCP не блокирует остальные страницы.

## Риски

1. **Единицы измерения.** Не все ингредиенты можно перевести в граммы: «2 шт.», «по вкусу»,
   «щепотка». Нужен явный fallback.
2. **Отсутствие порций.** У части страниц нет `servings`; без базового значения автоматический
   пересчёт невозможен.
3. **Полное покрытие холодильника.** «Все продукты есть» — продуктовое правило; нужно определить,
   считаются ли соль, вода и масло обязательными.
4. **Реальные данные.** Импорт и enrich — долгие сетевые операции; нужны кэш и ограничение
   выборки.
5. **MCP Vkusvill.** Внешняя зависимость с неизвестным API; сначала spike, потом реализация.
6. **ML-задача.** Требование loss/градиентов не соответствует текущей модели; нужно либо
   переформулировать, либо менять модель.
