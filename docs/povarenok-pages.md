# Данные со страниц povarenok.ru

Документ описывает вторую ступень импорта: как из страницы рецепта получаются шаги, время,
порции и пищевая ценность, что именно мы берём и чего на сайте нет. Постановка — user story 6
в [`docs/user_story.md`](user_story.md), план — задача 2 в [`docs/sprint-3-plan.md`](sprint-3-plan.md).

## 1. Зачем: чего нет в датасете

Kaggle-датасет `rogozinushka/povarenok-recipes` — это таблица из трёх колонок: `url`, `name`,
`ingredients`. У импортированного рецепта поэтому пусты `instruction` и `difficulty_level`, и
карточка выглядит беднее, чем на сайте-источнике. Страница рецепта содержит:

- пошаговую инструкцию (с фотографией на каждый шаг);
- время приготовления и количество порций (не у всех);
- пищевую и энергетическую ценность;
- описание, категории, автора, фото блюда.

## 2. Что подтвердила проверка (шаг 0)

Замер на живой выборке (12.11.2026, 20 страниц из `/recipes/` + 12 страниц отдельно):

| Свойство | Результат |
|---|---|
| Доступность | 20/20 страниц → `200 OK`, размер 258–312 КБ (в среднем 275 КБ) |
| Кодировка | `windows-1251` (не UTF-8!) |
| Разметка | **schema.org microdata** (`itemprop`), JSON-LD **нет** |
| Шаги | есть **у 100 %** страниц: в среднем 7,3 шага (минимум 3, максимум 11) |
| КБЖУ | есть у 12/12 проверенных страниц |
| Время (`totalTime`) | есть у **6 из 12** |
| Порции (`recipeYield`) | есть у **5 из 12** |
| Сложность | **отсутствует** (ни текстом, ни в разметке) |
| `robots.txt` | `Allow: /`; запрещены `/ajax/`, `/search/*`, `/userrecipes/*`, `*sort=*`; `/recipes/show/` разрешён |
| User-Agent | `curl/8` получает **403**, `RecepieBookBot/0.1 (+repo)` — **200** |
| Ссылки датасета | у синтетического сэмпла репозитория часть URL мертва; живость реального датасета проверяется шагом 0 на скачанных данных |

Вывод: парсить надо по `itemprop`, а не по CSS-классам, и ходить под собственным именем.

## 3. Разметка страницы → поля базы

| Что на странице | Разметка | Куда попадает |
|---|---|---|
| Название | `h1[itemprop=name]` | не перезаписываем: `recipes.recipe_name` уже из датасета |
| Описание | `div.article-text[itemprop=description]` | разбирается, но в базу не пишется (нет колонки) |
| Категории | `span[itemprop=recipeCategory]` | разбираются, в базу не пишутся |
| Ингредиенты | `li[itemprop=recipeIngredient]` → `span` (название, количество) | не перезаписываем: `recipe_ingredients` уже из датасета |
| Шаги | `ul[itemprop=recipeInstructions] > li.cooking-bl`: текст в `div > p`, фото в `img[itemprop=image]` | **`recipe_steps`** (`step_number`, `text`, `image_url`) |
| Тот же текст шагов | — | **`recipes.instruction`** как нумерованный текст (`1. …\n2. …`) |
| Время | `<time itemprop="totalTime" datetime="PT40M">40 минут</time>` | **`recipes.cooking_time_minutes`** (`PT1H20M` → 80) |
| Порции | `span[itemprop=recipeYield]` | **`recipes.servings`** |
| КБЖУ | `div[itemprop=nutrition]`: группы «Готового блюда» (`itemprop=calories/proteinContent/…`) и «100 г блюда» (без `itemprop`, второй блок строк) | **`recipe_nutrition`**: 4 значения «на всё блюдо» + 4 «на 100 г» |
| Сложность | — | остаётся `NULL`; не выдумываем |

Решения, которые стоит помнить:

- **Шаги хранятся дважды** — строками в `recipe_steps` (структура для user story 6 и будущих
  таймеров по шагам) и текстом в `recipes.instruction` (чтобы старый клиент и текущий контракт
  `instructions` ничего не потеряли).
- **Время и порции заполняются не всегда**: примерно половина страниц их не публикует. Это
  честно отражено в `openapi.yaml` (`nullable: true`) и в статистике прогона.
- **Значения «на порцию» не хранятся**: они выводятся из `recipes.servings`; в базе лежат
  «всё блюдо» и «100 г» ровно так, как их публикует сайт.
- **`itemprop` вместо классов**: классы на сайте меняются при редизайне, микроразметка — часть

## 4. Как запускается

```bash
cd backend

# одна страница: посмотреть, что парсер видит сегодня (без БД)
python -m app.importer --url https://www.povarenok.ru/recipes/show/184919/

# обогатить уже импортированные рецепты (нужен DATABASE_URL)
python -m app.importer --enrich --limit 200 --delay 1.0

# переразобрать всё, что разобрано этим парсером (например, после правки парсера)
python -m app.importer --enrich --limit 200 --force

# скачать страницу заново, не доверяя кэшу
python -m app.importer --enrich --limit 5 --refresh
```

| Флаг | Что делает |
|---|---|
| `--enrich` | берёт из БД рецепты с `source_url` и без разбора (`parsed_at IS NULL` или другая `parser_version`) |
| `--limit N` | сколько рецептов за прогон (по умолчанию 200) |
| `--delay S` | пауза между запросами к сайту, секунды (по умолчанию 1.0) |
| `--force` | разбирать заново, даже если рецепт уже разобран этой версией парсера |
| `--refresh` | игнорировать кэш HTML и скачать страницу снова |
| `--url URL` | разобрать конкретную страницу и напечатать сводку (БД не нужна) |
| `--pages-dir PATH` | каталог кэша (по умолчанию `data/pages`) |

В конце прогона печатается одна строка статистики:

```json
{"candidates": 6, "fetched": 0, "from_cache": 6, "updated": 6, "without_steps": 0,
 "without_time": 2, "without_servings": 2, "with_nutrition": 6, "failed": 0, "stopped": null}
```

## 5. Кэш, вежливость, идемпотентность

- **Кэш**: HTML складывается в `backend/data/pages/<id>.html`. Каталог в `.gitignore` (там же,
  где датасет): 275 КБ на страницу, 200 рецептов ≈ 55 МБ. Второй прогон не делает ни одного
  запроса, а новый парсер можно раскатать по кэшу бесплатно.
- **Вежливость**: `--delay 1.0` (не чаще одного запроса в секунду), таймаут 20 с, собственный
  User-Agent, стоп после трёх `403`/`429` подряд — сайт не должен страдать от нашего импорта.
- **Идемпотентность**: `recipes.parsed_at` + `recipes.parser_version` помечают разобранное, повторный
  прогон не делает `UPDATE`; `--force` нужен только после изменения парсера.
- **Одна транзакция на рецепт**: упавшая страница не откатывает уже обогащённые рецепты, а
  проверка «не разобран» гарантирует, что следующий прогон вернётся именно к ней.
- **Деградация вместо падения**: пустой/битый HTML, отсутствие микроразметки или шагов — счётчик
  `failed`/`without_steps`, а не исключение; страница без шагов всё равно помечается разобранной,
  чтобы её не тянуть бесконечно.

## 6. Почему свой парсер, а не готовый инструмент

Рассматривался [`goodnight000/api-anything`](https://github.com/goodnight000/api-anything) —
инструмент, который «выучивает» HTTP-операции сайта для агентов. Он здесь **не нужен**:

1. povarenok.ru отсутствует в его каталоге (там Hacker News, Reddit, Amazon, Steam и т. п.),
   поэтому операцию всё равно писать руками — но на его DSL и внутри его рантайма;
2. у задачи нет того, что он решает: страница отдаёт статический HTML с микроразметкой, а не
   XHR-эндпоинты (кстати, `/ajax/` у сайта запрещён в `robots.txt`);
3. Node-сервис рядом с Python-only репозиторием — второй рантайм, вторая цепочка зависимостей и
   вторая точка отказа в CI;
4. «Выученные» операции и «самолечение» — внешние изменяемые артефакты: офлайновые
   детерминированные тесты на фикстурах (как здесь) с ними невозможны;
5. по умолчанию он делится выученными операциями наружу — для учебного проекта лишний риск.

Стоимость своего парсера: ~290 строк `app/importer/pages.py` (стандартная библиотека, без
новых зависимостей) + ~250 строк обогащения и CLI. Дешевле любого нового рантайма.

## 7. Что осталось за рамками

- **Фото блюда, категории, автор, описание** — разбираются, но под них нет колонок; добавление
  потребует миграции и правки контракта (кэш уже всё скачал, повторный обход не нужен).
- **Пересчёт ингредиентов по порциям** (user story 6) — нужны порции, а они есть у ~42 % страниц;
  нужен fallback, отдельная задача.
- **Живость ссылок реального датасета** — измеряется шагом 0 на скачанных данных; при большом
  числе мёртвых ссылок источником URL станет каталог сайта, а не датасет.

## 8. Как это проверяется

- `tests/test_importer_pages.py` — 23 кейса (19 без БД + 4 с БД): разбор сохранённых страниц
  (`tests/data/pages/*.html`, реальная разметка, обрезанная до нужных блоков), ISO-длительности,
  cp1251 и User-Agent, ошибки сети и HTTP, битый HTML, кэш, идемпотентность и `--force`,
  запись шагов/КБЖУ/времени/порций в PostgreSQL;
- `tests/test_recipes.py` — карточка разобранного рецепта отдаёт `steps`, `servings`, `nutrition`;
- `tests/test_openapi_contract.py` — ответы со шагами и КБЖУ соответствуют схемам `Recipe`,
  `RecipeStep`, `RecipeNutrition`;
- `tests/test_database.py` — 12 таблиц, колонки `recipes.servings`/`parsed_at`/`parser_version`,
  внешние ключи `recipe_steps`/`recipe_nutrition`, уникальность `(recipe_id, step_number)`.

  SEO-обвязки и живёт годами.
