# План спринта 2: данные povarenok, аллергены и модель рекомендаций v1

Документ фиксирует решения, порядок работ и критерии приёмки спринта. Он дополняет
[`ml_planning/ml_plan`](../ml_planning/ml_plan) (целевая архитектура ML) и
[`docs/db_schema.md`](db_schema.md) (фактическая схема БД).

## Цель спринта

Научить сервис работать на реальных данных: импортировать рецепты из открытого датасета,
фильтровать их по аллергиям и непереносимостям и подбирать рекомендации обученной моделью, а не
заглушкой. Контракт API меняется только там, где данные датасета этого требуют, и каждое
изменение сопровождается обновлением `openapi.yaml`.

## Данные

| Параметр | Значение |
|---|---|
| Источник | Kaggle, `rogozinushka/povarenok-recipes`, версия 1 |
| Объём | ~147 000 рецептов (выгрузка 2021-06-16) |
| Поля | `url`, `name`, `ingredients` (словарь `{ингредиент: количество}`) |
| Чего нет | инструкций, шагов, времени, порций, сложности |
| Лицензия | не указана |

Следствия, зафиксированные в решениях:

- сырые данные **не коммитятся** и **не попадают в образ**: скачивание — скриптом, доступ к
  Kaggle — только через переменные окружения (`KAGGLE_USERNAME`, `KAGGLE_KEY`), артефакты модели
  лежат в `backend/app/ml/artifacts/` и перечислены в `.gitignore`;
- тесты используют синтетический сэмпл `backend/tests/data/povarenok_sample.json` (10–20 записей);
- из-за отсутствия инструкций `recipes.instruction` стала nullable, а импортированные рецепты
  получают `instruction = NULL`, `difficulty_level = NULL` и заполненный `source_url`;
- зависимость от pandas/pyarrow/kagglehub вынесена в отдельный файл
  `backend/requirements-ml.txt`, чтобы продовый образ не потяжелел.

## Задачи спринта

Порядок выполнения: **1 → 3 → 2 → 4 → 6.1 → 6.0/6.2 → 5**, задача 7 идёт параллельно.
Одна задача — одна ветка — один PR (CONTRIBUTION.md §1, §14).

### Задача 1. Схема БД под импорт — `feat/recipe-ingredients-schema`

- таблица `recipe_ingredients` (`recipe_id`, `ingredient_name`, `quantity_text`, `sort_order`),
  уникальность `(recipe_id, ingredient_name)`, индекс по `ingredient_name`, `ON DELETE CASCADE`;
- `recipes.source_url UNIQUE` — естественный ключ импорта и идемпотентность парсера;
- `recipes.instruction` → `text`, `recipes.created_at/updated_at`, `favorite_recipes.created_at`;
- триггер `recipes_updated_at_trigger`;
- миграция `0002_recipe_ingredients.sql`, идемпотентная и безопасная для пустой базы;
- исправление `0001`: `DROP TABLE` только для легаси-схемы (иначе миграция стирала данные);
- документация `docs/db_schema.md`, обновление README, TEST-CHECKLIST и TASKS-REPORT.

**Готово, если:** `pytest` — 44 passed, `ruff`/`black` чистые; `python -m app.migrate` на копии
старой схемы сохраняет данные, повторный запуск применяет `none`.

**Статус:** ✅ выполнено, ветка `feat/recipe-ingredients-schema` (9 таблиц, 44 кейса).

### Задача 2. Парсер датасета и пагинация `GET /recipes` — `feat/povarenok-import`

- `app/importer/povarenok.py`: чтение parquet/csv датасета, нормализация названий и ингредиентов,
  склейка `recipes.ingredients`, разбор словаря в `recipe_ingredients`;
- `app/importer/cli.py`: `python -m app.importer --limit 1000 --batch-size 1000 --dry-run`;
  батчевая вставка в одной транзакции, `ON CONFLICT (source_url) DO NOTHING`;
- логирование прогресса без персональных данных, таймауты на сетевые вызовы;
- пагинация `GET /recipes?limit=&offset=` (сейчас адрес отдаёт все рецепты — на 147 тыс. это
  неприемлемо), обновление `openapi.yaml` и тестов.

**Готово, если:** повторный импорт того же файла не создаёт дублей; импорт сэмпла укладывается в
согласованное время и не ест память пропорционально файлу; пагинация покрыта успешным и «плохим»
кейсом.

**Статус:** ✅ выполнено, ветка `feat/povarenok-import`: `app/importer/povarenok.py`,
`app/importer/source.py`, `app/importer/cli.py`, `python -m app.importer --dataset ... --limit ...
--batch-size ... --dry-run`, `GET /recipes?limit=&offset=` (по умолчанию 50, максимум 200), 13 новых
кейсов (11 импорт + 2 пагинация), всего 59. `kagglehub` и `pandas` не понадобились: скачивание —
стандартный `urllib` с таймаутом, CSV — `csv`, parquet — `pyarrow` из `requirements-ml.txt`.

### Задача 3. Исправление работы с просроченными продуктами — `fix/expired-products`

- просроченным считается продукт со `expiration_date < CURRENT_DATE`, «сегодня» ещё годен;
- `DELETE /delete_expired_products` и `/notify_expired` используют одно правило;
- тест на границу «сегодня/вчера» и на идемпотентность повторного удаления.

**Готово, если:** поведение совпадает у обоих адресов, граничный кейс покрыт тестом.

**Статус:** ✅ выполнено, ветка `fix/expired-products`: правило задано один раз
(`EXPIRED_CONDITION` в `app/models/fridge.py`) и считается по `CURRENT_DATE`, добавлены кейсы на
границу «вчера / сегодня / завтра», на повторное удаление и на совпадение отчёта с удалением
(59 кейсов всего после задач 1–3).

### Задача 4. API избранного — `feat/favorites-api`

- `GET/POST/DELETE /favorite_recipes` с JWT, `user_id` только из токена (CONTRIBUTION.md §3);
- список отдаётся по `favorite_recipes.created_at` (от новых к старым);
- повторное добавление идемпотентно (`ON CONFLICT DO NOTHING`), чужие записи недоступны;
- обновление `openapi.yaml`, по 1 успешному и 1 «плохому» кейсу на адрес.

**Готово, если:** авторизация и доступ к чужим данным проверены тестами.

**Статус:** ✅ выполнено, ветка `feat/favorites-api`: три адреса с `token_required`,
порядок по `favorite_recipes.created_at`, идемпотентное добавление, чужая запись — 404;
4 новых кейса (65 всего после задачи 4).

### Задача 6.1. Аллергии и непереносимости — `feat/allergen-filter`

- словарь аллергенов и групп (`app/ml/allergens.py`): молоко, глютен, орехи, яйца, соя, рыба,
  морепродукты и т. д., с синонимами и словоформами;
- фильтрация по `recipe_ingredients` (а не по тексту), совпадение по леммам;
- метрика качества фильтра: precision/recall/F1 на вручную размеченной выборке 200–300 рецептов
  и `violation_rate` (доля пропущенных аллергенов) — целевое значение `0`.

**Готово, если:** `violation_rate = 0` на размеченной выборке, F1 зафиксирован в отчёте, фильтр
покрыт unit-тестами (включая «похожие, но не аллергены» — кокос, гречка).

**Статус:** ✅ выполнено, ветка `feat/allergen-filter`: `app/ml/allergens.py` (13 групп, синонимы,
словоформы, `blockers` и `exceptions` против ложных срабатываний),
`app/services/allergen_service.py` (фильтр по `recipe_ingredients`, текст — только запасной
вариант), `app/models/recipes.py::list_ingredient_names`, `app/ml/allergen_eval.py` (метрики),
размеченная выборка `tests/data/allergen_labeled_sample.json` (211 рецептов, 259 меток),
`docs/allergen-filter.md`; оба режима `GET /recommend_recipes` используют новый фильтр.
Прогон: precision/recall/F1 = 1.000, `violation_rate = 0.000`; 10 новых кейсов (75 всего).

### Задача 6.0/6.2. Модель рекомендаций v1 и метрики — `feat/recommendation-model-v1`

- TF-IDF по леммам ингредиентов + косинусная близость, отбор кандидатов KNN;
- артефакт `backend/app/ml/artifacts/v1.joblib` (в `.gitignore`), путь — в настройке
  `SMART_RECOMMENDATIONS_ARTIFACT`, при отсутствии файла — прежняя заглушка (graceful fallback);
- SBERT — только ablation на подвыборке 10–20 тыс. рецептов, в v1 не входит;
- метрики ранжирования: leave-one-ingredient-out → Precision@5, Recall@5, HitRate@5, MRR,
  сравнение с текущей заглушкой как baseline;
- отчёт с числами и командами воспроизведения (`python -m app.ml.evaluate`).

**Готово, если:** метрики v1 выше baseline по Precision@5 и MRR, отчёт воспроизводится одной
командой, отсутствие артефакта не ломает сервис.

**Статус:** ✅ выполнено, ветка `feat/recommendation-model-v1`: `app/ml/model.py` (IDF
`ln((1+N)/(1+df)) + 1`, JSON-артефакт, стат-кэш, `python -m app.ml.model`), `app/ml/corpus.py`
(корпус из `recipes` + `recipe_ingredients` или из файла датасета), `app/ml/evaluate.py`
(leave-one-ingredient-out, `python -m app.ml.evaluate`), бэкенд `tf-idf-v1` в
`app/ml/vectorizer.py`, настройка `SMART_RECOMMENDATIONS_ARTIFACT`, корпус
`tests/data/recommendation_sample.json` (120 рецептов, 813 запросов), `docs/recommendation-model.md`.
Прогон: `P@5` 0.326 → 0.360 (+3,3 п.п., +10 % относительно), `MRR` 0.493 → 0.513, `Hit@5`
0.672 → 0.711; критерий выполнен. 9 новых кейсов (84 всего). Артефакт — JSON вместо
`v1.joblib`: модель это словарь весов, JSON не требует зависимости и не исполняет код при
загрузке (обоснование — в `docs/recommendation-model.md`).

### Задача 7. Покрытие тестами по ГОСТ — `docs/test-coverage-gost`

Отдельный документ `docs/test-coverage.md`: уровень покрытия и соответствие тестовой
документации российским стандартам. Что в нём будет:

- **метрики покрытия**: statement и branch coverage (`coverage.py`) по `app/` целиком и по новым
  модулям (`importer`, `ml/allergens`, `ml/model`), измеренные значения и целевые пороги
  (backend ≥ 80 % строк, новые модули ≥ 85 %, ветки фильтра аллергенов — 100 %);
- **уровни тестирования** по ГОСТ Р 56920-2016 (ISO/IEC/IEEE 29119-1): модульные, интеграционные,
  системные, приёмочные — что именно покрывает каждый уровень в проекте;
- **тестовые процессы** по ГОСТ Р 56921-2016 (29119-2): планирование, мониторинг, проектирование,
  выполнение, оценка критериев завершения;
- **тестовая документация** по ГОСТ Р 56922-2016 (29119-3): как `TEST-CHECKLIST.md` и отчёты о
  прогонах отображаются на документы стандарта (test plan, test design specification, test case,
  test procedure, test report);
- **виды испытаний** по ГОСТ 34.603-92 и программа и методика испытаний по ГОСТ 19.301-79:
  какие разделы ПМИ закрывает текущий набор и что нужно дописать для приёмки;
- **модель качества** по ГОСТ Р ИСО/МЭК 25010-2015: какие характеристики качества подтверждены
  тестами, а какие — нет (например, производительность подтверждается только замером импорта).

**Готово, если:** документ содержит измеренные числа (а не только пороги), таблицу соответствия
«требование стандарта → артефакт проекта» и раздел «чего не хватает для полного соответствия».

## Риски

| Риск | Что делаем |
|---|---|
| Лицензия датасета не указана | данные и артефакты не публикуются, импорт только локально, в отчёте — ссылка на источник |
| 147 тыс. рецептов не влезают в память | потоковое чтение + батчи по 1–5 тыс. строк |
| Флаг `SMART_RECOMMENDATIONS_ENABLED` меняет поведение адреса | оба режима проверяются на одних данных, baseline сохраняется до приёмки модели |
| Аллергены — цена ошибки выше метрик | `violation_rate = 0` как обязательный критерий, ручная разметка выборки |
| Расползание PR | одна задача — одна ветка, контракт обновляется в том же PR, где меняется API |
