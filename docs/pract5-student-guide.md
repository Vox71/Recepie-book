# Практика 5: что делать студентам

Короткая инструкция без лишней теории. У каждого своя ветка и свой маленький рефакторинг.
Главное правило: **не трогаем чужие файлы и не меняем поведение сайта**.

## 1. Возьми свою ветку

```bash
git switch main
git pull
git switch -c refactor/pract5-<имя>
```

Имя ветки смотри в своём файле в `docs/pract5-guides/`.

## 2. Поменяй только то, что написано в задании

В каждом гайде есть список файлов. Если по ходу работы захочется «заодно поправить» что-то
рядом — не надо. Лучше создай issue с меткой `tech-debt` и расскажи ревьюеру.

## 3. Проверь, что ничего не сломал

Бэкенд:

```bash
cd backend
ruff check .
black --check .
pytest
```

Фронтенд:

```bash
cd frontend
npm ci
npm run format:check
npm run lint
npm run typecheck
npm run test:coverage
npm run build
```

Если падает — сначала чиним, потом просим ревью. Красный CI на ревью не отправляем.

## 4. Открой PR

Заголовок примерно такой:

```text
refactor(importer): extract start tag handlers
```

В описании заполни шаблон из `.github/pull_request_template.md`. Коротко, без сочинений:

- что было;
- что стало;
- почему так;
- сколько примерно строк заняла область ревью;
- как проверял;
- что не менял.

## 5. Что будет дальше

1. Ревьюер читает PR и пишет замечания — это **первый раунд**.
2. Ты отвечаешь и исправляешь в этой же ветке.
3. Ревьюер смотрит исправления — это **второй раунд**.
4. После approve PR можно мержить.

Не создавай второй PR на исправления. Всё делается в том же PR.

## 6. Как отвечать на замечания

Нормальный ответ выглядит так:

```text
Понял, поправил в 4f2a1c. Согласен, так читается лучше.
```

Или так, если не согласен:

```text
Тут оставил как было, потому что порядок проверок важен: сначала h1, потом div.
Если поменять, сломается разбор страницы. Могу добавить комментарий в код.
```

Не спорь о вкусе. Если вопрос про стиль — открой `docs/pract3-style-guide.md` и дай ссылку на
пункт.

## 7. Что писать в отчёт

После раундов заполни свой файл в `docs/pract3-reviews/`. Там нужны:

- текст PR;
- комментарии ревьюера и твои ответы;
- оба раунда;
- оценки;
- «было/стало» и техдолг.

Шаблон: `docs/pract3-reviews/TEMPLATE.txt`.

## 8. Чего точно не делать

- не менять API и JSON;
- не трогать БД;
- не переименовывать чужие функции;
- не добавлять новую функциональность;
- не пушить в `main`;
- не ревьюить свой PR;
- не писать «исправил» без коммита.
