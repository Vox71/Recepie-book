# Практика 5: инструкция для студентов

Короткая инструкция без лишней теории. У каждого участника своя ветка и свой небольшой
рефакторинг. Главное правило: **чужие файлы не меняются, поведение сайта остаётся прежним**.

## 1. Ветка

Ветка создаётся от `main`:

```bash
git switch main
git pull
git switch -c refactor/pract5-<имя>
```

Название ветки указано в персональном файле в `docs/pract5-guides/`.

## 2. Границы изменения

В каждом гайде есть список файлов. Если по ходу работы хочется «заодно поправить» что-то рядом,
лучше создать issue с меткой `tech-debt` и сообщить об этом ревьюеру.

## 3. Проверки

Бэкенд:

```bash
cd backend
ruff check .
black --check .
pytest
```

Фронтенд:

```bash
cd frontend
npm ci
npm run format:check
npm run lint
npm run typecheck
npm run test:coverage
npm run build
```

Если проверки падают, PR не отправляется на ревью. Сначала исправляется CI, потом запрашивается
review.

## 4. PR

Пример заголовка:

```text
refactor(importer): extract start tag handlers
```

В описании заполняется шаблон из `.github/pull_request_template.md`. Коротко:

- что было;
- что стало;
- почему так;
- сколько примерно строк заняла область ревью;
- как выполнялась проверка;
- что не менялось.

## 5. Два раунда

1. Ревьюер читает PR и пишет замечания — это **первый раунд**.
2. Автор отвечает и исправляет код в этой же ветке.
3. Ревьюер проверяет исправления — это **второй раунд**.
4. После approve PR можно мержить.

Второй PR на исправления не создаётся. Всё делается в том же PR.

## 6. Ответы на замечания

Нормальный ответ:

```text
Понял, поправил в 4f2a1c. Согласен, так читается лучше.
```

Если замечание не подходит:

```text
Здесь оставлено как было, потому что порядок проверок важен: сначала h1, потом div.
Если поменять, сломается разбор страницы. Можно добавить комментарий в код.
```

Спорить о вкусе не нужно. Если вопрос про стиль, следует открыть `docs/pract3-style-guide.md` и
дать ссылку на пункт.

## 7. Отчёт

После раундов заполняется файл в `docs/pract3-reviews/`. Там нужны:

- текст PR;
- комментарии ревьюера и ответы автора;
- оба раунда;
- оценки;
- «было/стало» и техдолг.

Шаблон: `docs/pract3-reviews/TEMPLATE.md`.

## 8. Чего делать нельзя

- менять API и JSON;
- трогать БД;
- переименовывать чужие функции;
- добавлять новую функциональность;
- пушить в `main`;
- ревьюить свой PR;
- писать «исправил» без коммита.
