# Рекомендации: `backend/app/ml/engine.py`

## Что делает файл

`recommend_safe_recipes` — конвейер рекомендаций:

1. берёт любимые рецепты пользователя как обучающую выборку;
2. если любимых нет, строит cold start из продуктов холодильника;
3. убирает рецепты с аллергенами;
4. векторизует тексты ингредиентов;
5. строит профиль пользователя как центроид векторов;
6. находит K ближайших рецептов;
7. добавляет бонус за продукты из холодильника;
8. сортирует, фильтрует и возвращает top-limit.

Файл не ходит в базу. Все данные приходят аргументами, поэтому тесты вызывают его напрямую.

## Аргументы функции

| Аргумент | Что это | Почему |
|---|---|---|
| `favourites` | строки рецептов, которые пользователь любит | обучающая выборка |
| `fridge_products` | названия продуктов | бонус к похожим рецептам |
| `allergies` | аллергии пользователя | фильтр безопасности |
| `recipes` | кандидаты | из них выбирается ответ |
| `limit` | сколько вернуть | ограничение ответа |
| `neighbours` | сколько соседей взять у KNN | параметр алгоритма |
| `settings` | настройки приложения | выбор TF-IDF/fallback |
| `ingredient_names` | ингредиенты из `recipe_ingredients` | точный фильтр аллергенов |
| `model` | обученная TF-IDF-модель | необязательный артефакт |

Почему аргументы keyword-only (`*`): их много и они однотипные; позиционный вызов легко
перепутать.

Почему `max(limit, 0)`: отрицательный limit не должен превращаться в срез «с конца».

Почему фильтр `score > 0`: рецепт без сходства и без продукта из холодильника — не рекомендация.

Почему `tuple(matched_products)` в будущем `ScoredRecipe`: объект неизменяемый, как и весь
dataclass.

## Вспомогательные функции

`_ingredients(row)` (133–135) берёт `row.get("ingredients")` и `strip()`. Если поле `NULL`,
возвращается пустая строка, а не `None`, чтобы дальше не проверять тип.

`_training_sample(favourites)` (138–140) оставляет только непустые тексты. Рецепт без ингредиентов
не должен создавать пустой вектор.

`_reject_allergens` (143–167):

- `allergens.resolve_allergies(allergies)` расширяет группы («молочные продукты» → «сливки»,
  «творог»);
- если аллергий нет, возвращает всех кандидатов;
- для каждого рецепта берёт имена ингредиентов и проверяет `matched_allergens`;
- при совпадении увеличивает счётчик и логирует причину.

`_ingredient_names` (170–177): если есть `recipe_ingredients`, использует их; иначе падает на
текстовое поле `recipes.ingredients`. Это компромисс: структура точнее, но её может не быть.

`_matching_products` (180+) сравнивает продукты без учёта регистра и нормализует текст. Это нужно,
чтобы «Молоко» и «молоко» считались одним продуктом.

## Почему сейчас словарь, а не класс

Элемент результата выглядит так:

```python
{
    "recipe": row,
    "similarity": similarity,
    "score": similarity + FRIDGE_BONUS * share,
    "matched_products": matched_products,
}
```

Плюс словаря: быстро написать. Минус: ключи нигде не проверяются. Опечатка `"scor"` не вызовет
ошибку при создании, а сортировка упадёт позже или вернёт пустой результат.

`ScoredRecipe` с четырьмя полями делает контракт явным:

```python
@dataclass(frozen=True)
class ScoredRecipe:
    recipe: dict
    similarity: float
    score: float
    matched_products: tuple[str, ...]
```

Почему `frozen=True`: результат одного расчёта не должен меняться по дороге к сервису.

Почему `recipe: dict`, а не отдельный тип: строка из базы имеет много полей и используется в
разных местах; отдельный DTO для рецепта — другая задача.

## Почему KNN написан вручную

В `knn.py` нет sklearn:

- данных на один запрос мало (рецепты установки и любимые одного пользователя);
- не нужна тяжёлая зависимость в старте API;
- код KNN короткий и понятный;
- sklearn можно подключить позже, заменив только `k_nearest`.

Сортировка стабильная: при равном сходстве сохраняется исходный порядок, поэтому одинаковые
данные дают одинаковый ответ.

## Почему не другие варианты

- **Отдавать все рецепты без score** — пользователю не нужен мусор.
- **Сортировать по `similarity` без бонуса** — тогда холодильник не влияет.
- **Считать score в SQL** — ML-логика размажется по запросам.
- **Класс вместо dict сразу** — это и есть задача рефакторинга; до неё словарь работает, но
  хуже читается.
- **`list` вместо `tuple` для `matched_products`** — tuple подчёркивает неизменяемость результата.

## Что спросит преподаватель

1. Что такое cold start? — пользователь без любимых рецептов, профиль строится из холодильника.
2. Почему аллергены фильтруются до KNN? — безопасность важнее рекомендаций; дешевле не считать
   векторы для опасных рецептов.
3. Почему профиль — центроид? — это простой способ получить один вектор интересов пользователя.
4. Почему `stats` не уходит пользователю? — это диагностика; API отдаёт только рецепты.
5. Почему замена dict на dataclass не меняет API? — сервис превращает `ScoredRecipe` обратно в
   `entry.recipe`, а `outcome` остаётся словарём.
