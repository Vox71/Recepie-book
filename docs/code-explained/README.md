# Разбор кода для защиты практики 5

Эта папка — не методичка по рефакторингу и не отчёт. Здесь лежит объяснение кода, с которым
работают студенты: что делает каждая функция, что означает каждая группа строк, почему написано
именно так и какие альтернативы не выбраны.

## Как пользоваться

1. Открыть файл своего варианта.
2. Найти функцию, которую меняет студент.
3. Прочитать таблицу «строка → действие → причина».
4. Проверить себя вопросами в конце: преподаватель обычно спрашивает не «что такое for», а
   «почему здесь именно так и что будет, если сделать иначе».

Номера строк указаны по состоянию `main` на момент написания. Если строки сдвинулись, искать
нужно по имени функции или класса, а не только по номеру.

## Общая картина проекта

Проект состоит из четырёх больших частей:

```text
povarenok.ru / датасет
        ↓
backend/app/importer/  — читает датасет и страницы рецептов
        ↓
PostgreSQL             — recipes, ingredients, steps, timers, users
        ↓
backend/app/services/  — бизнес-логика
backend/app/api/       — HTTP-ручки
        ↓
frontend/              — React-страницы
```

Код разделён по слоям не для красоты:

- `api/` принимает HTTP-запрос и не содержит правил;
- `services/` решает, что делать;
- `models/` содержит SQL;
- `importer/` разбирает внешние данные;
- `frontend/` показывает результат.

На защите полезно объяснять не «этот файл что делает», а **поток данных**: откуда пришли данные,
кто их проверил, где они сохранились и как попали на экран.

## Вопросы, которые стоит задать себе перед защитой

- Что функция принимает и что возвращает?
- Какие у неё побочные эффекты: запись в базу, сеть, изменение файла?
- Что будет при `None`, пустом списке, чужом пользователе, битой странице?
- Почему выбрана эта структура данных, а не словарь/список/класс?
- Где это проверяется тестами?
- Что произойдёт, если убрать строку или поменять порядок строк?

Если на все эти вопросы есть ответ по своему участку, построчный разбор не будет неожиданностью.
