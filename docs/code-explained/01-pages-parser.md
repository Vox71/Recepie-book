# `backend/app/importer/pages.py`: разбор страницы рецепта

## Зачем нужен файл

Датасет povarenok содержит только ссылку, название и ингредиенты. На самой странице рецепта есть
шаги, время, порции, фото шагов и КБЖУ. Этот файл скачивает страницу и вытаскивает из HTML нужные
поля.

Ключевая идея: страница размечена **microdata schema.org** — атрибутами `itemprop`, а не
JSON-LD. Парсер ищет `itemprop="name"`, `itemprop="recipeIngredient"` и т. п. Если сайт поменяет
CSS-классы, парсер всё равно продолжит работать; если поменяет `itemprop`, сломается.

## Поток данных

```text
source_url из базы
    ↓
fetch_recipe_page() — скачать HTML, раскодировать windows-1251
    ↓
parse_recipe_page() — HTMLParser собирает microdata
    ↓
ParsedPage — неизменяемый объект с полями
    ↓
enrich.save_page() — запись в recipes / recipe_steps / recipe_nutrition
```

`parse_recipe_page` не ходит в сеть. Это важно для тестов: в тестах используется сохранённый HTML,
поэтому результат не зависит от интернета и от изменений на сайте.

## Константы и зачем они нужны

| Строки | Что | Почему |
|---|---|---|
| 40–43 | `USER_AGENT`, `DEFAULT_TIMEOUT_SECONDS` | Сайт отвечает 403 анонимным клиентам; таймаут обязателен для внешнего запроса |
| 45–51 | `MAX_STEPS`, `MAX_STEP_TEXT`, `MAX_INSTRUCTION_LENGTH`, `MAX_IMAGE_URL_LENGTH` | Ограничения колонок БД; битая страница не должна писать бесконечный текст |
| 53–58 | `NUMBER_RE`, `DURATION_RE` | Разбор чисел и ISO-длительности `PT1H20M` |
| 59–60 | `GROUP_TOTAL`, `GROUP_PER_100G` | Два блока КБЖУ: на всё блюдо и на 100 г |

Ограничения стоят не «на всякий случай»: `recipe_steps.text` и `image_url` имеют конечный размер.
Если не обрезать строку, PostgreSQL отклонит INSERT уже внутри транзакции.

## Классы данных

`Ingredient` (67–72) — имя и необязательное количество. `quantity: str | None`, потому что
«Соль» может быть без количества. Это не ошибка данных, а нормальный случай.

`Nutrition` (75–106) — восемь необязательных чисел. Метод `is_empty()` проверяет, есть ли хоть
одно число; если страница не дала КБЖУ, объект не сохраняется.

`ParsedPage` (109–135) — результат разбора. Поле `steps` — кортеж строк, `step_images` — кортеж
такой же длины. `instruction_text` собирает шаги в пронумерованный текст для старого поля
`recipes.instruction`.

Почему dataclass, а не словарь: поля проверяются при чтении, автодополнение работает, а
случайная опечатка в имени поля становится ошибкой, а не `None`.

## `_RecipeParser`: состояние разбора

`HTMLParser` вызывает методы `handle_starttag`, `handle_endtag`, `handle_data` по мере чтения
HTML. Парсер хранит счётчики вложенности: `_in_name`, `_in_description`, `_in_time` и т. д.

Счётчик нужен потому, что HTML может быть сломан: `</li>` иногда приходит без открывающего
`<li>`, а вложенные теги могут не закрываться. Если вычитать счётчик в ноль, это не должно
ронять импорт.

`_capturing` (287–297) — свойство, которое отвечает: «сейчас собирается какой-то текстовый
фрагмент?». Оно проверяет все счётчики. Если да, `handle_data` складывает текст в общий
`_buffer`.

## `handle_starttag` построчно

Сигнатура (178): `tag` — имя тега, `attrs` — список пар «атрибут, значение». `HTMLParser`
специально отдаёт список, а не словарь, потому что атрибуты могут повторяться.

| Строка | Код | Что происходит | Почему так |
|---|---|---|---|
| 179 | `data = dict(attrs)` | Список атрибутов превращается в словарь | Нужен быстрый доступ по имени: `data.get("itemprop")` |
| 180 | `props = (data.get("itemprop") or "").split()` | Значение `itemprop` режется по пробелам | У одного тега может быть несколько `itemprop` |
| 181 | `self.itemprops.update(props)` | Все встреченные `itemprop` запоминаются | По ним `parse_recipe_page` понимает, что это страница рецепта |
| 182 | `classes = (data.get("class") or "").split()` | CSS-классы тоже режутся на список | Классы нужны только как запасной признак (`cooking-bl`, `article-text`) |
| 184–186 | `h1` + `name` | Открывается заголовок рецепта | Это имя блюда; счётчик `_in_name` включает сбор текста |
| 187–189 | `div` + `nutrition` | Открывается блок КБЖУ | Счётчик `_in_nutrition`; `cells` очищается для новой таблицы |
| 190–192 | `div` + `description`/`article-text` | Открывается описание | Описание бывает и через `itemprop`, и через класс |
| 193–196 | `time` + `totalTime` | Открывается время | `datetime` хранится отдельно: `PT40M` надёжнее текста «40 минут» |
| 197–199 | `span` + `recipeYield` | Открываются порции | Текст порций разбирается позже |
| 200–202 | `span` + `recipeCategory` | Открывается категория | Категории складываются в список |
| 203–205 | `li` + `recipeIngredient` | Открывается ингредиент | Обнуляется список кусочков ингредиента |
| 206–208 | `span` внутри ингредиента | Открывается часть ингредиента | В разметке имя и количество лежат в разных `span` |
| 209–215 | `li` + `cooking-bl` | Открывается шаг | Если предыдущий `li` не закрыт, он сначала сохраняется через `_flush_step()` |
| 216–219 | `img` внутри шага | Открывается картинка шага | Берётся только `itemprop="image"` и непустой `src`; URL обрезается |
| 220–223 | `td` внутри nutrition | Открывается ячейка таблицы КБЖУ | `nae-title` означает заголовок, а не число |
| 224–225 | `br` внутри шага | Перенос строки в шаге | В тексте шага нужен `\n`, а не пробел |
| 226–228 | `br` внутри ячейки | Разделитель в ячейке | «ккал<br/>2576» требует пробела, иначе число склеится с подписью |
| 229–231 | любой тег внутри шага | Вложенный тег разделяет слова | `<b>блюдо!</b> Пикантное` иначе потеряет пробел |
| 232–234 | любой тег при сборе текста | То же для остальных фрагментов | Пробел сохраняет границу слов |

Порядок `elif` важен. Например, `div` с `nutrition` и `div` с `description` — разные ветки;
если проверять их в другом порядке, можно попасть не в тот счётчик. `li` с `recipeIngredient`
должен проверяться раньше общего `li` шага.

Почему не словарь `tag -> handler`: у веток разные условия не только по тегу, но и по
`itemprop`, `class` и текущему состоянию. Словарь пришлось бы делать вложенным и с проверками
внутри значений; порядок проверок стал бы неявным.

## `handle_endtag` и `handle_data`

`handle_endtag` (236–276) — обратная операция. Он уменьшает счётчик и забирает накопленный текст
через `_take()`.

Важные строки:

- 240–241: `div` закрывает nutrition только тогда, когда не открыта ячейка;
- 248–250: `span` с `recipeYield` сохраняет текст порций;
- 256–260: закрытие `span` внутри ингредиента добавляет кусочек имени/количества;
- 261–267: закрытие `li` ингредиента собирает первый кусочек как имя, второй как количество;
- 268–269: закрытие `li` шага вызывает `_flush_step()`;
- 270–272: закрытие `ul` тоже сохраняет шаг — страховка от незакрытого `li`;
- 273–276: закрытие `td` добавляет ячейку в `cells`.

`handle_data` (278–285):

- если открыта ячейка — текст идёт в `_cell_text`;
- если открыт шаг — в `_step_text`;
- иначе, если `_capturing` — в общий `_buffer`.

Проверка ячейки стоит первой: ячейка находится внутри шага, и без отдельной ветки её текст
попал бы в шаг.

## `parse_recipe_page`

Строки 322–327: создаётся парсер, в него загружается HTML, ошибки `HTMLParser` превращаются в
`PageError`.

Строки 329–330: шаги ограничиваются `MAX_STEPS`; тексты и картинки разделяются на два кортежа.

Строки 331–334: проверки, что это вообще рецепт. Нет ни одного `itemprop` — это не страница
рецепта. Нет имени и шагов — тоже. Иначе импорт записал бы мусор.

Строки 336–349: собирается `ParsedPage`. `name or None` и `description or None` превращают
пустую строку в `NULL`, чтобы в базе не было двух видов «пусто».

## `fetch_recipe_page`

Строки 363–370: создаётся `Request` с честным `User-Agent`. Сайт блокирует анонимные запросы,
поэтому представляться ботом — часть протокола.

Строки 371–375: `opener(request, timeout=timeout)`; `timeout` передаётся именованным аргументом,
потому что второй позиционный аргумент `urlopen` — это тело запроса, а не таймаут.

Строки 376–380: читаются байты и `Content-Type`; кодировка определяется ниже. Страница
povarenok отдаётся в `windows-1251`, поэтому нельзя всегда использовать `utf-8`.

## Почему не BeautifulSoup / lxml / regex

- **BeautifulSoup/lxml** добавили бы зависимость ради одной страницы; проект обходится
  стандартным `HTMLParser`.
- **regex по HTML** ломается на вложенных тегах и порядке атрибутов.
- **JSON-LD** на этой странице нет; используется microdata.
- **selenium/браузер** избыточен: страница отдаётся обычным GET-запросом.

## Что спросит преподаватель

1. **Почему счётчики, а не флаг?** Потому что теги вложенные; флаг нельзя уменьшить корректно.
2. **Почему `handle_data` проверяет ячейку раньше шага?** Ячейка вложена в шаг, иначе её текст
   попал бы не туда.
3. **Почему `_flush_step` вызывается и на `</li>`, и на `</ul>`?** На случай сломанной страницы
   без закрывающего `li`.
4. **Что будет, если убрать `self.itemprops.update(props)`?** `parse_recipe_page` не сможет
   отличить страницу рецепта от любой другой.
5. **Почему `source_url` передаётся в `parse_recipe_page`?** Парсер не ходит в сеть; URL нужен
   только для сообщения об ошибке и поля результата.
6. **Почему тесты не ходят в интернет?** `opener` подменяется, HTML берётся из
   `tests/data/pages`; иначе тест зависел бы от сайта.
