# Разбор ингредиентов: `backend/app/importer/povarenok.py`

## Зачем нужен этот код

Датасет povarenok хранит ингредиенты в колонке `ingredients`. В одном файле это словарь, в CSV —
строка с Python-литералом, в старом дампе — список строк. Функция `parse_ingredients` приводит все
формы к одному виду: кортежу `Ingredient(name, quantity)`.

## `Ingredient`

Строки 78–83:

```python
@dataclass(frozen=True)
class Ingredient:
    name: str
    quantity: str | None
```

`quantity` допускает `None`: «Соль» без количества — нормальный ингредиент.
`frozen=True` не даёт случайно изменить ингредиент после создания.

## `_ingredients_from_pairs`

Строки 333–346:

| Строки | Что | Почему |
|---|---|---|
| 337 | Перебор пар | Каждая пара — «имя, количество» |
| 338 | `normalize_ingredient_name` | Убирает лишние пробелы и пунктуацию |
| 339 | Проверка пустого/длинного имени | PostgreSQL не примет слишком длинное имя |
| 341–344 | `casefold()` и `seen` | «Мука» и «мука» — один ингредиент; в БД есть UNIQUE |
| 345 | `_normalize_quantity` | Количество приводится к строке или `None` |

Почему дедупликация здесь, а не в SQL: разные форматы могут дать дубли до вставки; лучше
отфильтровать один раз в памяти.

## `_normalize_quantity`

Строки 349–354:

- `NaN` превращается в `None`;
- текст нормализуется;
- пустая строка превращается в `None`;
- длина обрезается по `MAX_QUANTITY_LENGTH`.

Почему не хранить `""`: в базе `quantity_text` nullable; `None` — один способ сказать «нет
количества», а не два.

## `_split_lines` и `_split_line`

Строки 357–368:

- `_split_lines` режет текст по строкам и `;`;
- `_split_line` делит по первому `:`.

`partition(":")` возвращает три части и не падает, если двоеточия нет. Если разделителя нет,
возвращается `(line, None)`. Это проще, чем `split(":", 1)` с проверкой длины списка.

## `_decode_literal`

Строки 371–387 — важный компромисс:

1. Если строка не начинается с `{` или `[`, это не литерал.
2. Сначала `json.loads`.
3. Если не JSON — `ast.literal_eval`.

Почему `ast.literal_eval`, а не `eval`: `eval` выполнит любой код из файла, а `literal_eval`
принимает только литералы. CSV от pandas содержит одинарные кавычки и `None`, поэтому JSON не
подходит.

## Почему не pandas / regex

- pandas уже используется для parquet, но превращать весь импорт в pandas ради одной колонки
  избыточно;
- regex по словарю/списку хуже переживает вложенные кавычки;
- `eval` опасен;
- `json.loads` не понимает Python-литералы.

## Что спросит преподаватель

1. Почему `None` и `NaN` обрабатываются отдельно? — это разные представления пустоты из разных
   форматов.
2. Почему `Mapping`, а не `dict`? — CSV/pandas может дать другой mapping-совместимый объект.
3. Почему `casefold`, а не `lower`? — корректнее для Unicode.
4. Почему пустой список возвращается, а не `None`? — функция всегда возвращает кортеж; пустой
   кортеж — нормальное значение.
5. Почему неизвестный тип не вызывает ошибку? — импорт не должен падать на одной плохой строке.
