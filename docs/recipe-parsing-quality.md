# Качество парсинга: первые 500 рецептов

Проверка 27.11.2026 на локальной PostgreSQL 15. Цель — не полный каталог, а проверка
пайплайна на реальных данных: импорт датасета, скачивание страниц, заполнение шагов,
порций, времени и КБЖУ.

## Что запускали

```bash
# база
docker compose up -d db

# датасет (файл не коммитится)
cd backend
python -m app.importer --download --destination data/povarenok

# импорт первых 500 рецептов
python -m app.importer --dataset data/povarenok --limit 500 --batch-size 500

# обогащение страниц
python -m app.importer --enrich --limit 500 --delay 1.0
```

Датасет — `povarenok_recipes_2021_06_16.csv`, около 56 МБ. После импорта в базе:

- **500 рецептов**;
- **4 392 ингредиента**;
- у всех 500 рецептов есть `source_url`.

## Что показала выборка

- Пайплайн работает end-to-end: импорт → скачивание → разбор → запись в БД.
- Ошибок на 500 страницах нет; это хороший результат для первого прогона.
- КБЖУ есть почти везде, шаги — у четырёх из пяти рецептов.
- Время и порции отсутствуют чаще, потому что сами страницы их не публикуют; это не ошибка
  парсера.
- У 105 рецептов нет шагов. На примере `https://www.povarenok.ru/recipes/show/96774/`
  в сохранённом HTML есть ингредиенты, но нет `itemprop="recipeInstructions"` и блока
  `cooking-bl`. Парсер не выдумывает шаги — это правильно.
- Кэш 500 страниц занимает около **183 МБ**. Полный обход 147 тысяч страниц даст десятки
  гигабайт и займёт много часов, поэтому для следующих прогонов нужна выборка и
  приоритизация.
- Количества ингредиентов хранятся и текстом (`250 мл`, `3 шт`, `1 кг`), и в
  нормализованном виде: `quantity_value` + `quantity_unit`. Масса приводится к граммам,
  объём — к миллилитрам, штуки и ложки остаются в исходных единицах. «По вкусу» и
  диапазоны (`200–300 г`) не превращаются в одно число.

## Расширение до 12 000 рецептов

После проверки первых 500 рецептов импорт был расширен до 12 000 строк датасета:

- **12 000 рецептов** в базе;
- **105 087 ингредиентов**;
- **85 910** ингредиентов получили `quantity_value`/`quantity_unit` (81,75 %);
- 13 928 записей не имеют количества в источнике;
- остальные записи с текстом не нормализованы: это «по вкусу», диапазоны вроде
  `200–300 г` и другие нечисловые формы;
- обогащение страниц по-прежнему выполнено для первых 500 рецептов; остальные
  используются для обучения по ингредиентам.

## TF-IDF на реальном каталоге

Модель обучена командой:

```bash
python -m app.ml.model --from-db --limit 12000
```

Результат: **11 998 документов**, **778 лемм** в словаре, артефакт
`backend/app/ml/artifacts/v1.json` (не коммитится).

Честный split, BM25, co-occurrence и гибридный ранкер описаны отдельно:
[`docs/recommendation-ranking.md`](recommendation-ranking.md). На test-выборке
гибрид дал P@10 0,430, Hit@10 0,822 и MRR@10 0,565.

## Вывод

Выборка из 500 рецептов подтверждает, что парсер пригоден для наполнения базы. Для оценки
модели на реальных данных этого мало: нужен следующий прогон на 2–5 тысячах рецептов, а
полный каталог — отдельная фоновая задача с ограничением по диску и сетевой вежливости.

## Следующие шаги

1. Прогнать 2–5 тысяч рецептов и сравнить долю шагов, порций и КБЖУ с этой выборкой.
2. Обучить TF-IDF на полученном каталоге и измерить метрики на validation-выборке.
3. Для рецептов без `servings` оставить явный запрос базового количества порций, а не
   придумывать значение.
4. При необходимости использовать `quantity_value`/`quantity_unit` в API и пересчёте
   порций.
