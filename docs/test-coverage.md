# Покрытие тестами и соответствие ГОСТ

Документ отвечает на два вопроса: **сколько кода реально проверено тестами** и **насколько
тестовая документация проекта соответствует российским стандартам** (ГОСТ Р 56920/56921/56922-2016,
ГОСТ 34.603-92, ГОСТ 19.301-79, ГОСТ Р ИСО/МЭК 25010-2015). Он дополняет `TEST-CHECKLIST.md`
(что именно проверяет каждый кейс) и `TASKS-REPORT.md` (что сделано по задачам).

Все числа ниже **измерены**, а не взяты из головы:
- бэкенд — прогон 12.11.2026 на ветке `feat/recipe-pages`: 151 кейс против PostgreSQL 15
  (контейнер Docker, база `recipes_test`), `coverage.py` 7.5.3, Python 3.12 локально / 3.11 в CI;
- фронтенд — прогон 13.11.2026 на ветке `test/frontend-coverage`: 29 кейсов, Vitest 5.1.0 +
  `@vitest/coverage-v8` 5.1.0, jsdom, Node 26 локально / 22 в CI.

## 1. Как воспроизвести

```bash
cd backend
pip install -r requirements-dev.txt                     # pytest, coverage, black, ruff + контрактные либы

# полный набор с базой (тот же прогон, что делает CI)
TEST_DATABASE_URL=postgresql://postgres:changeme@localhost:5432/mydatabase \
  coverage run -m pytest && coverage report

# только быстрые кейсы без базы (80 из 151)
python -m pytest
```

Фронтенд — отдельный набор и отдельные команды (Node >= 22.12):

```bash
cd frontend
npm ci
npm run test:run        # 29 кейсов, Vitest + Testing Library
npm run test:coverage   # то же под покрытием и с порогом 80 %
npm run typecheck && npm run lint && npm run format:check && npm run build
```

Настройки живут в `backend/pyproject.toml`: `[tool.coverage.run]` (`source = ["app"]`,
`branch = true`) и `[tool.coverage.report]` (`fail_under = 80`, `show_missing = true`).
`source = app` значит, что в метрику попадает только код приложения — тесты, `conftest.py`,
`main.py` и `worker.py` её не разбавляют. Порог 80 % проверяется и в CI: шаг
«Run the test suite with coverage» в `.github/workflows/backend-tests.yml` падает, если покрытие
просело.

| Модуль | Строки | Причина | Что делать |

## 8. Чего не хватает для полного соответствия

1. **ПМИ по форме ГОСТ 19.301-79** — содержание есть (раздел 6), но нет титульного листа,
   обозначения программы и подписей. Нужно, если проект сдаётся по ЕСПД.
2. **Протокол и акт приёмочных испытаний по ГОСТ 34.603-92** — критерии есть, оформления нет.
3. **Политика тестирования отдельным документом** — сейчас это разделы `CONTRIBUTION.md`.
4. **Отчёт об инциденте** — нет шаблона issue «шаги → ожидание → факт → кейс», поэтому связь
   дефекта с тестом держится в голове, а не в трекере.
5. **Производительность (25010)** — нет нагрузочных тестов; для рекомендаций достаточно замерить
   p95 `GET /recommend_recipes` на каталоге 147 тыс. рецептов.
6. **Тесты восстановления** — нет кейса «база пропала во время запроса» (сейчас проверяется
   только `/ready`).
7. **Два нуля покрытия** — `app/migrate.py` (нужен кейс на чистой базе) и
   `app/models/fridge_history.py` (мёртвый код, удалить).
8. **Трассировка «требование → тест»** — таблицы в `TEST-CHECKLIST.md` ведутся вручную.
9. **E2E-тесты клиента** — нет Playwright/Cypress: до появления API-клиента (спринт 4) нечего
   прогонять сквозь реальный сервер; сейчас системные сценарии идут в `MemoryRouter` без сети.
10. **Автоматическая доступность и визуальная регрессия** — нет `axe-core` и скриншот-тестов;
    доступность подтверждается разметкой и ручной проверкой, внешний вид — сверкой с макетами.
11. **Кросс-браузерность и производительность клиента** — проверены только Firefox (скриншоты) и
    jsdom; замеров LCP/INP и тестов в Chrome/Safari нет.
12. **Покрытие фронтенда 100 % не равно «UI проверен»** — метрика считается по TS/TSX; CSS,
    визуал, доступность и браузерное поведение в неё не входят (см. 2.11).
