# Руководство по стилю команды Recepie-book

Версия 1.0. Практическая работа № 3.

Это не учебник по Python и не попытка переписать `CONTRIBUTION.md`. Наоборот: `CONTRIBUTION.md`
остаётся коротким сводом правил команды, а этот документ показывает, **как эти правила выглядят
в нашем коде**. Здесь есть примеры из `main`, команды проверки и места, где правило можно
нарушить без вреда для проекта.

Мы пишем на Python 3.11 (Flask, PostgreSQL, psycopg2) и на React 19 + TypeScript. Поэтому одни
разделы касаются в основном бэкенда, другие — фронтенда, но общие принципы у них одинаковые:
код должен быть понятным, проверяемым и безопасным.

## Как пользоваться документом

1. Перед началом задачи откройте раздел, который относится к вашей работе.
2. Перед PR прогоните автоматические проверки из раздела 10.
3. На code review не спорьте о форматировании: если вопрос стиля уже описан здесь, дайте ссылку
   на пункт. Если правила нет — предложите его добавить отдельным PR.
4. Если правило мешает в конкретной задаче, это нормально. Напишите причину в PR и создайте
   issue с меткой `tech-debt`, а не обходите правило молча.

Главный принцип: **руководство должно экономить время, а не создавать ещё один повод для
споров**. Если две реализации одинаково хороши, выбираем ту, которая проще объясняется и легче
тестируется.

## 1. Стандарты стиля, условия, DRY/KISS и работа с базой

**Вариант 1, ответственный — Волков Михаил.**

### 1.1. Форматирование

Python оформляется `black` с длиной строки 100 символов, линтер — `ruff`. Мы не выравниваем
код вручную и не спорим о пробелах: это делает инструмент. Если `black` и `ruff` расходятся,
побеждает настройка проекта в `backend/pyproject.toml`.

Исключения бывают только для длинных строк в документации и для URL. В таком случае лучше
перенести строку, а не отключать линтер на весь файл.

### 1.2. Условия и логические операторы

Мы стараемся писать условия так, чтобы их можно было прочитать вслух. Ранний возврат лучше
глубокой вложенности: читатель видит причину выхода и не держит в голове пять уровней `if`.

```python
# Хорошо: проверка причины и ранний выход
def add_items(db, payload: list) -> dict:
    if not payload:
        raise BadRequest("Request body must contain at least one fridge item")
    if len(payload) > MAX_BATCH_SIZE:
        raise BadRequest(f"Request body must contain at most {MAX_BATCH_SIZE} items")
    ...
```

```python
# Плохо: условие-лестница, в которой легко потерять основной путь
if payload:
    if len(payload) <= MAX_BATCH_SIZE:
        ...
    else:
        raise BadRequest(...)
else:
    raise BadRequest(...)
```

Для булевых значений используем имена, которые читаются как утверждение: `is_configured`,
`has_access`, `can_retry`. Не называем флаг `flag` или `status`, если он означает «готово ли»
или «есть ли право».

Сложное условие разбиваем на именованные части:

```python
# Плохо
if user and user["id"] and not user["deleted"] and user["role"] in ("admin", "owner"):
    ...

# Хорошо
is_active_user = user and user["id"] and not user["deleted"]
can_manage = is_active_user and user["role"] in {"admin", "owner"}
if can_manage:
    ...
```


### 1.3. DRY и KISS

DRY не означает «вынести любые две строки в функцию». Мы выносим повторяющееся **правило**, а не
случайное совпадение. Например, проверка строки, числа и даты уже живёт в
`backend/app/validation.py`: не нужно копировать её в каждый сервис.

```python
# backend/app/services/fridge_service.py
def _validated_item(raw: object, index: int) -> dict:
    if not isinstance(raw, dict):
        raise BadRequest(f"Item #{index} must be a JSON object")
    return {
        "user_id": require_positive_int(raw, "user_id"),
        "product_name": require_string(raw, "product_name", max_length=MAX_PRODUCT_NAME_LENGTH),
        "expiration_date": require_date(raw, "expiration_date"),
        "quantity": require_positive_int(raw, "quantity"),
    }
```

KISS — это когда функция делает одну понятную вещь. `list_items` получает страницу и сериализует
её, `add_items` валидирует пачку и вставляет, `delete_expired_products` удаляет просроченное.
Если функция начинает одновременно проверять права, ходить в базу, форматировать ответ и писать
письмо пользователю — её пора делить.

### 1.4. База данных

Правила жёсткие:

- SQL — только с параметрами `%s`. Никакой конкатенации строк и f-строк с пользовательскими
  данными.
- Соединение и курсор — через контекстный менеджер `Database.cursor()`. Он делает `commit` при
  успехе и `rollback` при ошибке.
- Схема меняется только миграцией, а не «вручную на проде».
- Списки отдаются страницами; `LIMIT` и `OFFSET` приходят из проверенных констант.
- Ограничения (`NOT NULL`, `UNIQUE`, `CHECK`, внешние ключи) живут в PostgreSQL, а не только в
  Python.

```python
# backend/app/db.py — один вход в транзакцию для всех запросов
@contextmanager
def cursor(self):
    ...
    try:
        with connection.cursor(cursor_factory=RealDictCursor) as cur:
            yield cur
        connection.commit()
    except psycopg2.Error:
        self._safe_rollback(connection)
        raise
```

Проверка: `ruff check .`, `black --check .`, `pytest`.

## 2. Имена, модульность, SOLID и внешние API

**Вариант 2 — только в руководстве и дизайн-плане; отдельного кодового PR нет.**

### 2.1. Имена

Имя должно отвечать на вопрос «что это?», а не «какого оно типа?». `recipe_id` лучше, чем
`rid`; `expiration_date` лучше, чем `date`; `fridge_products` лучше, чем `items`, если рядом есть
ещё несколько списков.

Функции называем глаголом: `list_items`, `add_items`, `delete_expired_products`. Предикаты —
через `is_`, `has_`, `can_`. Классы — существительным: `Database`, `InMemoryRateLimiter`.

Не боимся длины в 20–30 символов, если имя стало точным. Сокращения допустимы только
общепринятые (`db`, `id`, `url`, `api`).

### 2.2. Модули и слои

У нас уже есть разделение, и его надо сохранять:

```text
api/        — HTTP: разобрать запрос, вызвать сервис, вернуть JSON
services/   — бизнес-логика: правила, проверки, сценарии
models/     — SQL и работа с таблицами
validation.py — проверка входа
ml/         — рекомендации, векторы, аллергены
```

Роут не должен содержать SQL. Сервис не должен знать про `request` и `jsonify`. Модель не должна
решать, можно ли пользователю удалять чужой продукт. Если правило нарушается, его видно по
импортам: например, `from flask import request` в `models/` — тревожный сигнал.

```python
# backend/app/api/timers.py — тонкий роут
@bp.post("/timers")
@token_required
def start_timer() -> tuple:
    payload = json_object_body()
    return jsonify(timer_service.start_timer(get_db(), current_user_id(), payload)), 201
```

### 2.3. SOLID на практике

Мы не тащим в проект учебные классы ради слова SOLID. Но три принципа реально помогают:

- **SRP** — одна причина для изменения. `Database` отвечает за соединения, `fridge_service` — за
  правила холодильника, `serializers` — за преобразование строк в JSON.
- **DIP** — зависимости приходят снаружи. `recommend_safe_recipes` получает `settings`, `model` и
  `ingredient_names`, а не создаёт их внутри.
- **OCP** — новый тип ошибки или новый источник данных добавляется отдельным классом/функцией, а
  не правкой десяти `if`.

Если функция `recommend_safe_recipes` одновременно готовит выборку, фильтрует аллергены, считает
скоринг, собирает статистику и пишет лог, это кандидат на разделение. Сначала обсуждаем границы,
потом рефакторим.

### 2.4. Внешние API

Внешний сервис — это всегда риск: сеть, таймаут, чужие ошибки, смена формата. Поэтому:

- адрес и параметры — в константах;
- секреты — только из переменных окружения;
- таймаут обязателен;
- HTTP-вызов прячем за адаптером, чтобы тесты не ходили в сеть;
- ответ проверяем, а не верим, что там всегда ожидаемый JSON.

```python
# backend/app/importer/source.py
def download_dataset(..., opener: Opener = urlopen) -> Path:
    """... ``opener`` is injectable so that the unpacking logic is tested without network."""
    ...
    with opener(request, timeout) as response, archive.open("wb") as output:
        shutil.copyfileobj(response, output, length=CHUNK_SIZE)
```

Проверка: `ruff`, `black`, `pytest`, тесты импортёра без сети.


## 3. Форматирование, компоненты, зависимости и поддержка

**Вариант 3 — только в руководстве и дизайн-плане; отдельного кодового PR нет.**

### 3.1. Форматирование и переносы

Фронтенд форматирует Prettier: ширина 100, одинарные кавычки, точки с запятой, trailing comma.
Это записано в `frontend/.prettierrc.json`; руками не выравниваем.

```json
{
  "printWidth": 100,
  "singleQuote": true,
  "trailingComma": "all",
  "semi": true
}
```

Длинные цепочки вызовов и пропсов переносим по смыслу, а не «чтобы влезло». Если JSX-блок стал
нечитаемым, это повод вынести часть в компонент, а не уменьшить шрифт.

### 3.2. Один компонент — одна ответственность

Компонент может быть большим, но у него должна быть одна причина для изменения. `TextField`
отвечает за label и input, `PasswordField` — за переключение видимости пароля, страница
`LoginPage` — за композицию экрана. Это хорошее разделение: `PasswordField` не знает, куда
отправляется форма, а `TextField` не знает, что в нём пароль.

```tsx
// frontend/src/components/ui/PasswordField.tsx
export default function PasswordField({ label, id, ...rest }: PasswordFieldProps) {
  const [visible, setVisible] = useState(false);

  return (
    <TextField
      label={label}
      id={id}
      type={visible ? 'text' : 'password'}
      trailing={<button type="button" ... aria-pressed={visible}>...</button>}
      {...rest}
    />
  );
}
```

Если компонент одновременно грузит данные, форматирует дату, рисует таблицу и показывает модалку,
его нужно делить. Исключение — маленькая страница-композиция, где все части всё равно остаются
отдельными компонентами.

### 3.3. Зависимости и версии

- Все зависимости фиксируются в `package-lock.json`; `npm ci` — обязателен в CI и Docker.
- Версия Node указана в `package.json` (`engines.node`) и в `frontend/Dockerfile`. Менять её
  можно только вместе с проверкой сборки.
- Новую библиотеку добавляем, если она решает задачу лучше стандартной и не тянет пол-интернета.
  Для одной иконки или одной функции зависимость не нужна.
- Обновление зависимостей — отдельный PR, а не «заодно» с фичей.
- Удалённый код удаляем, а не комментируем: git всё помнит.

```json
"engines": { "node": ">=22.12" },
"scripts": {
  "typecheck": "tsc -b",
  "lint": "eslint .",
  "format:check": "prettier --check ."
}
```

### 3.4. Поддержка после выпуска

Мы считаем код поддерживаемым, если новый человек может:

1. найти точку входа;
2. запустить проект по README;
3. понять, где менять поведение;
4. прогнать тесты;
5. увидеть, что изменилось в API.

Для этого README и `docs/` обновляются в том же PR, где меняется поведение. Старые инструкции
не оставляем «на всякий случай»: они вводят в заблуждение.

Проверка: `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm run build`.

## 4. Комментарии, типы, конкурентность и рефакторинг

**Вариант 4, ответственный — Тропина Елизавета.**

### 4.1. Комментарии

Комментарий объясняет **почему**, а не пересказывает код. Если из строки и так понятно, что она
делает, комментарий не нужен.

```python
# Хорошо: объясняет неочевидное решение
# A dummy hash keeps the response time of a failed login close to a successful one.
DUMMY_PASSWORD_HASH = generate_password_hash("timing-safety-placeholder-password")

# Плохо: пересказ кода
# Увеличиваем счётчик на 1
counter += 1
```

Docstring обязателен для публичных функций и классов. В нём — назначение, вход, выход и
исключения. Комментарии к временным решениям должны содержать ссылку на issue или срок, когда
их можно удалить.

### 4.2. Типы и проверка ввода

Python-аннотации помогают читать код, но не заменяют проверку данных на границе. Данные из
HTTP, CLI и базы проверяются явно: тип, длина, диапазон, формат даты. Для этого есть
`backend/app/validation.py`.

```python
def require_string(data: dict, field: str, *, max_length: int = MAX_SHORT_FIELD_LENGTH) -> str:
    value = data.get(field)
    if value is None:
        raise BadRequest(f"Field '{field}' is required")
    if not isinstance(value, str):
        raise BadRequest(f"Field '{field}' must be a string")
    ...
```

На фронтенде включён `strict`; `any` не используем. Неизвестный JSON — `unknown` плюс явная
проверка. Props компонентов описываем интерфейсом, а не `object`.

### 4.3. Конкурентность и многопоточность

В Flask приложении один процесс может обслуживать несколько потоков, а `gunicorn` запускает
несколько процессов. Поэтому:

- одно соединение psycopg2 не передаём между потоками;
- используем `ThreadedConnectionPool` и всегда возвращаем соединение в пул;
- общее изменяемое состояние защищаем блокировкой;
- не храним пользовательские данные в глобальных переменных;
- фоновая задача не должна запускаться внутри HTTP-запроса.

```python
# backend/app/security.py — состояние rate limiter общее для потоков процесса
self._lock = threading.Lock()

def check(self, key: str) -> None:
    with self._lock:
        hits = self._hits.setdefault(key, deque())
        ...
```

Важно помнить: `InMemoryRateLimiter` работает в пределах одного процесса. При нескольких
gunicorn-воркерах это не общий лимит; если нужен общий — хранить счётчики в Redis/PostgreSQL.

### 4.4. Рефакторинг

Рефакторинг — это изменение структуры без изменения поведения. Поэтому:

1. сначала тесты, фиксирующие текущее поведение;
2. маленькие шаги, после каждого — зелёный прогон;
3. отдельный PR, не смешанный с фичей;
4. если по пути нашлась ошибка — сначала исправляем её отдельно, потом рефакторим.

Не «улучшаем всё сразу». Один PR — одна причина изменения.

Проверка: `pytest`, `ruff`, `black`, а для фронтенда — `npm run typecheck` и `npm run test:coverage`.


## 5. Структура проекта, документация API, async и ошибки

**Вариант 5, ответственный — Савчук Иван.**

### 5.1. Единая структура

Структура проекта — часть интерфейса для разработчика. Если файл лежит не там, где его ищут,
человек тратит время. Поэтому:

- `backend/app/api/` — только HTTP-слой;
- `backend/app/services/` — сценарии;
- `backend/app/models/` — SQL;
- `backend/app/validation.py` — проверки входа;
- `backend/app/serializers.py` — преобразование строк в JSON;
- `frontend/src/pages/` — экраны;
- `frontend/src/components/` — переиспользуемые части;
- `frontend/src/app/` — маршруты и общие настройки;
- `docs/` — объяснения, почему код устроен именно так.

Новый модуль появляется в существующем слое. Если для него нет места — сначала обсуждаем
структуру, потом создаём папку.

### 5.2. Документация API

`openapi.yaml` — источник истины. Если меняется адрес, тело или код ответа, контракт меняется в
том же PR. Контрактные тесты проверяют, что файл валиден, что маршруты совпадают с приложением и
что реальные ответы соответствуют схемам.

Правила:

- у каждого адреса описаны успешный ответ и ошибки;
- даты — ISO 8601, поля — `snake_case`;
- ошибка — `{"error": "..."}` согласно `components.schemas.Error`;
- пароли и токены в примерах не похожи на настоящие;
- breaking change требует новой версии или отдельного обсуждения.

### 5.3. Асинхронные операции и события

Flask у нас синхронный. Это значит, что долгая операция внутри запроса блокирует worker.
Тяжёлые вещи (импорт датасета, обучение модели, массовая рассылка) выносим в CLI или отдельный
процесс, а не запускаем в обработчике.

На фронтенде любая сетевая операция — это `Promise`. Поэтому:

- `async/await` вместо цепочки `.then()` там, где важна последовательность;
- ошибка `fetch` не должна теряться: показываем сообщение и даём повторить;
- отменяем запрос через `AbortController`, если компонент размонтирован;
- не запускаем `fetch` на каждом рендере без зависимости;
- loading/error/success — три разных состояния, а не один `isLoading`.

```ts
// пример для клиентского API-слоя, который появится в спринте 4
try {
  const items = await listFridgeItems(token, signal);
  setItems(items);
} catch (cause) {
  if (!signal.aborted) {
    setError('Не удалось загрузить холодильник');
  }
}
```

### 5.4. Ошибки и логи

Клиент не должен видеть traceback. Внутри приложения используем `ApiError` и его наследников:
`BadRequest`, `Unauthorized`, `NotFound`, `TooManyRequests`, `DatabaseUnavailable`. Обработчик
превращает их в единый JSON.

```python
# backend/app/errors.py
class ApiError(Exception):
    status_code = 400
    default_message = "Bad request"

    def __init__(self, message: str | None = None, status_code: int | None = None) -> None:
        self.message = message or self.default_message
        ...
```

В логах:

- `INFO` — важные события и отклонённые запросы;
- `WARNING` — подозрительное, но не падение;
- `ERROR` — ошибка, которую нужно разбирать;
- никогда не логируем пароли, токены, содержимое личных писем.

`print()` в приложении запрещён: используем `logging`.

Проверка: `pytest test_openapi_contract.py`, `ruff`, `black`.

## 6. Ошибки, стандартные библиотеки, паттерны и Git

**Вариант 6, ответственный — Журавлев Владислав.**

### 6.1. Обработка ошибок

Ловим конкретные исключения. `except Exception` допустим только на внешней границе приложения,
где мы логируем и превращаем ошибку в 500. Во внутреннем коде он скрывает баги.

```python
try:
    inserted = fridge_model.insert_items(db, items)
except pg_errors.ForeignKeyViolation as exc:
    logger.info("Fridge item batch rejected: unknown user_id")
    raise BadRequest("Unknown user_id in the batch") from exc
```

`except: pass` запрещён. Если ошибку можно обработать — обрабатываем; если нет — пробрасываем
выше с контекстом (`raise ... from exc`).

### 6.2. Стандартные библиотеки и инструменты

Сначала смотрим на стандартную библиотеку и уже выбранный стек. Не тащим новую зависимость,
если задача решается `pathlib`, `json`, `datetime`, `urllib`, `argparse`.

Инструменты проекта:

- Python: `black`, `ruff`, `pytest`, `coverage.py`;
- Frontend: `prettier`, `eslint`, `tsc`, `vitest`;
- CI: GitHub Actions;
- контракт: `openapi-spec-validator`.

Версии фиксируем в `requirements*.txt`, `package.json` и lock-файлах. Обновление — отдельным PR.

### 6.3. Паттерны проектирования

Паттерн нужен, когда он убирает повторение или делает границу явной, а не для красоты.

В проекте уже есть:

- **Фабрика** — `create_app()` в `backend/app/__init__.py`;
- **Blueprint** — отдельный модуль на область API;
- **Repository / Gateway** — модели и `Database` скрывают SQL;
- **Decorator** — `@token_required`, `@rate_limit`;
- **Strategy** — выбор backend векторизации (SBERT, TF-IDF, sparse);
- **Adapter** — `opener` в `importer/source.py`.

Если появляется новый паттерн, в PR нужно объяснить, какую проблему он решает. «Так пишут в
книге» — не объяснение.

### 6.4. Git

- Одна задача — одна ветка — один PR.
- Ветки: `feat/...`, `fix/...`, `docs/...`, `test/...`, `refactor/...`.
- Коммиты — Conventional Commits: `feat(fridge): add protected endpoints`.
- В `main` не force-push.
- PR описывает: что сделано, зачем, как проверить, какие риски.
- Перед merge — зелёный CI и approval.
- История должна быть читаемой: не смешиваем форматирование, фичу и рефакторинг в одном PR.

Проверка: `git status`, CI, `pytest`.


## 7. Вложенность, безопасность, документация и контейнеры

**Вариант 7, ответственный — Потапов Артем.**

### 7.1. Вложенность и цепочки вызовов

Стараемся не уходить глубже трёх уровней. Если появляется четвёртый — выносим часть в функцию
или используем ранний возврат.

```python
# Плохо
if user:
    if user.is_active:
        if user.has_permission:
            if not item.deleted:
                do_something()

# Хорошо
if not user or not user.is_active:
    return
if not user.has_permission or item.deleted:
    return
do_something()
```

Длинные цепочки `a.b().c().d()` тоже разбиваем на промежуточные переменные: так видно, где
именно произошёл сбой и что означает каждый шаг.

### 7.2. Безопасность

Базовые правила проекта:

- пароли — только scrypt-хеш (`werkzeug.security`), никогда не хранить и не логировать открытый
  пароль;
- JWT подписывается секретом из окружения, алгоритм — только из настроек;
- `user_id` берётся из токена, а не из тела запроса;
- SQL — только параметризованный;
- CORS ограничен известными origin;
- `/login` и `/register` защищены rate limit;
- секреты не попадают в git, образы и логи;
- `debug=True` — только локально.

```python
# backend/app/security.py
try:
    claims = decode_access_token(token)
    user_id = int(claims["sub"])
except (jwt.InvalidTokenError, KeyError, TypeError, ValueError) as exc:
    logger.info("Rejected token: %s", type(exc).__name__)
    raise Unauthorized("Authorization token is invalid or expired") from exc
```

Пароли не шифруем обратимо: это хеширование, а не шифрование. Для внешних интеграций, где нужен
асимметричный ключ, используем проверенную библиотеку и не пишем свою криптографию.

### 7.3. Документация

Документация делится на три уровня:

1. **README** — как запустить и что уже работает.
2. **docs/** — почему решение устроено именно так, ограничения, команды проверки.
3. **Docstring/комментарии** — конкретная функция и неочевидное решение.

Документация обновляется в том же PR, что и код. Если поведение изменилось, а README остался
старым — это баг.

### 7.4. Контейнеры

- Образы фиксируем по версии; `latest` допустим только для локального Swagger UI, но и его лучше
  зафиксировать.
- Backend собирается multi-stage; в финальном образе нет компилятора и кэша pip.
- Контейнер не работает от root.
- У backend есть `HEALTHCHECK`.
- Секреты передаются через env, а не запекаются в слой.
- `docker compose` — для разработки; production-конфигурация не должна монтировать исходники и
  запускать dev-сервер.

```dockerfile
# backend/Dockerfile
RUN groupadd --gid 10001 app && useradd --uid 10001 --gid app --create-home app
...
USER app
HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
    CMD python -c "..."
```

Проверка: `docker compose config`, `docker build`, `hadolint` — если он есть в окружении.


## 8. Тесты, локализация, UX и криптография

**Вариант 8, ответственный — Мокрецов Егор.**

### 8.1. Тесты

Тесты — часть кода, а не «после проекта». Минимальный набор:

- на каждый новый эндпоинт — успешный и неуспешный кейс;
- на авторизацию — запрос без токена, с чужим токеном, с истёкшим токеном;
- на фронтенде — поведение через роль и доступное имя, а не через CSS-класс;
- на баг — тест, который воспроизводит баг до исправления.

```python
def test_add_fridge_items_validates_the_payload(db_client):
    response = db_client.post("/fridge_items", json={})
    assert response.status_code == 400
```

Не тестируем реализацию ради покрытия. 100 % строк при отсутствии проверки поведения — плохой
результат. Порог проекта — 80 % по statements/branches/functions/lines, но важнее сами сценарии.

### 8.2. Локализация

Сейчас интерфейс на русском, а сообщения API — на английском. Это осознанное решение:
разработчик читает API-ошибки, пользователь — UI. Не смешиваем языки в одном слое.

Правила:

- текст интерфейса хранится в одном месте, а не раскидан по компонентам;
- даты и числа форматируются через `Intl` или явный формат, а не `toString()`;
- плейсхолдеры и `aria-label` тоже переводятся;
- API возвращает стабильные коды/сообщения, а UI решает, как их показать.

### 8.3. UX и доступность

- У каждого поля — настоящий `<label for="...">`.
- Кнопка — `<button>`, ссылка — `<a>`/`<Link>`; не наоборот.
- Фокус видим, Tab работает, модалка закрывается с клавиатуры.
- Ошибка формы объявляется через `role="alert"`, а не только цветом.
- Контраст и размеры берутся из `docs/design-system.md`.
- Состояние кнопки (`disabled`, `aria-pressed`) отражает реальное поведение.

```tsx
<button
  type="button"
  aria-label={visible ? 'Скрыть пароль' : 'Показать пароль'}
  aria-pressed={visible}
>
```

### 8.4. Криптография

- Пароли — `scrypt`/`werkzeug`, не MD5/SHA1 и не «свой» алгоритм.
- JWT — HS256 с секретом из env; в проде секрет длинный и случайный.
- Симметричное шифрование — только для данных, которые нужно расшифровать; пароли к ним не
  относятся.
- Асимметричное шифрование — для внешних интеграций и обмена ключами, через проверенную
  библиотеку.
- TLS завершается на прокси; приложение не изобретает свой протокол.

Проверка: `pytest`, `npm run test:coverage`, `ruff`, `black`, `tsc`.

## 9. Производительность, межплатформенность, auth и async API

**Вариант 9 — только в руководстве и дизайн-плане; отдельного кодового PR нет.**

### 9.1. Производительность

Сначала измеряем, потом оптимизируем. Основные правила:

- списки — с пагинацией, а не «отдать всё»;
- в SQL — только нужные колонки и индексы под фильтры;
- не делаем запрос в цикле, если можно один запрос с `JOIN`/`IN`;
- соединения — из пула, а не новое на каждый запрос;
- тяжёлые вычисления — вне HTTP-запроса;
- кэш — только там, где есть доказанная польза и понятная инвалидация.

```python
# backend/app/api/timers.py — сервер хранит дедлайн, клиент не пересчитывает его по своим часам
@bp.get("/timers/active")
@token_required
def active_timers() -> tuple:
    return jsonify(timer_service.active_timers(get_db(), current_user_id())), 200
```

В ML-части `vectorizer` использует разреженные словари для bag-of-lemmas: это дешевле плотной
матрицы и достаточно для текущего объёма. Не меняем алгоритм на «модный», пока метрики не
показали пользу.

### 9.2. Межплатформенность и совместимость

- Python и Node фиксируются в Docker и CI.
- Пути — через `pathlib`/`Path`, не через `\` вручную.
- Кодировка — UTF-8; файлы читаются с явной кодировкой.
- Даты в API — ISO 8601 с таймзоной; в БД — `timestamptz` там, где важно время.
- JSON — `snake_case`; фронтенд не переименовывает поля «по-своему».
- Внешний формат (CSV/JSON/HTML) проверяется на границе и не протекает во внутренние модели.

### 9.3. Авторизация и аутентификация

- Токен передаётся в `Authorization: Bearer <token>`.
- TTL токена ограничен настройками.
- Владелец ресурса всегда берётся из токена, а не из тела.
- 401 — нет/просрочен токен; 403 — токен есть, но прав нет; 404 — чужой ресурс, если не хотим
  раскрывать его существование.
- Пароли — только хеш; секреты — только env.
- Rate limit обязателен для логина и регистрации.

### 9.4. Асинхронные API и реальное время

- В Flask нет фонового выполнения «из коробки»; для долгих задач — отдельный процесс/CLI.
- Таймеры хранят абсолютный `ends_at` и `server_time`; клиент считает остаток по монотонным
  часам, а не по системному времени телефона.
- Для обновлений используем polling с разумным интервалом; WebSocket/Web Push добавляем только
  при реальной необходимости.
- Любой сетевой вызов имеет таймаут и обработку ошибки.
- Не блокируем event loop/поток долгим CPU-вычислением.

Проверка: профилирование на реальных данных, `pytest`, `npm run test:coverage`.

## 11. Что проверяем на code review

Ревью — не второй линтер. Когда форматирование и тесты уже сделаны машиной, человек смотрит на
то, что машина не видит:

- правильные ли границы модулей и слоёв;
- нет ли ошибки в логике, особенно в условиях и доступе к чужим данным;
- безопасно ли работаем с токеном, SQL и внешними API;
- есть ли тест на новый сценарий и на отказ;
- не изменился ли контракт без `openapi.yaml`;
- понятны ли имена и документация;
- не появился ли техдолг, который лучше вынести в issue.

Мы придерживаемся правил из лекции:

1. Скучную часть работы отдаём компьютеру — CI.
2. Спор о стиле решаем ссылкой на этот guide, а не вкусом.
3. Ревью начинаем сразу, не откладываем на последний день.
4. Идём сверху вниз: сначала архитектура и корректность, потом детали.
5. Даём примеры кода, а не только описание.
6. Не говорим «ты»; обсуждаем код, а не человека.
7. Формулируем как запрос: «Можно ли …?», «Предлагаю …».
8. Обосновываем принципом и причиной.
9. Не требуем больше одного-двух уровней улучшения за раунд.
10. Повторяющиеся замечания не дублируем 20 раз.
11. Не выходим за рамки PR: найденное рядом — в issue.
12. Большие изменения просим разбить; ориентир — до 400 строк.
13. Хвалим удачные решения, а не только ищем ошибки.

В каждом PR должно быть два раунда, если это учебное code review: первый — содержательные
замечания, второй — проверка исправлений. Подробный отчёт с цитатами комментариев и ссылками
на GitHub ведётся отдельно, в `docs/pract3-review-report.md`.

## 12. Исключения и изменения правил

Правило можно нарушить, если:

- этого требует внешний контракт;
- есть измеренная причина (производительность, совместимость);
- альтернатива заметно проще и не ухудшает безопасность.

В таком случае в PR пишем:

```text
Отступаю от §N, потому что <причина>.
Альтернатива: <что рассматривали>.
Риск: <что может сломаться>.
```

Если исключение повторяется, это уже не исключение, а новое правило. Обсуждаем его на командной
встрече и добавляем в guide отдельным PR. Так руководство остаётся живым, а не превращается в
документ, который все игнорируют.
