# Модель рекомендаций v1 и метрики ранжирования

Документ задачи 6.0/6.2 спринта 2: что именно обучается, как это включается в сервисе и
какие числа получились на прогоне. Числа воспроизводятся одной командой (см. ниже), поэтому
их можно показывать заказчику вместе с оговорками из раздела «Ограничения».

## Что требовалось

- TF-IDF по лемам ингредиентов + косинусная близость, отбор кандидатов KNN (задача 6.0);
- артефакт модели (`backend/app/ml/artifacts/v1.json`), путь — в настройке
  `SMART_RECOMMENDATIONS_ARTIFACT`; **отсутствие артефакта не ломает сервис** — остаётся
  прежняя заглушка (bag-of-lemmas);
- метрики ранжирования leave-one-ingredient-out: Precision@5, Recall@5, HitRate@5, MRR и
  сравнение с текущей заглушкой как baseline (задача 6.2);
- **критерий приёмки:** v1 выше baseline по Precision@5 и MRR.

## Что такое v1

| Компонент | Решение |
|---|---|
| признаки | ингредиенты рецепта, приведённые к лемам (`app/ml/preprocessing.py`), без названия и инструкции |
| вес признака | `tf * idf`, где `tf = 1` (лемма считается один раз на рецепт) |
| IDF | `ln((1 + N) / (1 + df)) + 1` — сглаженная формула `sklearn`; `N` — число рецептов корпуса, `df` — в скольких из них встречается лемма |
| незнакомое слово | получает `default_idf = ln(1 + N) + 1`, то есть **наибольший** вес: продукт, которого не было в корпусе, — самый специфичный |
| близость | косинусная (`app/ml/vectorizer.py::similarity`), как и раньше |
| кандидаты | KNN по косинусу (`app/ml/knn.py`); в метриках — те же кандидаты через инвертированный индекс |
| обучение | без учителя: только списки ингредиентов каталога, никаких пользовательских данных |
| артефакт | один JSON-файл: `version`, `trained_at`, `documents`, `source`, `default_idf`, `idf{лемма: вес}` |

Почему JSON, а не `v1.joblib` из плана: модель — это словарь весов. JSON читается глазами, не
требует зависимости (`joblib` тянется только вместе со `sklearn`, который модулю не нужен), и его
загрузка не исполняет код — артефакт может лежать на томе, куда пишет кто-то ещё. Формат
версионирован: файл с чужим `version` игнорируется, сервис молча остаётся на заглушке.

### Как модель попадает в ответ

`app/ml/vectorizer.py::encode_texts` выбирает векторизатор в явном порядке:

1. SBERT, если он включён и доступен (`EMBEDDINGS_ENABLED`) — это целевая архитектура `ml_plan`;
2. **модель v1**, если загружен артефакт;
3. bag-of-lemmas — если ни того, ни другого нет.

Выбор виден в логах и в статистике запроса: `vectorizer=tf-idf-v1`, `model_documents=<N>`.
Файл перечитывается только при изменении (кэш по `mtime`/размеру), поэтому переобучение
подхватывается без перезапуска. Ошибка чтения артефакта — предупреждение в лог и работа на
заглушке: `GET /recommend_recipes` продолжает отвечать.

## Как обучить и как измерить

```bash
cd backend

# 1. Обучить модель (по умолчанию — на корпусе из репозитория, 120 рецептов)
python -m app.ml.model
# или на реальном каталоге из БД (DATABASE_URL), например на 150 тыс. рецептов
python -m app.ml.model --from-db --limit 150000

# 2. Измерить метрики и сравнить с baseline (код возврата 1, если v1 хуже)
python -m app.ml.evaluate
python -m app.ml.evaluate --model app/ml/artifacts/v1.json   # ровно тот артефакт, что в работе
python -m app.ml.evaluate --from-db --limit 20000 --k 10
```

Артефакт по умолчанию пишется в `backend/app/ml/artifacts/v1.json` — каталог в `.gitignore`
(см. `docs/sprint-2-plan.md`: данные и артефакты не коммитятся). Другой путь задаётся
`--out` при обучении и `SMART_RECOMMENDATIONS_ARTIFACT` в окружении сервиса:

```bash
SMART_RECOMMENDATIONS_ENABLED=true
SMART_RECOMMENDATIONS_ARTIFACT=/srv/models/v1.json
```

Те же два шага (`python -m app.ml.model` и `python -m app.ml.evaluate`) выполняет workflow
`Backend CI` на каждый pull request: регресс модели роняет сборку, а не остаётся незамеченным.

## Протокол измерения

**Leave-one-ingredient-out.** Для каждого рецепта корпуса и каждого его ингредиента `x`:

1. `x` прячется, остальные ингредиенты рецепта становятся запросом — это модель «в холодильнике
   пользователя есть эти продукты»;
2. весь корпус ранжируется косинусной близостью (тот же порядок, что в сервисе), сам рецепт из
   выдачи исключается;
3. релевантные рецепты — те, в списке ингредиентов которых есть `x` (по лемам).

Запросы, у которых нет ни одного релевантного рецепта (продукт встречается только в исходном
рецепте), пропускаются и считаются в отчёте отдельно.

| Метрика | Определение |
|---|---|
| `P@1` | доля запросов, где первый же рецепт использует скрытый продукт |
| `P@5` | доля из пяти рекомендованных рецептов, использующих скрытый продукт |
| `R@5` | найдено релевантных в топ-5 / `min(число релевантных, 5)` |
| `Hit@5` | доля запросов, где в топ-5 есть хоть один релевантный рецепт |
| `MRR@5` | среднее `1 / позиция` первого релевантного рецепта |

Сравниваются две стратегии на одних и тех же запросах и одном корпусе:

- **baseline** — bag-of-lemmas с весом 1.0 на лемму, то есть поведение модуля до задачи 6.0;
- **v1** — та же схема с весами IDF.

## Числа последнего прогона

Прогон 29.10.2026, `python -m app.ml.evaluate --model app/ml/artifacts/v1.json` на корпусе
`backend/tests/data/recommendation_sample.json` (120 рецептов, 156 лемм, 813 запросов, `k = 5`,
42 запроса пропущено):

| Стратегия | P@1 | P@5 | R@5 | Hit@5 | MRR@5 |
|---|---|---|---|---|---|
| baseline (bag-of-lemmas) | 0.385 | 0.326 | 0.344 | 0.672 | 0.493 |
| **v1 (TF-IDF)** | **0.395** | **0.360** | **0.380** | **0.711** | **0.513** |
| прирост | +0.010 | **+0.033** | +0.037 | +0.039 | **+0.020** |

Критерий приёмки выполнен: `P@5` 0.360 против 0.326 (**+3,3 п.п., +10 % относительно**) и
`MRR@5` 0.513 против 0.493. Дополнительно: `Hit@5` 0.711 против 0.672 — почти три четверти
запросов получают хотя бы один рецепт с нужным продуктом.

Разбивка по тому, насколько продукт частый в корпусе (сколько рецептов его используют):

| Группа | Запросов | P@5 baseline | P@5 v1 | Прирост |
|---|---|---|---|---|
| редкий (≤ 5 рецептов) | 189 | 0.087 | 0.101 | +0.014 |
| средний (6–20) | 212 | 0.160 | 0.158 | −0.002 |
| частый (> 20) | 412 | 0.522 | 0.582 | **+0.060** |

Читать это надо так: на частых продуктах (`картофель`, `яйцо`, `мука`) выигрывает именно
взвешивание по IDF — заглушка тонула в общих ингредиентах; на редких продуктах потолок метрики
низкий по построению (релевантных рецептов один-два, поэтому `P@5` не может быть высоким), и там
разницы почти нет.

## Ограничения: что эти числа не значат

- Корпус метрик — **120 рецептов, написанных для проверки**, а не выборка из датасета povarenok
  (датасет не коммитится, см. `docs/sprint-2-plan.md`). Числа in-sample относительно корпуса, на
  котором обучены IDF. Для отчёта заказчику на реальных данных — та же команда с `--from-db` на
  импортированном каталоге.
- Корпус маленький и сильно пересекается по составу (супы, салаты, выпечка), поэтому прирост
  скромный: чем больше и разнообразнее каталог, тем сильнее эффект IDF.
- Протокол — приближение: в сервисе профиль пользователя это **центроид избранного**, а в
  метриках — один рецепт без одного ингредиента. Бонус за продукты из холодильника
  (`FRIDGE_BONUS`) в метриках не участвует, поэтому числа описывают чистую близость.
- Количества продуктов не учитываются (датасет даёт их текстом), SBERT в v1 не входит — он
  остаётся ablation на подвыборке 10–20 тыс. рецептов.
- Лемматизация — таблица окончаний (`app/ml/preprocessing.py`), а не `pymorphy2`: формы вроде
  `grapes → grap` возможны, но влияют на обе стратегии одинаково.

## Решения, которые стоит помнить

1. **Артефакт обязателен?** Нет. Нет файла — нет модели, работает заглушка: это и требование
   задачи, и защита от «положили битый файл в прод».
2. **Переобучение без рестарта** — стат-кэш в `app/ml/model.py`: файл читается один раз и
   перечитывается только при изменении `mtime`/размера.
3. **Почему не `sklearn.TfidfVectorizer`**: матрица «147 тыс. × словарь» в памяти не нужна, а
   сервису на запрос нужен вектор одного текста; веса IDF — это и есть модель, остальное считает
   `app/ml/vectorizer.py`.
4. **Инвертированный индекс в метриках** — чтобы `--from-db` на 20 тыс. рецептов считался
   минутами, а не часами; ранжирование при этом то же, что у полного перебора (рецепты без общих
   лемм имеют близость 0 и в сервисе тоже не попадают в ответ).
5. **Тесты** — `backend/tests/test_recommendation_model.py` (9 кейсов): веса IDF, round-trip
   артефакта, битый/отсутствующий файл, переключение движка на модель, арифметика метрик,
   критерий приёмки на корпусе репозитория, коды возврата CLI и чтение корпуса из БД.
