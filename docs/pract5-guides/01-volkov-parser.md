# Волков Михаил, вариант 1

**Ветка:** `refactor/pract5-parser`

**Файлы:** только `backend/app/importer/pages.py`.

## Что делаем

В `handle_starttag` сейчас один длинный метод: разбор атрибутов и сразу 15 веток `if/elif`.
Каждая ветка выносится в отдельный маленький метод, а в `handle_starttag` остаются разбор
атрибутов и цепочка вызовов.

Главное — **порядок проверок не меняется**. Сначала проверяется `h1`, потом `div`, потом `time`
и так далее. При изменении порядка парсер начнёт иначе читать страницу.

## Порядок работы

1. Ветка создаётся командами:

   ```bash
   git switch main
   git pull
   git switch -c refactor/pract5-parser
   ```

2. Текущий `handle_starttag` изучается, порядок веток фиксируется.
3. Тела веток выносятся в методы `_start_name`, `_start_nutrition`, `_start_description` и т.д.
4. В `handle_starttag` остаётся только:

   ```python
   data = dict(attrs)
   props = ...
   classes = ...

   if tag == "h1" and "name" in props:
       self._start_name()
   elif ...
   ```

5. Проверяется, что старые тела веток удалены, а не остались два раза.
6. Выполняются проверки:

   ```bash
   cd backend
   ruff check .
   black --check .
   pytest tests/test_importer_pages.py -q
   pytest
   ```

## Что писать в PR

Заголовок:

```text
refactor(importer): extract start tag handlers
```

В описании: было 59 строк и 24 проверки, стало около 25 строк в диспетчере и 15 маленьких
методов. Поведение не меняется, тесты те же.

## Что может спросить ревьюер

- «Почему не использован словарь `tag -> handler`?» — потому что порядок проверок важен, а
  словарь его не гарантирует.
- «Почему методы начинаются с `_`?» — они внутренние, снаружи их никто не вызывает.
- «Точно ли ничего не поменялось?» — можно показать, что старые тела перенесены, а не переписаны.

## Границы изменения

`handle_endtag`, `handle_data`, правила разбора и тесты не меняются. Если проблема обнаружена
рядом, создаётся issue, но в этот PR она не попадает.
