# Волков Михаил, вариант 1

**Ветка:** `refactor/pract5-parser`

**Файлы:** только `backend/app/importer/pages.py`.

## Что делаем

В `handle_starttag` сейчас один длинный метод: разбор атрибутов и сразу 15 веток `if/elif`.
Выносим каждую ветку в отдельный маленький метод, а в `handle_starttag` оставляем разбор
атрибутов и цепочку вызовов.

Главное — **порядок проверок не менять**. Там важно, что сначала проверяется `h1`, потом `div`,
потом `time` и так далее. Если порядок поменять, парсер начнёт по-другому читать страницу.

## Порядок работы

1. Создай ветку:

   ```bash
   git switch main
   git pull
   git switch -c refactor/pract5-parser
   ```

2. Посмотри текущий `handle_starttag` в `pages.py` и выпиши себе ветки по порядку.
3. Вынеси тела веток в методы `_start_name`, `_start_nutrition`, `_start_description` и т.д.
4. В `handle_starttag` оставь только:

   ```python
   data = dict(attrs)
   props = ...
   classes = ...

   if tag == "h1" and "name" in props:
       self._start_name()
   elif ...
   ```

5. Убедись, что старые тела веток удалены, а не остались два раза.
6. Проверь:

   ```bash
   cd backend
   ruff check .
   black --check .
   pytest tests/test_importer_pages.py -q
   pytest
   ```

## Что писать в PR

Заголовок:

```text
refactor(importer): extract start tag handlers
```

В описании: было 59 строк и 24 проверки, стало около 25 строк в диспетчере и 15 маленьких
методов. Поведение не меняется, тесты те же.

## Что может спросить ревьюер

- «Почему не сделал словарь `tag -> handler`?» — потому что порядок проверок важен, а словарь
  его не гарантирует.
- «Почему методы начинаются с `_`?» — они внутренние, снаружи их никто не вызывает.
- «Точно ли ничего не поменялось?» — покажи, что старые тела просто перенёс, а не переписал.
