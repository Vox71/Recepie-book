# Спринт 4: вход в аккаунт и первые живые данные

Это отчёт об учебном спринте проекта **Recepie-book** — сервиса с рецептами, холодильником и
таймерами. Документ написан простым языком: его можно читать на защите, показывать преподавателю и
давать студентам, которые ещё не разбираются в коде.

В спринте 3 мы сделали сервер и «скелет» сайта: страницы уже открывались, но данные были
демонстрационными, а форма входа ничего не отправляла. Спринт 4 — про то, чтобы сайт начал
по-настоящему разговаривать с сервером. Первая задача — самая важная: без входа в аккаунт
пользователь не увидит ни личный холодильник, ни таймеры, ни избранное.

**Цель спринта:** пользователь открывает сайт, входит под своей учётной записью, открывает рецепт и
запускает таймер. После перезагрузки страницы таймер продолжает идти, потому что время считает
сервер. Контракт API при этом не меняется: всё нужное сервер уже умеет отдавать, задача клиента —
научиться этим пользоваться.

## 2. Задача 1. API-клиент и авторизация (подробно)

### 2.1. Зачем это пользователю

Представьте, что сайт — это дом, а сервер — охраняемый склад с продуктами и рецептами. Раньше
сайт мог только заглядывать в окно: форма входа была нарисована, но кнопка «Войти» ничего не
делала. Теперь сайт получает **пропуск** — токен — и с ним может просить у сервера личные данные.

Без входа не работает ничего личного:

- холодильник — у каждого пользователя свои продукты;
- таймеры — чужой таймер нельзя увидеть или отменить;
- избранное — тоже привязано к конкретному человеку.

Поэтому первая задача — не «красивая кнопка», а настоящая дверь в приложение.

### 2.2. Что было до этой задачи

В спринте 3 страница входа уже была свёрстана по макету: поля Email и пароль, кнопка «Войти»,
красивая картинка и переключение видимости пароля. Но это был только внешний вид:

- форма не отправляла данные на сервер;
- после нажатия «Войти» ничего не происходило;
- все адреса были открыты любому гостю;
- сайт не умел хранить токен и прикладывать его к запросам.

Получалось как дверь с нарисованной ручкой: выглядит правильно, а открыть нельзя.


### 2.3. Что сделал Иван

Задача получилась не одной кнопкой, а маленькой цепочкой: форма → API → токен → защищённая
страница. Вот из чего она состоит.

**1. Общий клиент для запросов к серверу.**

В `frontend/src/api/client.ts` появился один способ общаться с API. Страницы больше не пишут
`fetch` каждая по-своему — они вызывают `apiRequest`. Клиент:

- берёт адрес сервера из `VITE_API_URL` (по умолчанию `http://localhost:8000`);
- прикладывает заголовок `Authorization: Bearer <токен>`, если токен есть;
- отправляет JSON и разбирает ответ;
- превращает ошибки сервера в понятный `ApiError` со статусом и сообщением.

Это важно, потому что иначе каждый экран мог бы забыть приложить токен или по-своему разобрать
ошибку. Теперь правило одно для всех.

**2. Запрос на вход.**

В `frontend/src/api/auth.ts` есть `loginRequest(email, password)`. Он отправляет
`POST /login` и получает токен. Сервер уже умел это делать в спринте 3 — менять API не пришлось.

**3. Хранение входа.**

`AuthProvider` в `frontend/src/auth/AuthContext.tsx` хранит токен и email в `localStorage`:

- после перезагрузки страницы вход не теряется;
- `useAuth()` даёт любому компоненту понять, вошёл человек или нет;
- `logout()` удаляет токен и email;
- `login()` сохраняет токен после успешного ответа сервера.

Пароль нигде не сохраняется. В `localStorage` лежит только пропуск — токен — и email для подписи
в шапке.

**4. Защита страниц.**

`frontend/src/auth/RequireAuth.tsx` — «вахтёр» у личных страниц. Если токена нет, он отправляет
гостя на `/login` и запоминает, куда тот шёл. После входа пользователь возвращается на нужный
адрес, а не всегда на главную.

Защищены:

- `/recipes/:recipeId` — страница рецепта;
- `/fridge` — холодильник;
- страница 404 внутри личного каркаса.

`/login` остаётся открытым: туда и должен попадать человек без токена.

**5. Настоящая форма входа.**

`LoginPage` теперь:

- хранит email и пароль в состоянии;
- показывает «Входим…», пока идёт запрос;
- при неверных данных показывает «Неверный email или пароль»;
- при другой ошибке показывает сообщение API;
- после успеха переходит на холодильник или на страницу, куда пользователь шёл до этого.

**6. Шапка и выход.**

В `SiteHeader` появились email вошедшего пользователя и кнопка «Выйти». «Мой холодильник» стал
настоящей ссылкой, а не заглушкой. После выхода токен удаляется, и защищённая страница снова
просит войти.

### 2.4. Как это работает по шагам

1. Пользователь открывает `/login` и вводит email и пароль.
2. Сайт отправляет их на `POST /login`.
3. Сервер проверяет данные и возвращает токен — длинную строку-пропуск.
4. Сайт сохраняет токен в `localStorage` и запоминает email для шапки.
5. При переходе на защищённую страницу `RequireAuth` проверяет: токен есть? Если нет — на вход.
6. Каждый запрос к личным данным уходит с заголовком `Authorization: Bearer <токен>`.
7. Если сервер отвечает `401` (токен истёк или неправильный), сайт удаляет токен и возвращает
   пользователя на `/login`.
8. Кнопка «Выйти» делает то же самое вручную.

Короткая схема:

```text
форма входа → POST /login → токен → localStorage
                                      ↓
                              Authorization: Bearer …
                                      ↓
                     защищённая страница / API
```

### 2.5. Что видит пользователь

- На `/login` — рабочую форму. Ошибка видна прямо под полями, кнопка не «залипает».
- После входа — холодильник и шапку с email.
- Если открыть `/recipes/42` без входа — сайт перекинет на `/login`, а после входа вернёт на
  рецепт.
- Если нажать «Выйти» — снова экран входа, токен удалён.
- Если сервер ответил `401` — сайт не показывает «белый экран», а объясняет, что нужно войти
  заново.

### 2.6. Что осталось за рамками задачи

- **Регистрация в интерфейсе** пока заглушка: кнопка «Создать аккаунт» не отправляет форму.
  Пользователя для проверки можно создать через API или заранее подготовить в базе.
- **Токен в `localStorage`** удобен, но уязвим к XSS: если на страницу попадёт чужой скрипт, он
  сможет прочитать токен. Это осознанный компромисс для учебного проекта; более защищённый
  вариант — `httpOnly` cookie — требует отдельной настройки CORS и CSRF.
- **Обновления токена (refresh token)** нет: когда срок действия истечёт, пользователь войдёт
  заново.
- **Страница рецепта** в этой задаче ещё на демонстрационных данных — её делает задача 3.
- **Экран таймеров** ещё не сделан — это задача 4.

### 2.7. Как проверяли

На ветке `feat/fridge-auth`:

- **49 фронтенд-тестов** (Vitest + Testing Library), включая вход, неверные данные, защиту
  маршрутов, выход и 401;
- **159 бэкенд-тестов** на реальной PostgreSQL: регистрация, вход, защищённые адреса и доступ к
  чужим данным;
- `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run build` — без ошибок;
- `ruff`, `black`, `pytest` на бэкенде — без ошибок;
- покрытие фронтенда — выше порога 80 % (около 93 % строк и 86 % ветвей).

Важно: код первой задачи лежит в ветке `feat/fridge-auth`. На `main` уже влит отчёт по практике
№ 3, но сама ветка с авторизацией ещё не объединена — это стоит проверить перед защитой.

## 6. Словарь терминов

| Термин | Простыми словами |
|---|---|
| API | «Официант» между сайтом и сервером: сайт просит — сервер отвечает |
| Эндпоинт | Конкретная команда API, например `POST /login` |
| Токен (JWT) | Цифровой пропуск, который сайт прикладывает к личным запросам |
| `Authorization: Bearer` | Способ передать пропуск: в заголовке запроса |
| `localStorage` | Хранилище в браузере, которое переживает перезагрузку страницы |
| Защищённый маршрут | Страница, которую нельзя открыть без входа |
| `401` | Сервер говорит: «не авторизован, войди заново» |
| `ApiError` | Ошибка запроса, у которой есть статус и понятное сообщение |
| CORS | Правило браузера, с каких адресов сайту разрешено обращаться к серверу |
| XSS | Атака, при которой на страницу попадает чужой вредоносный скрипт |

## 8. Задача 2 подробно: парсинг рецептов и качество рекомендаций

**Автор: Елизавета Тропина.**

Этот раздел описывает вторую задачу спринта. Разделы 1–7 выше относятся к первой задаче —
авторизации; здесь — следующий шаг: научить систему работать не на демонстрационных, а на
реальных рецептах и проверить, насколько хорошо она подбирает блюда.

### 8.1. Зачем вообще парсить рецепты

В открытом датасете povarenok есть только три вещи:

- ссылка на страницу рецепта;
- название;
- список ингредиентов.

Этого достаточно, чтобы показать название и состав, но мало для нормального приложения. На самой
странице рецепта есть ещё:

- пошаговая инструкция;
- время приготовления;
- количество порций;
- калорийность и БЖУ;
- фотографии шагов.

Поэтому импорт разделён на два этапа:

```text
CSV/parquet датасета
        ↓
импорт: recipes + recipe_ingredients
        ↓
обогащение: скачать страницу → разобрать HTML
        ↓
recipe_steps, recipe_nutrition, servings, cooking_time_minutes
```

Если объяснить просто: сначала мы заносим в базу «что за блюдо и из чего оно», а потом идём на
страницу и дописываем «как его готовить и сколько в нём калорий».

### 8.2. Что уже было готово

К началу этой части уже были:

- импорт датасета;
- парсер страниц povarenok на стандартном `HTMLParser`;
- кэш HTML, чтобы не скачивать одну и ту же страницу дважды;
- идемпотентность: повторный импорт не создаёт дубликаты;
- `PARSER_VERSION`, чтобы после изменения парсера можно было переразобрать страницы;
- защита от «зависшего» сайта: таймауты, пауза между запросами, остановка после нескольких
  `403/429`;
- тесты на сохранённых HTML-страницах, без интернета.

Парсер ищет не CSS-классы, а microdata `itemprop`: `recipeInstructions`, `recipeYield`,
`totalTime`, `nutrition`. Это надёжнее: классы на сайте меняются при редизайне, а микроразметка
живёт дольше.

| Время есть | 346 рецептов (69 %) |
| Порции есть | 284 рецепта (57 %) |
| КБЖУ есть | 494 рецепта (99 %) |

Почему не 100 %:

- не на каждой странице сайт публикует время и порции;
- у 105 рецептов вообще нет блока с шагами — это видно в сохранённом HTML, парсер не выдумывает
  данные;
- у части ингредиентов нет количества: например, «Соль» без граммовки — это нормально.

Главный вывод: парсер работает, но данные по полноте похожи на источник. Если сайт не дал
порции — приложение должно честно попросить базовое количество, а не подставлять случайное число.

### 8.4. Нормализация количеств

После первого прогона стало понятно, что количество вида `250 мл`, `3 шт`, `1 кг` неудобно
сравнивать и пересчитывать. Добавили две колонки:

- `quantity_value` — число;
- `quantity_unit` — единица.

Правила простые:

- граммы и килограммы → граммы (`1 кг` → `1000 г`);
- миллилитры и литры → миллилитры;
- штуки, зубчики, ложки, щепотки, стаканы остаются в своих единицах;
- «по вкусу» и диапазоны вроде `200–300 г` не превращаются в одно число.

`quantity_text` остаётся как было: это исходная строка, по ней всегда можно проверить, что именно
написал автор рецепта. Нормализованные поля — дополнение, а не замена.

Для старых записей есть команда:

```bash
python -m app.importer --normalize-quantities
```

### 8.5. Расширение до 12 000 рецептов

Для обучения модели 500 рецептов слишком мало. Импортировали 12 000:

| Показатель | Значение |
|---|---:|
| Рецептов | 12 000 |
| Ингредиентов | 105 087 |
| Нормализовано количеств | 85 910 (81,75 %) |
| Без количества в источнике | 13 928 |
| Обогащено страниц | 500 |

Обогащение всех 12 000 страниц заняло бы много часов и десятки гигабайт кэша, поэтому для
обучения по ингредиентам оставили весь каталог, а подробный разбор страниц проверили на 500
рецептах. Для рекомендаций по составу этого достаточно; для карточки каждого рецепта страницы
можно обогащать постепенно, с кэшем.

### 8.6. Почему нельзя просто «посчитать метрики»

Сначала использовали простой честный эксперимент **leave-one-ingredient-out**:

1. берём рецепт;
2. прячем один ингредиент, например «томат»;
3. остальные ингредиенты превращаем в запрос;
4. смотрим, найдёт ли система другие рецепты с томатом;
5. повторяем для всех рецептов и ингредиентов.

Это не совсем сценарий «что приготовить из холодильника», но хороший способ проверить, умеет ли
модель связывать продукты. Скрытый продукт отсутствует в запросе, поэтому нужно угадать его по
остальным продуктам.

Чтобы не обмануть самих себя, корпус разделили на три части:

- **train** — на нём учим веса;
- **validation** — на нём выбираем настройки;
- **test** — на нём показываем финальные числа.

Если обучать и проверять на одних и тех же рецептах, модель может просто запомнить ответы. Split
по рецептам это исключает.

В финальном прогоне:

- 8 398 рецептов — train;
- 1 800 — validation;
- 1 800 — test;
- по 1 000 запросов на validation и test.

### 8.7. Какие технологии и почему

| Технология | Зачем |
|---|---|
| Python | весь backend и ML-эксперименты уже на нём |
| PostgreSQL | реальные рецепты, ингредиенты и нормализованные количества |
| TF-IDF | базовая модель: редкие ингредиенты важнее частых |
| BM25 | лучше TF-IDF для коротких списков: учитывает длину рецепта и не даёт одному слову слишком много веса |
| Co-occurrence / PMI | ищет продукты, которые часто встречаются вместе: «если в запросе есть эти продукты, возможно, есть и скрытый» |
| Гибридный score | объединяет BM25, PMI и долю пересечения ингредиентов |
| pytest | проверка кода и метрик |
| HTMLParser | разбор страниц без тяжёлых библиотек |
| JSON-артефакт | TF-IDF-модель можно сохранить и загрузить без отдельной ML-инфраструктуры |

SBERT и тяжёлые нейросети пока не подключали: сначала нужно было проверить более простые и
объяснимые сигналы.

### 8.8. Что такое BM25 и co-occurrence простыми словами

**BM25** — это способ сравнивать запрос и рецепт по словам. Он похож на TF-IDF, но:

- редкое слово получает больший вес;
- если слово повторяется много раз, его вес не растёт бесконечно;
- длинный рецепт не получает преимущество только потому, что в нём больше слов.

**Co-occurrence** — это «совместная встречаемость». Если «томат» и «базилик» часто появляются в
одних и тех же рецептах, между ними есть связь. В запросе остался базилик, значит, рецепты с
томатом можно поднять выше.

**PMI** — численная мера такой связи. Положительный PMI означает: продукты встречаются вместе
чаще, чем случайно.

**Гибрид** складывает несколько сигналов с весами. Веса подбираются на validation, а не на test:

```text
score = 0.50 × BM25 + 0.75 × co-occurrence + 0.10 × пересечение ингредиентов
```

### 8.9. Результаты

Финальные числа на **test**, 1 000 запросов, `k = 10`:

| Стратегия | P@1 | P@10 | R@10 | Hit@10 | MRR@10 |
|---|---:|---:|---:|---:|---:|
| BM25 | 0.287 | 0.291 | 0.292 | 0.739 | 0.427 |
| co-occurrence | 0.420 | 0.405 | 0.405 | 0.818 | 0.552 |
| **гибрид** | **0.445** | **0.430** | **0.430** | **0.822** | **0.565** |

На validation гибрид показал P@10 0.438 и MRR 0.600. Разница с test небольшая, значит настройки
не «подогнаны» под один набор.

### 8.10. Что означают эти числа

- **P@1 = 0.445** — примерно в 44,5 % запросов первый же рекомендованный рецепт содержит скрытый
  продукт.
- **P@10 = 0.430** — в среднем 43 % мест в топ-10 занимают рецепты с нужным продуктом.
- **Hit@10 = 0.822** — в 82,2 % запросов хотя бы один полезный рецепт попал в топ-10.
- **MRR@10 = 0.565** — первый полезный рецепт в среднем стоит довольно высоко; чем ближе к 1,
  тем лучше.

Это не «43 % пользователей получили идеальный ответ». P@10 — средняя доля релевантных рецептов
в десяти показанных. Но для учебного проекта числа уже показывают, что гибридный подход работает
и заметно лучше одного BM25.

### 8.11. Почему co-occurrence оказался сильнее BM25

В этом эксперименте скрытый продукт отсутствует в запросе. BM25 ищет совпадения слов, а PMI ищет
продукты, которые часто встречаются рядом. Поэтому ассоциации дают более прямой сигнал.

Но это не значит, что BM25 не нужен:

- BM25 лучше, когда в запросе есть точные названия;
- PMI лучше, когда нужно «достроить» связь;
- гибрид использует оба сигнала и даёт лучший результат.

### 8.12. Ограничения

- 12 000 рецептов — это первые строки датасета, а не случайная выборка. На другом каталоге числа
  могут измениться.
- Метрики считались по 1 000 отложенных запросов, а не по всем: это ограничение времени и памяти.
- Используются только названия ингредиентов. Шаги, КБЖУ, популярность и профиль пользователя пока
  не участвуют.
- SBERT и оценка на реальных профилях холодильника — следующие задачи.
- `P@10` нельзя читать как «вероятность правильного ответа»; это средняя доля релевантных
  рецептов в топ-10.

## 9. Задача 3 подробно: пересчёт порций и реальная карточка рецепта

**Автор: Михаил Волков.**

### 9.1. Зачем это пользователю

В макете рецепт был красивой картинкой с демонстрационными данными. Но пользователю нужно
другое: открыть реальный рецепт, увидеть, сколько в нём продуктов, и приготовить не «как в
примере», а столько, сколько нужно его семье.

Например, рецепт рассчитан на 2 порции, а пользователь хочет 4. Тогда:

- паста: `200 г` → `400 г`;
- томаты: `4 шт.` → `8 шт.`;
- масло: `2 ст. л.` → `4 ст. л.`;
- КБЖУ тоже увеличивается в два раза;
- значения на 100 г не меняются.

Это задача не про «умножение на два» только в одном месте, а про аккуратный пересчёт всей
карточки.

### 9.2. Что сделано

**1. Страница получает реальные данные.**

`RecipePage` больше не импортирует `src/mocks/recipe.ts`. Вместо мока — `GET /recipes/{id}`:

- название, время, сложность и порции;
- ингредиенты из `ingredient_list`;
- шаги из `steps`;
- КБЖУ из `nutrition`;
- ссылка на источник.

Добавлены состояния загрузки, ошибки, `404` и повтор запроса.

**2. Появился API-клиент рецепта.**

В `frontend/src/api/recipes.ts` описаны DTO (`Recipe`, `RecipeIngredient`, `RecipeStep`,
`RecipeNutrition`) и функция `getRecipe(token, recipeId, signal)`. Она использует тот же
`apiRequest`, что и остальные защищённые запросы.

**3. Добавлено управление порциями.**

Пользователь вводит целое положительное число. Формула:

```text
коэффициент = выбранные порции / базовые порции
новая граммовка = исходная граммовка × коэффициент
```

Некорректный ввод (`0`, минус, строка, пустое поле) не применяется: остаётся последнее
корректное значение, а под полем появляется ошибка.

**4. Отдельно обработаны случаи, когда базовых порций нет.**

Примерно у 58 % страниц povarenok количество порций не опубликовано. Нельзя подставлять
случайное число. Поэтому интерфейс просит:

> На сколько порций рассчитан рецепт?

Пока пользователь не введёт корректное базовое число, пересчёт отключён.

**5. Нормализация количеств.**

Для пересчёта используются `quantity_value` и `quantity_unit`, которые появились в задаче 2:

- масса — в граммах;
- объём — в миллилитрах;
- штуки, ложки, зубчики, щепотки — в своих единицах;
- «по вкусу» и диапазоны не превращаются в выдуманное число.

Если единицу нельзя честно перевести в граммы, она масштабируется в исходной единице. Например,
`2 ст. л.` при удвоении становятся `4 ст. л.`, а не «60 г» без таблицы плотностей.

**6. КБЖУ пересчитывается вместе с порциями.**

- общие калории, белки, жиры и углеводы умножаются на коэффициент;
- значения на 100 г остаются прежними;
- значения на порцию делятся на новое количество порций.

**7. Статусы ингредиентов.**

Если холодильник доступен, страница отмечает, какие продукты уже есть, а каких не хватает.
Если запрос холодильника не удался, показывается «Статус неизвестен», а не ложное «Нужно
добавить».

### 9.3. Как это выглядит для пользователя

1. Открыть `/recipes/42`.
2. Увидеть реальное название, шаги, ингредиенты и КБЖУ.
3. Ввести, например, `4` порции.
4. Увидеть, что все числовые количества и КБЖУ пересчитались.
5. Ввести `0` — увидеть ошибку, при этом старые значения остаются на месте.
6. Открыть рецепт без порций — увидеть просьбу указать базовое количество.

### 9.4. Ограничения

- Количество порций не сохраняется на сервере: это локальное состояние отображения. Если
  понадобится запоминать выбор пользователя, нужна отдельная таблица и endpoint.
- `шт.`, `ст. л.`, `щепот.` не переводятся в граммы: без плотности продукта это было бы
  неточно.
- Аллергены в карточке пока не выводятся: в текущем API рецепта их нет.
- Страница использует заглушку фотографии, а не реальное фото блюда.
