# Спринт 4: вход в аккаунт и первые живые данные

Это отчёт об учебном спринте проекта **Recepie-book** — сервиса с рецептами, холодильником и
таймерами. Документ написан простым языком: его можно читать на защите, показывать преподавателю и
давать студентам, которые ещё не разбираются в коде.

В спринте 3 мы сделали сервер и «скелет» сайта: страницы уже открывались, но данные были
демонстрационными, а форма входа ничего не отправляла. Спринт 4 — про то, чтобы сайт начал
по-настоящему разговаривать с сервером. Первая задача — самая важная: без входа в аккаунт
пользователь не увидит ни личный холодильник, ни таймеры, ни избранное.

**Цель спринта:** пользователь открывает сайт, входит под своей учётной записью, открывает рецепт и
запускает таймер. После перезагрузки страницы таймер продолжает идти, потому что время считает
сервер. Контракт API при этом не меняется: всё нужное сервер уже умеет отдавать, задача клиента —
научиться этим пользоваться.

## 1. Коротко о спринте и ролях

| № | Задача | Исполнитель | Что должно получиться | Статус |

| 1 | API-клиент и авторизация | **Иван Савчук (@MyascoFP)** | вход по-настоящему, токен, защита личных страниц | ✅ выполнено |
| 2 | Страница рецепта на реальных данных | — | вместо мока — `GET /recipes/{id}`, шаги и КБЖУ с сервера | ⏳ следующая |

Порядок не случайный. Пока нет токена, нельзя открыть ни холодильник, ни таймеры, ни избранное:
сервер защищает эти адреса и смотрит, кто именно пришёл. Поэтому первая задача — вход, а уже
потом — остальные экраны.

## 2. Задача 1. API-клиент и авторизация (подробно)

### 2.1. Зачем это пользователю

Представьте, что сайт — это дом, а сервер — охраняемый склад с продуктами и рецептами. Раньше
сайт мог только заглядывать в окно: форма входа была нарисована, но кнопка «Войти» ничего не
делала. Теперь сайт получает **пропуск** — токен — и с ним может просить у сервера личные данные.

Без входа не работает ничего личного:

- холодильник — у каждого пользователя свои продукты;
- таймеры — чужой таймер нельзя увидеть или отменить;
- избранное — тоже привязано к конкретному человеку.

Поэтому первая задача — не «красивая кнопка», а настоящая дверь в приложение.

### 2.2. Что было до этой задачи

В спринте 3 страница входа уже была свёрстана по макету: поля Email и пароль, кнопка «Войти»,
красивая картинка и переключение видимости пароля. Но это был только внешний вид:

- форма не отправляла данные на сервер;
- после нажатия «Войти» ничего не происходило;
- все адреса были открыты любому гостю;
- сайт не умел хранить токен и прикладывать его к запросам.

Получалось как дверь с нарисованной ручкой: выглядит правильно, а открыть нельзя.


### 2.3. Что сделал Иван

Задача получилась не одной кнопкой, а маленькой цепочкой: форма → API → токен → защищённая
страница. Вот из чего она состоит.

**1. Общий клиент для запросов к серверу.**

В `frontend/src/api/client.ts` появился один способ общаться с API. Страницы больше не пишут
`fetch` каждая по-своему — они вызывают `apiRequest`. Клиент:

- берёт адрес сервера из `VITE_API_URL` (по умолчанию `http://localhost:8000`);
- прикладывает заголовок `Authorization: Bearer <токен>`, если токен есть;
- отправляет JSON и разбирает ответ;
- превращает ошибки сервера в понятный `ApiError` со статусом и сообщением.

Это важно, потому что иначе каждый экран мог бы забыть приложить токен или по-своему разобрать
ошибку. Теперь правило одно для всех.

**2. Запрос на вход.**

В `frontend/src/api/auth.ts` есть `loginRequest(email, password)`. Он отправляет
`POST /login` и получает токен. Сервер уже умел это делать в спринте 3 — менять API не пришлось.

**3. Хранение входа.**

`AuthProvider` в `frontend/src/auth/AuthContext.tsx` хранит токен и email в `localStorage`:

- после перезагрузки страницы вход не теряется;
- `useAuth()` даёт любому компоненту понять, вошёл человек или нет;
- `logout()` удаляет токен и email;
- `login()` сохраняет токен после успешного ответа сервера.

Пароль нигде не сохраняется. В `localStorage` лежит только пропуск — токен — и email для подписи
в шапке.

**4. Защита страниц.**

`frontend/src/auth/RequireAuth.tsx` — «вахтёр» у личных страниц. Если токена нет, он отправляет
гостя на `/login` и запоминает, куда тот шёл. После входа пользователь возвращается на нужный
адрес, а не всегда на главную.

Защищены:

- `/recipes/:recipeId` — страница рецепта;
- `/fridge` — холодильник;
- страница 404 внутри личного каркаса.

`/login` остаётся открытым: туда и должен попадать человек без токена.

**5. Настоящая форма входа.**

`LoginPage` теперь:

- хранит email и пароль в состоянии;
- показывает «Входим…», пока идёт запрос;
- при неверных данных показывает «Неверный email или пароль»;
- при другой ошибке показывает сообщение API;
- после успеха переходит на холодильник или на страницу, куда пользователь шёл до этого.

**6. Шапка и выход.**

В `SiteHeader` появились email вошедшего пользователя и кнопка «Выйти». «Мой холодильник» стал
настоящей ссылкой, а не заглушкой. После выхода токен удаляется, и защищённая страница снова
просит войти.

### 2.4. Как это работает по шагам

1. Пользователь открывает `/login` и вводит email и пароль.
2. Сайт отправляет их на `POST /login`.
3. Сервер проверяет данные и возвращает токен — длинную строку-пропуск.
4. Сайт сохраняет токен в `localStorage` и запоминает email для шапки.
5. При переходе на защищённую страницу `RequireAuth` проверяет: токен есть? Если нет — на вход.
6. Каждый запрос к личным данным уходит с заголовком `Authorization: Bearer <токен>`.
7. Если сервер отвечает `401` (токен истёк или неправильный), сайт удаляет токен и возвращает
   пользователя на `/login`.
8. Кнопка «Выйти» делает то же самое вручную.

Короткая схема:

```text
форма входа → POST /login → токен → localStorage
                                      ↓
                              Authorization: Bearer …
                                      ↓
                     защищённая страница / API
```

### 2.5. Что видит пользователь

- На `/login` — рабочую форму. Ошибка видна прямо под полями, кнопка не «залипает».
- После входа — холодильник и шапку с email.
- Если открыть `/recipes/42` без входа — сайт перекинет на `/login`, а после входа вернёт на
  рецепт.
- Если нажать «Выйти» — снова экран входа, токен удалён.
- Если сервер ответил `401` — сайт не показывает «белый экран», а объясняет, что нужно войти
  заново.

### 2.6. Что осталось за рамками задачи

- **Регистрация в интерфейсе** пока заглушка: кнопка «Создать аккаунт» не отправляет форму.
  Пользователя для проверки можно создать через API или заранее подготовить в базе.
- **Токен в `localStorage`** удобен, но уязвим к XSS: если на страницу попадёт чужой скрипт, он
  сможет прочитать токен. Это осознанный компромисс для учебного проекта; более защищённый
  вариант — `httpOnly` cookie — требует отдельной настройки CORS и CSRF.
- **Обновления токена (refresh token)** нет: когда срок действия истечёт, пользователь войдёт
  заново.
- **Страница рецепта** пока по-прежнему на демонстрационных данных — это задача 2.
- **Экран таймеров** ещё не сделан — это задача 3.

### 2.7. Как проверяли

На ветке `feat/fridge-auth`:

- **49 фронтенд-тестов** (Vitest + Testing Library), включая вход, неверные данные, защиту
  маршрутов, выход и 401;
- **159 бэкенд-тестов** на реальной PostgreSQL: регистрация, вход, защищённые адреса и доступ к
  чужим данным;
- `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run build` — без ошибок;
- `ruff`, `black`, `pytest` на бэкенде — без ошибок;
- покрытие фронтенда — выше порога 80 % (около 93 % строк и 86 % ветвей).

Важно: код первой задачи лежит в ветке `feat/fridge-auth`. На `main` уже влит отчёт по практике
№ 3, но сама ветка с авторизацией ещё не объединена — это стоит проверить перед защитой.


## 3. Остальные задачи спринта

Первая задача — фундамент. Остальные задачи опираются на неё, поэтому в отчёте они пока отмечены
как следующие.

### 3.1. Задача 2. Страница рецепта на реальных данных

Сейчас `/recipes/:recipeId` показывает демонстрационный набор из `src/mocks/recipe.ts`. Нужно
заменить его на `GET /recipes/{id}`:

- заголовок, описание, время, сложность и порции;
- ингредиенты из `ingredient_list`;
- шаги из `steps`;
- КБЖУ из `nutrition`;
- состояния загрузки, ошибки и 404.

Вёрстка уже готова, поэтому меняется источник данных, а не внешний вид. Пустые поля (`null`) —
норма: у импортированных рецептов не всегда есть время и порции, и интерфейс должен показывать
прочерк, а не выдумывать значение.

**Статус:** следующая задача, не начата.

### 3.2. Задача 3. Экран таймеров

Серверная часть таймеров готова ещё с спринта 3. На клиенте нужно:

- кнопка «Старт»;
- список активных таймеров;
- отмена;
- восстановление после перезагрузки по ответу сервера;
- звонок один раз по истечении времени.

Главное правило: остаток считается от пары `ends_at` и `server_time`, а не от часов телефона.
Подробный алгоритм — в [`docs/timer.md`](timer.md).

**Статус:** после задачи 2.

### 3.3. Задача 4. Остальные страницы

Лента рецептов, избранное и холодильник. Холодильник уже частично сделан в той же ветке
`feat/fridge-auth`: есть защищённые адреса `/profile/fridge`, список, добавление, удаление и
удаление просроченных. Лента и избранное ещё впереди.

**Статус:** холодильник начат, остальные страницы следующие.

## 6. Словарь терминов

| Термин | Простыми словами |
|---|---|
| API | «Официант» между сайтом и сервером: сайт просит — сервер отвечает |
| Эндпоинт | Конкретная команда API, например `POST /login` |
| Токен (JWT) | Цифровой пропуск, который сайт прикладывает к личным запросам |
| `Authorization: Bearer` | Способ передать пропуск: в заголовке запроса |
| `localStorage` | Хранилище в браузере, которое переживает перезагрузку страницы |
| Защищённый маршрут | Страница, которую нельзя открыть без входа |
| `401` | Сервер говорит: «не авторизован, войди заново» |
| `ApiError` | Ошибка запроса, у которой есть статус и понятное сообщение |
| CORS | Правило браузера, с каких адресов сайту разрешено обращаться к серверу |
| XSS | Атака, при которой на страницу попадает чужой вредоносный скрипт |
