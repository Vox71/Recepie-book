# Спринт 4: вход, холодильник, реальные рецепты и проверка рекомендаций

Это отчёт об учебном спринте проекта **Recepie-book** — сервиса с рецептами, холодильником и
рекомендациями. Документ написан простым языком: его можно читать на защите, показывать
преподавателю и давать студентам, которые ещё не разбираются в коде.

Спринт 3 дал сервер и «скелет» сайта: страницы открывались, но данные были демонстрационными, а
форма входа ничего не отправляла. Спринт 4 — про то, чтобы сайт начал работать с настоящими
данными.

## 1. Задача 1. API-клиент, авторизация и защищённое API холодильника

**Автор: Иван Савчук.**

### Шаг 1. Понять, зачем нужен вход

Сайт — это дом, а сервер — охраняемый склад с продуктами и рецептами. Раньше сайт мог только
заглядывать в окно: форма входа была нарисована, но кнопка «Войти» ничего не делала.

Без входа не работает ничего личного:

- холодильник — у каждого пользователя свои продукты;
- таймеры — чужой таймер нельзя увидеть или отменить;
- избранное — привязано к конкретному человеку.

Поэтому первая задача — не «красивая кнопка», а настоящая дверь в приложение.

### Шаг 2. Сделать общий клиент для запросов

В `frontend/src/api/client.ts` появился один способ общаться с API. Страницы больше не пишут
`fetch` каждая по-своему — они вызывают `apiRequest`. Клиент:

- берёт адрес сервера из `VITE_API_URL` (по умолчанию `http://localhost:8000`);
- прикладывает заголовок `Authorization: Bearer <токен>`, если токен есть;
- отправляет JSON и разбирает ответ;
- превращает ошибки сервера в понятный `ApiError` со статусом и сообщением.

Это важно, потому что иначе каждый экран мог бы забыть приложить токен или по-своему разобрать
ошибку. Теперь правило одно для всех.

### Шаг 3. Сделать настоящий вход

В `frontend/src/api/auth.ts` есть `loginRequest(email, password)`. Он отправляет `POST /login` и
получает токен. Сервер уже умел это делать в спринте 3 — менять API не пришлось.

`AuthProvider` в `frontend/src/auth/AuthContext.tsx` хранит токен и email в `localStorage`:

- после перезагрузки страницы вход не теряется;
- `useAuth()` даёт любому компоненту понять, вошёл человек или нет;
- `logout()` удаляет токен и email;
- `login()` сохраняет токен после успешного ответа сервера.

Пароль нигде не сохраняется. В `localStorage` лежит только пропуск — токен — и email для подписи
в шапке.

`LoginPage` теперь:

- хранит email и пароль в состоянии;
- показывает «Входим…», пока идёт запрос;
- при неверных данных показывает «Неверный email или пароль»;
- при другой ошибке показывает сообщение API;
- после успеха переходит на холодильник или на страницу, куда пользователь шёл до этого.

### Шаг 4. Закрыть личные страницы

`frontend/src/auth/RequireAuth.tsx` — «вахтёр» у личных страниц. Если токена нет, он отправляет
гостя на `/login` и запоминает, куда тот шёл. После входа пользователь возвращается на нужный
адрес, а не всегда на главную.

Защищены:

- `/recipes/:recipeId` — страница рецепта;
- `/fridge` — холодильник;
- страница 404 внутри личного каркаса.

`/login` остаётся открытым: туда и должен попадать человек без токена.

### Шаг 5. Сделать защищённое API холодильника

На сервере появились адреса:

- `GET /profile/fridge` — список продуктов текущего пользователя;
- `POST /profile/fridge` — добавление;
- `DELETE /profile/fridge/{id}` — удаление только своего продукта;
- `DELETE /profile/fridge/expired` — удаление только своих просроченных продуктов.

Владелец всегда берётся из токена, а не из тела запроса или URL. Чужой продукт даёт `404`.

В шапке `SiteHeader` появились email вошедшего пользователя и кнопка «Выйти». «Мой холодильник»
стал настоящей ссылкой, а не заглушкой.

### Шаг 6. Проверить сценарий

1. Пользователь открывает `/login` и вводит email и пароль.
2. Сайт отправляет их на `POST /login`.
3. Сервер возвращает токен.
4. Сайт сохраняет токен в `localStorage`.
5. При переходе на защищённую страницу `RequireAuth` проверяет токен.
6. Каждый запрос к личным данным уходит с `Authorization: Bearer <токен>`.
7. Если сервер отвечает `401`, токен удаляется и пользователь возвращается на `/login`.
8. Кнопка «Выйти» делает то же самое вручную.

### Шаг 7. Проверить тестами

На ветке `feat/fridge-auth`:

- **49 фронтенд-тестов** (Vitest + Testing Library);
- **159 бэкенд-тестов** на реальной PostgreSQL;
- `npm run typecheck`, `lint`, `format:check`, `build` — без ошибок;
- `ruff`, `black`, `pytest` — без ошибок;
- покрытие фронтенда — выше порога 80 %.

### Шаг 8. Запомнить ограничения

- Регистрация в интерфейсе пока заглушка.
- Токен в `localStorage` уязвим к XSS; более защищённый вариант — `httpOnly` cookie.
- Refresh token нет: после истечения срока пользователь входит заново.

**Итог:** сайт научился входить в аккаунт и прикладывать пропуск к личным запросам. Вёрстка
холодильника в эту задачу не входит — это следующая задача.

## 2. Задача 2. Вёрстка страницы холодильника

**Автор: Артём Потапов.**

### Шаг 1. Понять, что должно быть на экране

Холодильник — главный личный экран пользователя. На нём должно быть видно:

- сколько всего продуктов;
- что скоро истекает;

Без удобного экрана API холодильника есть, но пользователь им не пользуется. Поэтому вёрстка
выделена в отдельную задачу, хотя технически она делалась в той же ветке, что и API.

- кнопку «Удалить просроченные»;
- сводку;
- список продуктов;
- фильтры;
- боковую колонку советов.

Стили лежат в `FridgePage.module.css`.

### Шаг 3. Сделать переиспользуемые компоненты

Каждый компонент имеет свой CSS-модуль. Цвета и отступы берутся из токенов дизайн-системы, а не

### Шаг 4. Добавить фильтры и состояния

Фильтры:

Состояния страницы:

Статусы продуктов переданы текстом («Свежий», «Скоро истекает», «Просрочен»), а не только цветом:

## 3. Задача 3. Парсинг рецептов, реальные данные и нормализация количеств

**Авторы: Елизавета Тропина и Михаил Волков.**

### Шаг 1. Понять, чего не хватает в датасете

В открытом датасете povarenok есть только:

- ссылка на страницу рецепта;
- название;
- список ингредиентов.

Этого мало для приложения. На самой странице есть ещё:

- пошаговая инструкция;
- время приготовления;
- количество порций;
- калорийность и БЖУ;
- фотографии шагов.

Поэтому импорт разделён на два этапа:

```text
CSV/parquet датасета
        ↓
импорт: recipes + recipe_ingredients
        ↓
обогащение: скачать страницу → разобрать HTML
        ↓
recipe_steps, recipe_nutrition, servings, cooking_time_minutes
```

### Шаг 2. Импортировать датасет

Импортёр `backend/app/importer/povarenok.py`:

- читает CSV, JSON, JSONL или parquet;
- нормализует название и ингредиенты;
- пишет `recipes` и `recipe_ingredients`;
- идемпотентен по `source_url`;
- не пишет инструкции, порции, время и сложность — в датасете их нет.

Повторный импорт не создаёт дубликаты. Данные и HTML-кэш не коммитятся.

### Шаг 3. Разобрать страницы рецептов

`backend/app/importer/pages.py` и `enrich.py`:

- скачивают HTML страницы;
- разбирают microdata `itemprop`;
- записывают шаги в `recipe_steps`;
- записывают общий текст шагов в `recipes.instruction`;
- заполняют время, порции и КБЖУ;
- кэшируют HTML в `backend/data/pages/`;
- останавливаются после нескольких `403/429`;
- умеют `--force` и `--refresh`.

Парсер ищет `recipeInstructions`, `recipeYield`, `totalTime`, `nutrition`. Классы CSS не
используются: они меняются при редизайне, а микроразметка живёт дольше.

### Шаг 4. Проверить качество на 500 рецептах

| Показатель | Результат |
|---|---:|
| Импортировано рецептов | 500 |
| Ингредиентов | 4 392 |
| Страниц обогащено | 500 |
| Ошибок | 0 |
| Шаги есть | 395 рецептов (79 %) |
| Время есть | 346 рецептов (69 %) |
| Порции есть | 284 рецепта (57 %) |
| КБЖУ есть | 494 рецепта (99 %) |

Почему не 100 %:

- не на каждой странице сайт публикует время и порции;
- у 105 рецептов нет блока с шагами — это видно в HTML, парсер не выдумывает данные;
- у части ингредиентов нет количества: например, «Соль» без граммовки.

### Шаг 5. Нормализовать количества

В `recipe_ingredients` добавлены:

- `quantity_value` — число;
- `quantity_unit` — единица.

Правила:

- граммы и килограммы → граммы (`1 кг` → `1000 г`);
- миллилитры и литры → миллилитры;
- штуки, зубчики, ложки, щепотки, стаканы остаются в своих единицах;
- «по вкусу» и диапазоны вроде `200–300 г` не превращаются в одно число.

`quantity_text` остаётся исходной строкой. Старые записи можно обновить командой:

```bash
python -m app.importer --normalize-quantities
```

## 4. Задача 4. Пересчёт порций и реальная карточка рецепта

**Автор: Михаил Волков.**

### Шаг 1. Понять пользовательский сценарий

В макете рецепт был красивой картинкой с демонстрационными данными. Пользователю нужно другое:
открыть реальный рецепт, увидеть состав и приготовить столько, сколько нужно его семье.

Если рецепт рассчитан на 2 порции, а пользователь хочет 4:

- паста: `200 г` → `400 г`;
- томаты: `4 шт.` → `8 шт.`;
- масло: `2 ст. л.` → `4 ст. л.`;
- КБЖУ увеличивается в два раза;
- значения на 100 г не меняются.

### Шаг 2. Заменить мок на реальный API

`RecipePage` больше не импортирует `src/mocks/recipe.ts`. Вместо мока — `GET /recipes/{id}`:

- название, время, сложность и порции;
- ингредиенты из `ingredient_list`;
- шаги из `steps`;
- КБЖУ из `nutrition`;
- ссылка на источник.

В `frontend/src/api/recipes.ts` появились DTO и `getRecipe(token, recipeId, signal)`. Добавлены
состояния загрузки, ошибки, `404` и повтор запроса.

### Шаг 3. Добавить управление порциями

Пользователь вводит целое положительное число. Формула:

```text
коэффициент = выбранные порции / базовые порции
новая граммовка = исходная граммовка × коэффициент
```

Некорректный ввод (`0`, минус, строка, пустое поле) не применяется: остаётся последнее корректное
значение, а под полем появляется ошибка.

### Шаг 4. Обработать отсутствие базовых порций

Примерно у 58 % страниц povarenok количество порций не опубликовано. Нельзя подставлять случайное
число. Поэтому интерфейс просит:

> На сколько порций рассчитан рецепт?

Пока пользователь не введёт корректное базовое число, пересчёт отключён.

### Шаг 5. Пересчитать ингредиенты и КБЖУ

Для пересчёта используются `quantity_value` и `quantity_unit` из задачи 3:

- масса — в граммах;
- объём — в миллилитрах;
- штуки, ложки, зубчики, щепотки — в своих единицах;
- «по вкусу» и диапазоны не превращаются в выдуманное число.

Если единицу нельзя честно перевести в граммы, она масштабируется в исходной единице. Например,
`2 ст. л.` при удвоении становятся `4 ст. л.`, а не «60 г» без таблицы плотностей.

КБЖУ:

- общие калории, белки, жиры и углеводы умножаются на коэффициент;
- значения на 100 г остаются прежними;
- значения на порцию делятся на новое количество порций.

### Шаг 6. Добавить статусы ингредиентов

Если холодильник доступен, страница отмечает, какие продукты уже есть, а каких не хватает. Если
запрос холодильника не удался, показывается «Статус неизвестен», а не ложное «Нужно добавить».

### Шаг 7. Проверить

Ветка: `feat/recipe-servings`.

- `npm run typecheck`;
- `npm run lint`;
- `npm run format:check`;
- `npm run test:run` — **54 теста**;
- `npm run test:coverage` — выше порога 80 %;
- `npm run build`.

Тесты покрывают загрузку рецепта, пересчёт граммовок и КБЖУ, отсутствие базовых порций, неверный
ввод, `404`, повтор запроса, недоступность холодильника, шаги и источник.

### Шаг 8. Запомнить ограничения

- Количество порций не сохраняется на сервере: это локальное состояние отображения.
- `шт.`, `ст. л.`, `щепот.` не переводятся в граммы без плотности продукта.
- Аллергены в карточке пока не выводятся: в текущем API рецепта их нет.
- Используется заглушка фотографии, а не реальное фото блюда.

**Итог:** пользователь открывает реальный рецепт, меняет порции и видит пересчитанные граммовки и
КБЖУ.

## 5. Задача 5. Тестирование ИИ-модели

**Автор: Владислав Журавлев.**

### Шаг 1. Понять, что именно проверяем

Недостаточно сказать «модель работает». Нужно проверить, что она:

- не запоминает обучающие рецепты;
- находит рецепты с нужным продуктом на новых данных;
- не становится лучше только за счёт подгонки под один набор;
- ведёт себя предсказуемо на пустых и странных запросах.

Поэтому тестирование ИИ-модели — это не только `pytest`, но и отдельный ML-эксперимент.

### Шаг 2. Выбрать протокол

Использовали **leave-one-ingredient-out**:

1. из рецепта убирали один ингредиент;
2. остальные ингредиенты становились запросом;
3. проверяли, попали ли в топ рецепты, где скрытый ингредиент есть.

Это не совсем сценарий «что приготовить из холодильника», но хороший способ проверить, умеет ли
модель связывать продукты. Скрытый продукт отсутствует в запросе, поэтому нужно угадать его по
остальным продуктам.

### Шаг 3. Разделить данные

Корпус разделили на три части:

- **train** — на нём учим IDF и co-occurrence;
- **validation** — на нём выбираем веса;
- **test** — на нём показываем финальные числа.

Если обучать и проверять на одних и тех же рецептах, модель может просто запомнить ответы. Split
по рецептам это исключает.

В финальном прогоне:

- 8 398 рецептов — train;
- 1 800 — validation;
- 1 800 — test;
- по 1 000 запросов на validation и test.

### Шаг 4. Сравнить подходы

- **BM25** — учитывает редкие слова и длину рецепта;
- **co-occurrence / PMI** — ищет продукты, которые часто встречаются вместе;
- **гибрид** — складывает BM25, PMI и долю пересечения ингредиентов.

### Шаг 5. Получить метрики

На test-выборке из 1 000 запросов:

| Модель | P@1 | P@10 | Hit@10 | MRR@10 |
|---|---:|---:|---:|---:|
| BM25 | 0.287 | 0.291 | 0.739 | 0.427 |
| co-occurrence | 0.420 | 0.405 | 0.818 | 0.552 |
| **гибрид** | **0.445** | **0.430** | **0.822** | **0.565** |

На validation гибрид показал P@10 0.438 и MRR 0.600. Разрыв с test небольшой, значит веса не
подогнаны под один набор.

### Шаг 6. Понять, что означают числа

- **P@1 = 0.445** — примерно в 44,5 % запросов первый же рекомендованный рецепт содержит скрытый
  продукт.
- **P@10 = 0.430** — в среднем 43 % мест в топ-10 занимают рецепты с нужным продуктом.
- **Hit@10 = 0.822** — в 82,2 % запросов хотя бы один полезный рецепт попал в топ-10.
- **MRR@10 = 0.565** — первый полезный рецепт в среднем стоит довольно высоко.

Это не «43 % пользователей получили идеальный ответ». P@10 — средняя доля релевантных рецептов
в десяти показанных.

### Шаг 7. Проверить дополнительные условия

- одинаковый `seed` даёт одинаковый split;
- train/validation/test не пересекаются;
- пустой запрос и запрос без релевантных рецептов;
- поведение при отсутствии продукта в словаре;
- метрики считаются на отложенных запросах, а не на обучающих.

### Шаг 8. Запомнить ограничения

- Используется только список ингредиентов, без шагов и КБЖУ.
- SBERT и пользовательские профили холодильника не входят в этот прогон.
- Оценка сделана по 1 000 запросов, а не по всему test-набору.
- Метрики описывают учебный протокол, а не гарантируют такое же качество в реальном UI.

**Итог:** модель проверена на отложенных данных, гибридный подход показывает лучший результат.

## 6. Задача 6. Проверка на отказоустойчивость системы

**Автор: Егор Мокрецов.**

### Шаг 1. Понять, зачем это нужно

Приложение должно не только работать «в идеальных условиях», но и объяснять, что произошло,
если что-то сломалось. Пользователь не должен видеть белый экран или traceback.

### Шаг 2. Проверить отказы базы

- PostgreSQL недоступна — понятная ошибка `503`, без частично записанных данных.
- Пул соединений исчерпан — запрос не висит бесконечно, соединение возвращается.
- Ошибка внутри транзакции — `rollback`, данные не остаются в полусыром виде.

### Шаг 3. Проверить авторизацию и доступ

- неверный или просроченный токен — `401`, очистка токена, возврат на `/login`;
- чужой ресурс — `404`, без раскрытия существования;
- пустой холодильник — понятное сообщение, а не пустой экран.

### Шаг 4. Проверить парсер и импорт

- таймаут povarenok — рецепт не считается разобранным, импорт продолжается;
- `403/429` от сайта — остановка после серии ошибок, без потери уже импортированного;
- битый HTML — запись не ломает транзакцию;
- повторный запуск — идемпотентность.

### Шаг 5. Проверить модель

- отсутствующий артефакт — fallback на bag-of-lemmas;
- битый артефакт — предупреждение в лог, fallback;
- пустой каталог или пустой запрос — понятный ответ, а не падение.

### Шаг 6. Проверить фронтенд

- ошибка загрузки — сообщение и кнопка «Повторить»;
- отмена запроса при размонтировании;
- `401` — возврат на вход;
- пустые состояния — понятный текст.

### Шаг 7. Оформить результат

Для каждого отказа записать:

- отказ;
- ожидаемое поведение;
- фактический результат;
- найденный дефект;
- исправление или issue с меткой `tech-debt`.
