# Практика 5: рефакторинг и code review

Этот документ описывает процесс, по которому шесть участников делают по одному PR с
рефакторингом из [`docs/pract5_resolve`](pract5_resolve), проводят два раунда code review и
оформляют текстовый отчёт.

## 2. Ревьюеры

На каждый PR назначается один основной ревьюер — другой студент. Второй ревьюер не обязателен.
Лид или преподаватель может подключиться как арбитр, если автор и ревьюер не согласны или если
нужно проверить смежную зону. Арбитр не может быть автором этого же PR.

| PR | Автор | Основной ревьюер | Арбитр |
|---|---|---|---|
| 01 parser | Волков Михаил | Журавлев Владислав | по запросу |
| 02 timer | Журавлев Владислав | Потапов Артем | по запросу |
| 03 ingredients | Потапов Артем | Савчук Иван | по запросу |
| 04 pageframe | Савчук Иван | Тропина Елизавета | по запросу |
| 05 engine | Тропина Елизавета | Мокрецов Егор | по запросу |
| 06 enrich | Мокрецов Егор | Волков Михаил | по запросу |

Каждый студент ревьюит ровно один чужой PR. Свой PR ревьюить нельзя.

## 3. Два раунда review

Раунд — это один цикл «ревьюер посмотрел → оставил замечания; автор ответил и исправил».
Два раунда — это два таких цикла в **одном PR**, а не два PR и не две ветки.

```text
PR открыт, commit A
        ↓
Раунд 1: ревьюер читает A, оставляет замечания → Request changes
        ↓
Автор: commits B1, B2, отвечает на комментарии → Re-request review
        ↓
Раунд 2: ревьюер проверяет diff A..B и тесты → Approve
        ↓
Merge
```

Правила раунда:

- не больше 10–20 замечаний за раунд;
- повторяющиеся ошибки объединяются: «этот же приём ещё в трёх местах»;
- замечание содержит: что вижу → почему это проблема → что предлагаю → пункт style guide;
- стиль не обсуждается вкусом: ссылка на [`docs/pract3-style-guide.md`](pract3-style-guide.md);
- после `Approve` автор не пушит новый код, иначе approval сбрасывается;
- если во втором раунде нужны исправления, они делаются в том же PR и проверяются там же.

## 4. Размер PR

Ориентир методички — участок кода на 150–200 строк. Это **область ревью**, а не требование
искусственно раздуть diff: у части заданий изменения занимают 40–100 строк.

В описании PR нужно указать:

- файлы и строки, которые входят в область ревью;
- примерный размер области;
- `git diff --stat`.

Жёсткий предел — 400 изменённых строк. Если PR больше, его нужно разделить. Нельзя добавлять
чужие файлы и посторонние исправления только ради количества строк.

## 5. Что не меняется

Во всех PR запрещено менять:

- адреса API и HTTP-коды;
- названия полей JSON;
- таблицы и колонки базы;
- поведение: те же входные данные должны давать тот же результат;
- файлы, не указанные в задании.

Если по ходу ревью найдена проблема рядом, она оформляется отдельным issue с меткой `tech-debt`,
а не исправляется в этом PR.

## 6. Текстовые отчёты

Основной артефакт для преподавателя — `.txt`-файлы с дословными текстами PR, комментариев,
ответов и оценок. Ссылки на GitHub недостаточно.

```text
docs/pract3-reviews/
  01-volkov-parser.txt
  02-zhuravlev-timer.txt
  03-potapov-ingredients.txt
  04-savchuk-pageframe.txt
  05-tropina-engine.txt
  06-mokretsov-enrich.txt
  TEMPLATE.txt

docs/pract3-review-report.txt
docs/pract5-report.txt
```

В каждом файле PR должны быть:

- автор, вариант, ветка, base/head, ревьюеры, ссылка на PR;
- дословный заголовок и описание PR;
- область ревью и `git diff --stat`;
- pract5: было, стало, причина, выгода, техдолг до/после;
- раунд 1: комментарии ревьюера, ответы автора, commit исправления;
- раунд 2: что проверено, комментарии, approve;
- оценки ревьюера и арбитра, если он участвовал;
- merge commit и оставшиеся задачи.

Шаблон: [`docs/pract3-reviews/TEMPLATE.txt`](pract3-reviews/TEMPLATE.txt).

Тексты собираются после merge в отдельном docs-PR, чтобы не менять код и не сбрасывать
approval. Автор проверяет свой файл перед merge отчёта.

## 7. Оценка

Каждый PR оценивается по 10-балльной шкале. Основной ревьюер ставит оценку после каждого
раунда; арбитр может скорректировать итог, если ревьюеры расходятся.

| Критерий | Баллы |
|---|---|
| Корректность: поведение не изменилось, границы обработаны | 0–2 |
| Читаемость: имена, размер функций, соответствие style guide | 0–2 |
| Тесты и CI: старые зелёные, новые границы покрыты | 0–2 |
| Отчёт pract5: было/стало, причина, выгода, техдолг | 0–2 |
| Процесс: два раунда, ответы, отсутствие выхода за рамки | 0–2 |

В раунде 1 оценка предварительная, в раунде 2 — итоговая.

## 8. Порядок работы

### Подготовка

1. Зафиксировать базу и поставить тег `pract5-base`.
2. Создать ветки `refactor/pract5-*` от `main`.
3. В каждом PR заполнить шаблон и указать ревьюера.
4. Настроить защиту `main`: PR обязателен, approval нужен, старые approval сбрасываются,
   обсуждения должны быть закрыты, CI должен быть зелёным.

### Автор

```bash
git switch main
git pull
git switch -c refactor/pract5-<имя>
```

Проверки бэкенда:

```bash
cd backend
ruff check .
black --check .
pytest
```

Проверки фронтенда:

```bash
cd frontend
npm ci
npm run format:check
npm run lint
npm run typecheck
npm run test:coverage
npm run build
```

### Ревью

1. Ревьюер проверяет границы PR, поведение, тесты и отчёт.
2. Оставляет замечания и `Request changes`, ставит предварительную оценку.
3. Автор отвечает, исправляет, пушит в ту же ветку и просит re-review.
4. Ревьюер проверяет diff между раундами, тесты и отсутствие новых изменений вне задачи.
5. После `Approve` PR мержится; после merge остальные ветки обновляются от `main`.

### Финальная проверка

```bash
cd backend
ruff check .
black --check .
pytest

cd ../frontend
npm ci
npm run format:check
npm run lint
npm run typecheck
npm run test:coverage
npm run build
```

После всех шести PR:

- заполнить `docs/pract3-review-report.txt` и `docs/pract5-report.txt`;
- проверить `git diff --stat pract5-base..main`;
- поставить тег `pract5-done`.
